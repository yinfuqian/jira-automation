# 原型设计准入审核

本 Skill 的问题是：**PRD 和产品原型初稿是否足够完整且相互一致，可以交给设计师精修？**

它只做业务准入审核，不判断产品使用了哪个生成 Skill 版本，不要求产品提供制作说明或静态门禁记录，也不修改 PRD、原型或审批状态。

## 运行环境适配（容器部署，先读这一节）

本技能随仓库 `skills/` 目录一起只读挂载进 Codex 容器，**技能目录固定为 `/data/skills/review-jira-design`**（桌面端为 `<仓库>/skills/review-jira-design`）。下面所有 `scripts/...`、`references/...` 都按这个绝对目录展开。

- **对 Jira 只读**：本技能不访问 Jira、不发任何网络写请求，输入只有本地的 PRD 与原型文件；需求单里的附件由调用方（如 `jira-gate-1-mock`）先下载到工作目录，再以文件路径传入。
- **产物落在调用方的工作目录**：报告 HTML 的落盘位置由调用方指定（`jira-gate-1-mock` 用 `<工作目录>/work/jira-gate/<KEY>/design/`），不要写进只读的技能目录。
- **截图能力随环境降级**：`scripts/capture_prototype_evidence.mjs` 按 `Playwright → 本机 Chrome/Edge 的 Playwright → Chrome/Edge headless CLI` 顺序尝试；容器内通常没有浏览器，此时脚本会失败——按「无法截取时」处理，写清 HTML 路径、selector 与"截图未验证"原因，**不要伪造截图，也不要自行安装浏览器**（桌面端才能拿到内联截图）。
- 需要临时指定运行时可以用环境变量：`ZY_ADMISSION_NODE_MODULES`（Playwright 所在 `node_modules`）与 `ZY_ADMISSION_BROWSER`（浏览器可执行文件路径）。

## 输入

必需输入：

1. 定稿 PRD：精确路径和版本。
2. 产品原型初稿：具体业务 HTML 和必要资源。

可选输入：PRD Review 结论、风险分析、变更说明、运行记录或已确认的产品答复。

制作说明、Skill 版本和静态门禁结果只作为可选辅助证据。缺少它们不应单独阻断 G1；只有原型无法读取、无法编辑或无法核对时，才记录为原型交付问题。

如果存在多个 PRD、多个原型或多个版本，先锁定用户明确指定的唯一对象；不能按相似文件名自行选择。

## 执行步骤

### 1. 读取标准并确定范围

读取本 Skill 的 [审核检查项](references/review-checks.md)，并以《产品设计协作标准》中的“PRD 准出”和“产品原型初稿准出”为主要检查基线。设计精修稿的 G2/G3 100%要求只用于识别后续交接边界，不提前当作本次 G1 的全部要求。

以 PRD 为唯一业务事实源，先确定本轮目标、角色、页面、主流程、分支、字段、状态、权限、边界规则和验收标准。原型、截图、历史页面和导航索引只能提供证据，不能新增业务事实。

### 2. 检查 PRD 是否达到准出

检查以下内容是否完整、明确、可追溯：

- 业务背景、目标、范围和非目标；
- 角色、权限、入口和核心场景；
- 主流程及关键分支；
- 字段含义、类型、校验、必填条件、默认值和示例；
- 正常、加载、空、失败、异常、禁用等状态及状态变化；
- 边界规则，包含“触发条件 → 处理方式 → 用户反馈”；
- 成功、取消、返回、重复操作、失败恢复和副作用；
- 可验证的验收标准；
- 版本、维护人、更新时间、变更记录和待确认事项。

核心流程、字段、状态、权限、边界或验收标准缺失时，属于阻断问题。普通组件选型、CSS 写法、接口实现、数据库字段和部署参数不作为 PRD 缺失项。

### 3. 检查原型初稿是否达到准出

对照同一版本 PRD 检查：

- 核心流程是否能从入口走到结果；
- 关键分支、异常路径和必要页面是否覆盖；
- 字段、枚举、文案、操作顺序和成功落点是否一致；
- 关键状态、权限差异、禁用条件和失败反馈是否体现或有明确说明；
- 边界规则是否有对应的触发、处理和用户反馈；
- 原型是否新增了 PRD 未定义的业务规则；
- 原型是否遗漏 PRD 中影响设计的内容。

《产品设计协作标准》中的初稿指标可作为量化证据：分支覆盖率建议 ≥95%、边界规则覆盖率建议 ≥90%、五类基础状态至少体现 3 类。使用时必须说明分母、排除项和计算范围；百分比不能抵消核心流程或状态阻断。

### 4. 建立需求—页面映射

对每个核心 `G / FR / BR / IR / AC`，或没有编号时的 PRD 章节，记录：

```text
需求依据 → 角色/前置 → 页面/入口/操作 → 结果与状态 → 原型位置/演示路径 → 覆盖结论
```

不要因为页面上有按钮就认定需求已覆盖；必须能说明操作结果、状态和业务影响。

### 4.1 优先使用可视化证据

问题定位优先输出可展开的内联证据，而不是只写章节或行号：

- **PRD 证据**：引用最小必要的原文摘录，标出章节、稳定 ID 或表格行，并用加粗标记关键句；不要整页复制。
- **原型证据**：在可以打开原型且状态可复现时，截取对应页面/区域，标出问题位置，并记录 HTML 路径、CSS selector 或操作路径、视口和状态。
- **并排说明**：证据区左右对照“PRD 要求 → 原型实际表现”；差异、影响和建议动作写在所属问题里。

优先使用本包的 [证据截取说明](references/evidence-capture.md)。截图应作为 data URL 嵌入最终 HTML，避免报告依赖外部路径。无法运行、资源不可用或状态无法复现时，不伪造截图，改用源码位置并标记“截图未验证”。截图是定位证据，不替代 PRD 文字和一致性判断。

### 5. 形成可执行问题和建议

每条问题必须包含：

- 唯一编号和级别：阻断 / 需补齐 / 建议；
- PRD 章节或 HTML 位置；
- 实际缺失或不一致；
- 对设计、开发或验收的影响；
- 责任角色；
- 具体修改动作；
- 完成标准或复核证据。

如果存在截图，问题下的内联证据展示截图并标注证据编号 E-00x；如果没有截图，必须给出精确的 HTML selector、行号或可复现操作路径，并在展开区写明原因。

只把会改变业务范围、规则、权限、结果或验收的问题交给产品确认。资料中可以自行核对的事实由审核者继续查，不要把组件、代码或环境问题转给产品经理。

### 6. 输出结论

按以下顺序判定：

| 结论 | 条件 |
| --- | --- |
| **退回补齐** | PRD P0 内容缺失，或 PRD 与原型存在影响流程、字段、状态、权限、结果的关键冲突 |
| **有条件通过** | 核心内容一致，只剩可隔离、可并行补齐的非阻断事项 |
| **通过** | PRD 达到准出，原型初稿与 PRD 一致，没有阻断问题 |
| **审核未完成** | 文件无法读取、对象无法唯一定位，或关键证据不足以判断 |

已确认失败优先于证据缺失；不能用其他页面通过、平均覆盖率或页面相似度抵消阻断问题。

### 7. 生成报告并复核

使用 [HTML 报告模板](references/report-template.html) 生成一份简洁、自包含、可直接打开的 UTF-8 HTML；只写结论、证据和建议，不写审核过程记录。

保留模板的 `<style>` 和 `<script>` 原样，只替换 `{{...}}` 占位符及其注释中的示例内容。模板已经固定字号层级、配色、分隔线、标签列对齐和证据展开交互，不要重写、精简或另起一套样式。

填写规则：

- **章节顺序**：结论与阻断原因 → 摘要指标 → 需求—页面映射（可选）→ 问题与可执行建议 → 最小补齐清单 → 未验证项。没有需求映射时整段删除；不另设“证据卡片”章节。
- **问题**：按阻断 → 需补齐 → 建议排序。左列写需求依据、原型位置、实际差异；右列写影响、责任人和修改动作、完成标准。
- **证据**：内联在对应问题下方并默认折叠。问题标题行放“查看证据 E-00x”按钮，展开区放证据编号、对应问题、证据标题和“收起”；没有证据的问题不渲染按钮和展开区。
- **证据内容**：只放与结论直接相关的 PRD 摘录和截图。差异影响与建议动作只写在问题里，证据区不重复；截图未验证时在展开区页脚写明原因，不用占位图。
- **交付前**：删除模板中的 HTML 注释，正文里不保留版式说明。

补齐后沿用原问题编号，只复核受影响的 PRD 章节、页面、状态和一致性关系，记录已关闭、仍存在或未验证。通过后交给设计精修，不自动开始 G2/G3、开发或 Jira 流转。

## 证据边界

每项结论标记为：

- **PRD 证据**：来自指定版本 PRD；
- **原型证据**：来自具体 HTML 的位置或演示路径；
- **运行证据**：本轮实际操作后的观察；
- **未验证**：当前资料无法判断。

静态源码检查、Skill 来源和制作说明可以增强可信度，但不是本 Skill 的核心准入条件。未实际运行时，不宣称核心流程已经运行通过。
