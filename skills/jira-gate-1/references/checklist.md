# PRD 需求准入 Checklist

## 1. 定位

本清单是 Jira 从“需求设计”流转到“开发设计中”的 G1 需求准入正式判定依据。

- **入口状态**：需求设计。
- **目标状态**：开发设计中。
- **提交角色**：产品经理。
- **参与检查角色**：产品架构师、研发、测试。
- **最终确认角色**：产品架构师。
- **正式结论**：通过 / 退回补充。

G1 只判断产品业务逻辑能否唯一指导研发设计和测试验收，不检查文档格式或纯技术实现。PRD 可以使用段落、列表或表格，不强制提供状态权限矩阵、追溯矩阵、原型或图示。

## 2. 权威来源与准入输入

- 指定版本 PRD 是当前需求唯一业务事实源；项目中正式产物名为 PRD-DELIVERY 时，以该版本为准。
- `G/FR/BR/IR/AC` 用于追溯。PRD 已使用这些标识时沿用；缺少固定编号格式不作为业务阻断。
- 原型、图示、Overview、Prompt 说明、截图、历史资料和 Review 结论只能作为证据，未经回填 PRD 不得定义新需求。
- 准入发现的新业务结论必须回填 PRD 并升版；技术事实由研发或对应专业角色补充。
- 只要求 PRD 文件、版本和需求 Owner 可定位。证据材料按需提供；材料缺失但不影响业务判定的，不作为准入阻断。

## 3. 判定原则

### 3.1 同一结果测试

对同一业务条件，两名合格研发仅依据 PRD 会得出不同的用户结果、权限、状态、数据含义、失败行为或 AC 时，判定业务逻辑未闭环，必须退回补充。

如果所有合理解释产生相同业务结果，差异只在实现方式、文档组织、原型表现或技术选型，则不阻断 G1。

### 3.2 核心链路

核心链路是完成主要目标必需的入口、角色、前置条件、关键规则、状态、权限、数据和异常恢复，覆盖 P0 及直接影响核心结果的 P1。

缺少核心业务事实，导致研发需要自行选择产品规则，或测试无法判断是否通过时，必须阻断。

## 4. 检查项等级

| 等级 | 含义 | 准入影响 |
|---|---|---|
| `MUST` | 所有需求必须满足 | 任一不满足即退回补充 |
| `CONDITIONAL` | 命中触发条件后必须满足 | 触发后等同 `MUST`；不触发需说明依据 |
| `SHOULD` | 有助于降低歧义和返工 | 不单独阻断，但需记录取舍 |
| `OBSERVE` | 进入研发后仍需关注的业务假设或风险 | 不代替缺失的业务事实，也不包装成已确认结论 |

## 5. `MUST`：所有需求必查

- [ ] **事实源**：PRD 文件和版本唯一可定位；目标、范围、规则、状态、权限、文案、异常和 AC 无冲突；其他材料的新增结论已回填。
- [ ] **目标与范围**：目标用户或业务对象、当前问题、影响、本期包含范围和可观察成功结果明确；真实相邻范围歧义已说明。
- [ ] **核心链路**：主要角色、触发条件、前置条件、关键动作、关键分支和最终结果闭环，研发无需自行补齐业务路径。
- [ ] **业务规则**：`FR/BR/IR` 的触发、条件、优先级、例外、冲突处理和结果唯一；新增字段、状态和功能有当前目标、AC 或现实失败路径依据。
- [ ] **状态与权限**：核心状态的进入和退出条件、角色可见和可执行范围、用户可见操作、数据变化、业务副作用和操作结果唯一。
- [ ] **业务数据**：核心字段的来源、含义、默认值、空值、条件必填、枚举、读写和更新规则明确；接口编码和存储类型留给研发。
- [ ] **异常恢复**：现实可触发且改变用户结果的核心失败，已说明用户反馈、业务状态、数据保留和恢复方式；超时、重复操作、部分成功和不可逆操作按适用情况闭环。
- [ ] **验收标准**：关键及 P0/P1 FR、用户可见的 LLM 结果均有关联 AC；AC 可客观判断，覆盖主流程和关键失败，不使用“功能正常”等不可判断表述。

## 6. `CONDITIONAL`：命中场景后必查

命中场景只代表需要检查。细节只有会改变用户可见结果、权限、状态、数据含义、失败恢复、不可逆操作或 AC 时才阻断。

### 6.1 UI 与字段

触发：新增或修改页面、入口、字段、操作、用户可见状态或正式文案。

- [ ] 全部可编辑字段及影响理解、权限、状态或结果的只读字段有业务契约；动态字段的显示、隐藏、只读、脱敏和旧值处理明确。
- [ ] 保存、取消、返回、关闭、联动、筛选分页、批量操作和失败恢复的用户可见结果明确；PRD 不规定组件、校验位置或普通前端样式。

### 6.2 角色、状态与高风险确认

触发：角色、状态或操作组合会改变动作合法性、结果或验收。

- [ ] 不同角色在不同状态下的可见内容、可执行操作和结果能够唯一推导；不强制使用固定矩阵。
- [ ] 高风险确认、状态回退、非法迁移、越权、重复操作和数据过期时，确认或取消后的状态、数据和用户反馈明确。

### 6.3 跨系统、异步与外部依赖

触发：依赖外部系统、回调、消息、轮询、长任务、批处理或异步结果。

- [ ] 外部参与方、责任边界、触发条件、最终业务结果和用户可观察结果明确。
- [ ] 等待、处理中、成功、失败、超时、取消、重试、晚到结果、部分成功和依赖不可用时，用户行为及恢复状态明确。

### 6.4 迁移、历史兼容与存量对象

触发：修改历史数据、既有接口、字段、状态、配置或用户已有行为。

- [ ] 新旧行为、兼容范围、生效时点、历史数据口径，以及存量用户、旧页面和旧调用方的可观察结果明确。
- [ ] 迁移失败、回退和不可逆影响有产品边界及 AC；是否需要双轨、灰度或保留旧能力有明确业务决策。

### 6.5 LLM 业务质量、失败策略与副作用

触发：Prompt、模型输出、工具调用或模型失败会影响业务动作、状态或用户结果。

- [ ] 指令是新增还是调整、业务问题、输入范围、输出消费者、业务质量指标和数值门槛明确；候选模型、Schema、实验环境和账号不要求产品经理提供。
- [ ] 拒答、超时、非法输出、安全拦截、重试、降级和人工兜底时用户看到什么、业务状态是什么明确；模型触发副作用时，允许动作和 AC 明确。

### 6.6 性能、安全、隐私与合规

触发：相关约束会影响用户行为、可用性、合同、合规或验收。

- [ ] 产品级性能和容量承诺的口径、时间窗、样本条件可测；超限后的反馈、降级、排队、拒绝或恢复明确。
- [ ] 敏感数据范围、脱敏、保留、删除、审计及不同角色的可见性边界明确。

## 7. `SHOULD` 与 `OBSERVE`

### 7.1 `SHOULD`

- [ ] 目标较多或跨角色复杂时提供轻量 `G → FR → AC` 追溯矩阵。
- [ ] 复杂判断使用单一决策表，避免重复文字形成第二规则源。
- [ ] 参考资料标明用途，避免无说明的链接池。
- [ ] 核心场景提供代表性反例，避免只描述成功路径。

### 7.2 `OBSERVE`

只记录不会改变当前业务规则和验收结论、但研发或发布阶段需要继续验证的事项，例如实际流量、第三方稳定性和生产容量。

观察项必须说明当前事实、观察指标或证据、责任角色、检查时点和触发动作。若结果不同会改变用户行为或 AC，必须先回填 PRD，不能作为观察项放行。

## 8. 角色分工与产品决策

| 角色 | G1 职责 |
|---|---|
| 产品经理 | 确认会改变用户结果、规则、状态、权限、数据含义或 AC 的业务决策，回填并升版 PRD |
| 产品架构师 | 转换术语和产品口径；从现有资料、组织规范或历史一致做法澄清边角问题；确认最终 G1 |
| 研发 | 提供技术事实和可行性建议；不得替产品选择业务结果 |
| 测试 | 检查核心 AC 是否可观察、可判断、可执行 |

架构师在判定前先完成分流。能够唯一确定的边角问题直接记录答案和依据；纯技术问题交研发；原型、图示或文档问题交对应产物责任人。分流不得覆盖核心业务歧义，答案若会改变核心结果，必须转为 G1 阻断。

产品经理只处理业务决策。每次最多展示 5 张决策卡，按“目标范围、核心链路、规则状态、异常恢复、验收”归并。每张卡固定包含：

- 业务场景。
- 当前歧义。
- 两种可能结果及影响。
- 推荐方案及依据。
- 关联 `FR/BR/IR/AC` 或 PRD 章节。

决策卡不得出现 Java 类、接口设计、数据库类型、SQL、缓存 Key、Topic、线程池、部署参数、组件选型、模型 Schema 或环境配置。

## 9. Jira Agent 执行与输出

### 9.1 执行规则

Agent 每次执行全部 8 项 `MUST` 和命中的 `CONDITIONAL`，不抽样、不使用总分或平均分。单项结果为“满足 / 不满足 / N/A”；证据不足、语义冲突或无法唯一判断按“不满足”处理。`N/A` 只适用于未命中的场景项，并记录依据。

任意适用 `MUST` 或命中 `CONDITIONAL` 不满足，G1 结论只能为“退回补充”。架构师和研发已承接的澄清项不阻断 G1，但必须在 G2 结论前关闭；若改变核心业务事实，必须升版 PRD 并重新 G1。

### 9.2 Jira 评论

评论顶部只展示产品经理需要处理的信息：

```markdown
## G1 需求准入结论

- 结论：通过 | 退回补充
- 结论说明：{{一句话}}
- PRD：{{精确路径}}，版本：{{版本}}
- 产品决策：{{无；或最多 5 张决策卡}}
- 架构师澄清：{{数量及 G2 前关闭时点}}
- 研发技术澄清：{{数量及 G2 前关闭时点}}
- 复审范围：{{全量或受影响章节}}
- 产品架构师确认人／时间：
```

结论为“退回补充”时，在摘要后附决策卡；结论为“通过”时不展示逐项通过清单。评论下部保留机器判定明细：

| 检查项 | 等级 | 结果 | 证据位置 | 失败原因或判定依据 | 责任角色 | 关联 ID |
|---|---|---|---|---|---|---|
| {{检查项名称}} | MUST / CONDITIONAL / SHOULD / OBSERVE | 满足 / 不满足 / N/A | {{PRD 章节或材料}} | {{说明}} | {{角色}} | {{ID}} |

人肉评论可以补充证据或记录架构师澄清，但不能直接把 Agent 的“不满足”改成“满足”。收到证据或 PRD 新版本后，Agent 必须重新执行全部核心项和命中的场景项；已通过的 G1 也不因修改评论文字而改变。

## 10. 生效、复审与指标

- 通过 G1 后，研发依据该版本 PRD 和 `Project.md` 进入技术方案设计。
- 目标范围、核心规则、状态权限、数据含义、关键异常或 AC 发生变化时，必须升版 PRD 并重新 G1；纯技术或展示形式变化不触发重新 G1。
- 已通过 G1 的历史需求不追溯作废；新版规则从下一次判定开始执行。
- 必须统计 G1 执行率、无记录流转次数和核心阻断关闭率，目标分别为 100%、0、100%。
- 首次通过率仅作改进观察项，不设惩罚阈值，不以数量压降替代真实业务检查。

## 11. 判定示例

| 场景 | 结论 | 原因 |
|---|---|---|
| 简单后端需求已说明触发、结果、权限和 AC，无原型或技术细节 | 通过 | 核心业务语义已唯一，缺失的是非阻断产物或技术事实 |
| 同一状态下既写“可重新提交”又写“提交后不可修改”，未说明条件 | 退回补充 | 两种业务结果都合理，未通过同一结果测试 |
| 关键角色能否查看或操作数据未说明 | 退回补充 | 核心权限和用户结果不唯一 |
| 核心失败后用户看到什么、数据是否保留未说明 | 退回补充 | 核心异常恢复未闭环 |
| P0/P1 关键功能缺少可验证 AC | 退回补充 | 测试无法判断是否通过 |
| LLM 业务门槛、失败行为和副作用 AC 明确，但缺 Schema 或实验配置 | 通过，技术问题交研发 | 缺的是技术专项输入，不是产品事实 |
| LLM 可能改变业务状态，但拒答和降级后的用户结果未定义 | 退回补充 | 模型失败会改变用户结果和状态 |
| 原型、图示或文档排版缺失，但 PRD 业务语义可唯一理解 | 通过，对应责任人后续补齐 | 展示载体缺失不等于产品语义缺失 |
