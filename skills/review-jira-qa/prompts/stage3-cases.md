# 测试用例设计 Prompt

本文件同时承载阶段二的测试点设计规则（「内容规范」中关于正式叶子、标题、notes 与编号的部分）和阶段三的用例转换规则。阶段三基于人工复核后的测试方案和人工审核后的测试点 XMind，先刷新并修正最终测试方案，再设计完整、可执行的测试用例。冲突裁决：**契约**（交付物字段、命名、目录、阶段门禁）以 `prompts/contract.md` 为准；**方法**（分析规则、设计细则、合并与判断策略）以本文件为准。

## 输入与阶段门禁

- 人工复核后的测试方案：必需，是范围、策略、资源、风险和取舍基线。
- 人工审核后的测试点 XMind：必需，是唯一最终测试点基线。
- Jira Key：可显式提供，也可从当前流程或两个标准文件名前缀中唯一确定。
- 缺少任一审核后文件、多个可信 Key 冲突、测试方案与 XMind 不在同一 `outputs/<scope>/<JiraKey>/` 需求交付根目录或页面路径仍未确认时，停止对应正式交付。

## 执行顺序

1. 对照最终 XMind 检查测试方案中的范围、重点、策略、风险、资源和数据要求。
2. 刷新并修正标准命名的最终测试方案。
3. 依据最终测试点生成 Excel 与 Xray CSV。
4. 回读最终方案、Excel 和 CSV，完成一致性校验。

## 目标
输出覆盖充分、结构清晰、适合落地执行和后续自动化转换的测试用例。

## 默认输出字段
必须包含以下字段（与 `prompts/contract.md` 的测试用例契约一致）：
- 用例编号
- 模块/分类
- 用例标题
- 前置条件
- 测试数据
- 测试步骤
- 预期结果
- 优先级
- 用例类型
- 是否适合自动化
- Requirements

如需求或测试方案另有要求，可补充测试目标等字段，但不得省略上述必含字段。

## 内容规范
- XMind 中无业务子 topic、标题符合 `【模块名称】具体测试场景` 且 notes 结构完整的叶子，才是正式用例叶子。禁止将字面“测试点”作为中间节点。
- 每个正式用例叶子一对一生成一条用例；不得在阶段三跨叶子合并，也不得把一个叶子拆成多条。连续检查和数据变体应在叶子 notes 内完成组织。
- 常规用例采用“进入入口、执行核心操作、检查最终结果”的三步法，使用 2～4 个主要步骤；超过 4 步原则上在阶段二拆分。不可分割的 P0/P1 长链路按 notes 中的保留原因、覆盖链路和失败定位方式作为例外，机械校验不直接判定失败。依赖配置、账号权限、初始状态和预置数据写入前置条件或测试数据；但本用例真正要验证的配置、状态变更或数据构造不得为压缩步骤而伪装成前置条件。
- 不可分割的端到端闭环、连续状态流转或跨系统链路可作为 P0/P1 核心场景化长用例例外保留；notes 的“补充说明”必须记录保留原因、覆盖链路和失败定位方式。
- 场景、路径、预期或用例边界条件不明确时，标题以 `【待确认】` 开头；notes 保留当前建议主要类型和优先级、完整步骤和预期，并补充待确认问题、现有依据和用户需给出的明确结果；确认前不生成正式 Excel/CSV 记录。
- 叶子 notes 必须包含“用例属性”“前置条件”“测试步骤”“预期结果”；“用例属性”记录一个中文主要类型和一个优先级，测试数据和补充说明按需增加。可选“测试数据”段存在时，阶段三仅统一换行和首尾空白并原样写入 Excel“测试数据”和 CSV `Data`；不存在时两处均为空，不得推测或补写。
- 每个正式用例叶子必须输出 XMind 任务优先级标记，并与 notes 中的优先级完全一致：P0→`priority-1`、P1→`priority-2`、P2→`priority-3`、P3→`priority-4`。
- notes 各段内容结尾必须保留换行；不在中文行为描述中添加无意义空格，英文短语、命令、路径、协议字段、JSON 及其他技术内容保留必要空格；同一段存在多个条件或检查项时，使用连续数字序号罗列，一个序号一行。
- 用例设计必须围绕需求明确新增、修改和受影响的业务行为，不扩展大量与需求无直接关系的通用检查。
- 同一叶子内可连续完成的功能/UI 检查通过多个编号步骤和预期结果分别验证；不得在阶段三重新改变人工审核后的用例边界。
- 用例编号使用 `<完整Jira需求Key>-TC<三位序号>`，必须完整包含输入的真实需求编号；例如输入 `ZY20260061-30` 时从 `ZY20260061-30-TC001`、`ZY20260061-30-TC002` 连续递增，禁止截断、猜测或沿用其他需求编号。
- 模块/分类直接作为 Xray `Test Repository Path`，按 `需求名称 / XMind业务层级 / 测试分类` 生成可变层级路径。第一级固定为需求名称，中间层继承人工审核后 XMind 的业务语义 topic，末级使用主要验证目标对应的测试分类；过滤 `业务管理`、`业务配置`、`业务管理 > 业务配置` 等通用菜单包装层级，统一使用 `/` 分隔且不保留 `>`。例如：`外呼预警配置 / 对话设计 / 场景类型与通知类场景 / 功能验证`。
- 用例标题直接使用正式用例叶子标题，并保持 `【模块名称】具体测试场景` 格式及业务模块前缀。
- 前置条件全部使用 `1. 2. 3.` 从 1 开始连续编号并分行填写，即使只有一条也必须编号；不允许无序项目符号、跳号或将多个独立条件合并为一条。
- 测试步骤与预期结果必须分别从 `1.` 开始连续编号，编号集合和数量完全一致，并按相同编号逐项对应。允许一个步骤参数化执行同一规则的等价数据，对应预期说明各数据结果差异；禁止“结果正常”“处理正确”“符合预期”等不可判定表达。
- 页面业务用例统一以会话已登录为前提，步骤 `1` 使用：`1. 进入【完整路径】页面。`；完整路径包含实际存在的全部导航层级，不在每条用例中重复登录。登录、会话失效、鉴权或账号切换另行设计独立用例。经人工确认的 SSO、深链、移动端、弹窗或无菜单入口可使用等价真实入口，弹框操作不强制补充触发按钮。
- 查询、接口、日志、数据库、消息和后台任务等非页面用例必须写明真实接口名或 URL、日志入口、表名、消息、任务名或后台作业入口，不虚构菜单路径或套用页面登录步骤。
- 普通 UI 和正向功能用例默认只验证页面操作、直接业务结果和明确不变量，不机械附加接口、数据库、日志、缓存、traceId 或运行时检查；数据库检查仅用于必要的数据校验或真实跨系统全链路场景。重要写操作至少说明一个目标对象变化和必要的关联数据不变量。
- 操作路径优先从需求、原型、截图、环境实测或人工审核后的 XMind 获取；无法获取、层级不完整或材料冲突时停止对应正式页面用例。
- 用户确认后的路径必须在 XMind notes、Excel 测试步骤和 CSV `Test Steps` 中保持一致。
- 优先级使用 P0/P1/P2/P3，分别映射 Jira Highest/High/Medium/Low。等级定义：P0 覆盖系统基本功能和基础核心用例，失败会导致多处重要功能不可用，或属于高概率、经常使用的核心功能，每个功能 1～2 条，新功能和后续每个迭代版本回归均需执行，自动化优先覆盖；P1 覆盖使用频率较高的正常功能、重要应用场景、功能交互和规则校验，新功能和后续每个迭代版本回归均需执行；P2 覆盖应用场景较少、使用频率较低的边界值、特殊符号、一般异常和兼容性等场景，新功能测试时执行，后续仅在全量回归时执行验证；P3 覆盖前置条件或数据设置生僻、使用频率非常低且不影响主要功能使用的场景，没有适用场景时允许为 0，新功能测试后仅在全量回归时评估是否验证。分布参考值（P1 约 60%、P2 约 20%、P3 不超过 10%）仅用于交付后的分布复核，不作事前分配；定级一律按上述等级定义逐条判断。每条主要业务操作路径默认仅选择一个代表性核心用例作为 P0/P1 候选；独立致命风险可例外增加并说明理由。P0 建议不超过正式用例总数的 10%，超过时逐条说明独立致命风险并人工复核，但不作为机械交付阻断条件。异常测试在没有更高风险证据时默认作为 P2 候选，但应根据业务/数据影响、可恢复性和补偿能力逐条上调或下调，不按类型批量定级。
- 用例类型从以下标准枚举中选择一个主要类型：功能测试、接口测试、UI测试、数据校验、权限/安全测试、异常测试、边界值测试、兼容性测试、性能测试、回归测试。
- 一个业务场景只保留一个主要类型，以主要验证目标而不是执行入口定型：越权拦截优先为权限/安全测试，第三方协议字段映射优先为接口测试，历史能力不回退优先为回归测试。功能流程已覆盖的普通 UI、内部接口和数据结果不再按其他类型重复输出。
- 接口测试默认面向需求明确的外部、第三方、开放、回调或集成接口；内部接口通常由功能流程覆盖。
- 同一操作、字段或规则下的空值、负数、特殊字符等边界组合尽量合并；检查项过多或风险独立时再拆分。
- 同一页面操作路径下的入口、展示、字段回显、布局、文案和控件状态尽量合并，不按字段机械拆分。
- 报表指标可按独立指标成例；不同页面中公式、口径和来源相同的指标合并对账，存在差异时再拆分。
- 权限/安全用例必须具备授权、账号、入口和可验证证据；兼容性仅基于私有化 B 端支持或部署矩阵；回归用例必须有历史缺陷、现有用例、需求准入门禁清单或明确影响清单依据。
- 类型不确定时在阶段二标记 `【待确认】`，阶段三不得猜测或重新分类；不适用类型允许为 0 条，XMind 不创建空类型分组。

## 覆盖要求
测试用例应尽量覆盖：
- 正常流程
- 异常流程
- 边界值
- 权限控制
- 状态流转
- 数据校验
- 并发/重复提交
- 回归影响点

## 质量要求
- 用例步骤可执行
- 预期结果明确可验证
- 避免过于笼统
- 优先补齐容易遗漏的场景
- 标记适合自动化的用例

## Xray CSV 导出要求
- 本 Prompt 只在测试方案和测试点 XMind 均已完成人工复核后执行；输入必须包含两个审核后文件，并能确认唯一真实 Jira Key。
- Excel 格式以 `templates/test-cases/test-case-template.xlsx` 为基准，Xray CSV 以 `templates/test-cases/xray-test-case-import-template.csv` 为基准。
- CSV 使用 UTF-8 BOM、英文逗号分隔；List Delimiter 使用 `/`。
- CSV 采用 Xray 导入标准版本 3，固定字段为：Summary、Description、Test Repository Path、Priority、Labels、Test Steps、Data、Expected Result、External ID、Requirements。版本 3 同时要求独立 `Data` 映射和以需求名称为根、继承 XMind 业务层级的 Repository Path。
- 当前 Xray 没有独立的前置条件文本映射字段，前置条件写入 `Description`，不要输出独立 `Precondition` 列；Excel“测试数据”对应 CSV `Data`，CSV `Data` 映射 Xray `Data`，不在 `Description` 中重复测试数据。
- `Test Repository Path` 与 Excel 中该用例的“模块/分类”完全一致。
- `Labels` 只输出一列，多个标签以 `/` 分隔。
- `Test Steps` 映射到 Xray `Action`，`Data` 映射到 Xray `Data`，`Expected Result` 映射到同名字段；测试步骤与预期结果的编号数量必须一致。
- `Priority` 在 Excel 中使用 P0/P1/P2/P3，在 Xray CSV 中固定映射为 Highest/High/Medium/Low。
- `External ID` 映射到 Xray“测试用例标识符”，格式必须为 `<完整Jira需求Key>-TC<三位序号>`，必须唯一且稳定，不能替代需求关联字段。
- 文件名前缀、Excel 用例编号、CSV `External ID` 和 `Requirements` 必须使用同一个完整、真实的 Jira 需求 Issue Key。
- 无法确认真实 Jira 需求 Issue Key 时必须要求用户提供并停止正式交付，禁止猜测、截断或沿用其他需求编号。
- `Requirements` 每行填写目标 Jira 需求 Issue Key，导入时映射为 `Link "Tests"`。
- 导入后 Test 侧应显示 `tests` 需求，需求侧应显示 `tested by` Test；不得使用 `relates to`。
- 缺少真实 Jira 需求 Issue Key 时停止正式交付，先列出阻塞项，不猜测、不留空。
- 阶段三不得静默修改业务语义、页面路径、用例边界、步骤与预期关系、风险定级或主要类型；仅允许去除首尾空白、统一换行、CSV 转义、固定优先级映射、连续编号、安全路径拼接，以及明确不改变业务含义的错别字、空格和标点修正。可能改变业务含义的文字问题、标题重复、不可执行、类型冲突或覆盖问题必须退回阶段二人工审核。
- Xray CSV 不承载中文主要类型，不得向 `Labels` 或其他字段新增 `type-*` 或未经确认的类型映射。
- Excel “用例类型”只能填写一个标准中文枚举；用例统计必须保留十种类型的数量和占比，未使用类型显示 0。
- 文件结构、数量、编号、External ID、Requirements、步骤/预期编号和格式可读性等机械一致性及导入完整性校验必须 100% 通过；业务覆盖和内容合理性以人工审核结论为准。
- 交付前回读 XMind、Excel 和 CSV，校验 XMind ZIP、`content.xml`、sheet/root topic 可解析，XMind 2.0 核心元素使用默认命名空间 `urn:xmind:xmap:xmlns:content:2.0`，不得被全量重写为 `ns0:` 等前缀形式；附件文件名前缀、全部用例编号/External ID 前缀和全部 Requirements 均为目标 Key，编号/External ID 非空、从 TC001 连续递增且唯一；正式用例叶子数、Excel 数据行数和 CSV 数据行数一致，Excel 与 CSV 的 ID 集合和顺序一致；XMind notes、Excel“测试数据”和 CSV `Data` 的可选测试数据内容及空值状态一致；XMind 与 Excel 的主要类型一致，Excel 类型统计合计等于用例总数。

## cases.json 与阶段三脚本

`extract-cases.mjs` 从最终 XMind 生成 cases.json（正式叶子，`【待确认】` 排除）：

```json
{
  "jiraKey": "KEY-123",
  "requirementName": "需求名称",
  "scope": "项目/模块",
  "cases": [
    {
      "id": "KEY-123-TC001",
      "module": "需求名称 / 模块 / 分类",
      "title": "【模块】场景",
      "precondition": "1. ...",
      "testData": "...",
      "steps": "1. ...",
      "expected": "1. ...",
      "priority": "P1",
      "type": "功能测试",
      "automation": "是",
      "requirements": "KEY-123"
    }
  ]
}
```

- `build-cases.mjs` 生成 10 列 Xray CSV 与 Excel；CSV `Data` 只来自 XMind notes 的「测试数据」段。
- `validate-cases.mjs` 校验 XMind 正式叶子数 = Excel 行数 = CSV 行数、ID 顺序、Requirements、Data。
- Excel/CSV 不上传 Jira。
