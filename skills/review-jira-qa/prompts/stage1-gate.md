# 需求准入门禁 Prompt（生成需求准入门禁清单）

本 Prompt 用于需求评审前的需求准入门禁判定：按 B1–B7 / C1–C6 判定需求材料是否完整、明确、可验证，输出「需求准入门禁清单」，用于判断需求材料能否进入下游开发设计。本 Prompt 不承担测试方案、测试点或测试用例设计。

- **定位**：输入是 Jira 最新需求附件（PRD、Overview、原型等）；输出是「能否进入下游开发设计」的判定。
- **边界**：QA 只列事实、冲突和关闭条件，不替产品决定具体改法；产品自行选择表述，满足条件并复跑通过即可放行。本清单只用于需求材料准入，不评价开发设计、方案设计与测试方案设计。
- **方法依据**：本文件（需求准入门禁判据）。
- **材料依据**：同单全部需求侧 Jira 附件，完整清单见「读取材料清单」。
- **证据规则**：每条不通过项均引用上述材料的原文；无原文依据的推测不作为阻塞项，不计入不通过项数量。
- **口径说明**：凡阻断下游设计的问题，都计为不通过；全部不通过项关闭并复跑结论为「通过」才放行；「有条件通过」或仍有未关闭项时，材料不予放行。

冲突裁决：**契约**（交付物字段、命名、目录、阶段门禁）以 `prompts/contract.md` 为准；**方法**（分析规则、设计细则、合并与判断策略）以本文件为准。

## 输入

- Jira Issue Key 或可严格解析 `/browse/<IssueKey>` 的完整 URL（必需）。
- 主需求材料：Jira 单当前最新需求附件，执行时自动读取/下载，不单独传入材料路径；单内无需求附件或主需求材料无法唯一确定时，记录 `failedStep=materials` 与缺失项，输出 `ok=false` 结果后返回调用方，不阻塞父流程。
- 配套材料：同单其他需求侧附件（Overview、原型、接口、流程、字段、权限、依赖和验收说明）。

**需求侧材料须整套核读（强制）**：

- 同一需求的全部需求侧材料逐份核读：主需求材料 `.md` 正文 + 配套 `.html`（Overview、评审概览、原型、页面示意）。只读主需求材料即视为分析未完成。
- 正文藏在脚本里的 `.html`（JS 驱动原型）需从其字符串或渲染结果中提取正文后再核读，不得因“剥标签后为空”而略过。
- 核读后交叉核对功能范围、页面控件、用户可见文案、字段与枚举、状态与口径；差异按 B7 判定。

## 判定依据

只分析需求本身的完整性、明确性和可验证性，以及业务规则与用户可见结果；不分析技术架构、模块拆分、接口实现、缓存/消息/事务/部署方案。技术内容若影响用户可见行为或验收口径，只记录由此暴露的需求缺口，不提出技术方案。

**分析覆盖**：需求测材料冲突、描述歧义或不完整、业务规则遗漏、异常流程缺失、边界条件不清、权限控制问题、状态流转不清晰、数据一致性问题、并发/重复操作、外部依赖、可测试性不足。

### 必答项（B1–B7）

| 编号 | 判据 | 合格标准 |
|---|---|---|
| B1 | 验收标准 | 验收口径可量化、可验证，能据此直接写出通过/不通过；增删改类操作的日志留痕范围、记录字段与查看入口明确 |
| B2 | 主流程闭环 | 入口、操作、输出结果完整，无断点、无未定义的结果 |
| B3 | 角色与权限边界 | 角色、可做与不可做、未登录与越权的期望业务结果明确 |
| B4 | 核心业务规则 | 触发条件、限制条件、状态流转规则明确且互不冲突 |
| B5 | 异常流程的业务结果 | 异常发生时用户可见结果、业务与数据所处状态明确 |
| B6 | 本期范围边界 | 本期包含项明确；需求触及或暗示的边界项均有归属。未触及边界项判「已明确」 |
| B7 | 需求侧材料冲突 | 多份需求材料在功能范围、页面控件、用户可见文案、字段与口径上无冲突；存在差异时已裁决 |

### 应明确项（C1–C6）

| 编号 | 判据 |
|---|---|
| C1 | 边界与取值：空值、长度、数量、时间、精度 |
| C2 | 并发与重复操作下的业务结果 |
| C3 | 历史数据处理与报表口径影响 |
| C4 | 外部依赖异常时的用户可见行为 |
| C5 | 回归影响范围：历史功能、上下游、通知、报表、权限逻辑 |
| C6 | 需求明确提出的可量化用户体验或业务约束 |

> **判定口径**：C 项未明确或未关闭同样计入不通过，不再区分「应明确项不阻断准入」。

### 判定取值

| 判定值 | 口径 |
|---|---|
| 已明确 | 材料中有明确表述，无歧义、无冲突，能直接写出通过/不通过的判定 |
| 缺失 | 材料完全没有涉及该判据 |
| 不可验证 | 有表述但无法判定，包括：① 主观描述无量化口径；② 表述自相矛盾或与其它章节冲突；③ 只给方向不给边界 |

### 判定规则

- B1–B7、C1–C6 任一项判为缺失、不可验证或未明确 → 计为不通过。
- 全部判为已明确 → 通过。
- 每条不通过项必须有材料原文依据；无原文依据的推测不作为阻塞项，不计入不通过项数量。
- 判定只依据材料事实；不能用「已关闭」等状态替代材料更新，必须更新材料后复跑。

## 输出结构（需求准入门禁清单）

本清单只呈现不通过项，不呈现完整判定明细和工作编号。

### 文档结构（固定顺序）

1. 标题与结论行：`结论：暂不通过：N 项未关闭`;
2. 不通过项总表：编号从 1 连续递增；列固定为 `编号 | 类型 | 事项 | 当前问题 | 关闭条件 | 产品需要做什么`。
3. A. 材料冲突：每项只写「事实原文 → 事实认定 → 关闭条件」；不写「如何判定」「不接受的关闭方式」。
4. B. 材料未明确：每项只写「原文 → 当前问题 → 关闭条件」。
5. 非阻断文字事实：不影响放行、不计入 N；只列术语/笔误等事实，不列历史版本记录。
6. 评审说明：定位、边界、方法依据、材料依据、证据规则、口径说明。
7. 读取材料清单：只列 Jira 附件（文件名、版本/类型、附件 ID、上传时间）；不写本地路径、sha256、旧版本说明。
8. 分析时间：全文最后一行。

### 强制规则

- **只列不通过项**：本清单不呈现完整判定明细和工作编号。
- **QA 不替产品改法**：只写事实、冲突和关闭条件；产品自行选择表述。
- **全部计入不通过**：凡阻断下游设计的问题都计为不通过；材料未明确项也计入 N，不区分「阻断准入/不阻断准入」。
- **连续编号**：1..N；不得使用 Q-xx、R-xx、B1/B2 等内部编号作为总表编号。
- **证据规则**：每条引用 Jira 附件原文；无原文依据的推测不作为阻塞项，不计入 N。
- **确定性**：同一份材料多次运行必须输出相同的清单、相同的编号与结论；禁止「窄读法/宽读法」「按字面可理解」「可以读出」等模糊表述；每项只写单一事实认定和唯一结论。
- **材料基准**：以 Jira 最新附件为准；读取材料清单只列 Jira 附件，不列本地副本。
- **HTML**：UTF-8、自包含内嵌 CSS、无外部资源。

## HTML 与版本

```text
outputs/<scope>/<JiraKey>/risk-analysis/<JiraKey>-<需求名称>-需求准入门禁清单-v<版本>.html
```

- scope 为空时从 `outputs/<JiraKey>/risk-analysis/` 开始；scope 推导与安全规则见 `prompts/contract.md`。
- 版本号为交付物自身版本（v1.0→v1.1→v1.2…），PRD/需求材料版本写入文档内；首次生成从 v1.0 开始。
- 三处名称与版本必须一致：文件名 `…-需求准入门禁清单-v<版本>.html`、HTML 标题与 `<h1>` 为 `需求准入门禁清单（v<版本>）`、Jira 评论标题为 `QA-需求准入门禁结果v<版本>`；PRD 版本只出现在评论末行 `材料版本：…`。
- HTML 的结论、不通过项编号、事实引用、关闭条件、材料清单和分析时间必须一致。
- HTML 使用 UTF-8、自包含内嵌 CSS，不引用外部 CDN、脚本、字体或第三方服务，支持浏览器打印/PDF 导出。
- 读取材料清单只列 Jira 附件；分析时间放在全文最后一行。
- 生成后先保存到上述 `outputs/...` 路径，再按 `prompts/contract.md`「Jira 附件同步」上传 HTML，删除同名旧版本，只保留最新版本；上传不替代本地保存；上传失败时记录 `failedStep=upload`，跳过评论并产出 `ok=false` 结果，随后返回调用方，不阻断父流程。

## Jira 评论

上传 HTML 后，按材料版本同步一条 Jira 评论：

- 标题：`QA-需求准入门禁结果v<交付物版本>`。
- 正文最后一行：`材料版本：PRD <版本>（Jira 附件 <ID 列表>）`。
- 结论为「通过」：只写结论，不呈现不通过项总表。
- 结论为「暂不通过」：写结论 + 不通过项总表。
- 末尾引用最新 HTML 附件。
- 同一材料版本只保留一条评论，复跑编辑该条；材料更新后复跑才新发一条；持续到复跑结论为「通过」。

## 执行边界

- 本阶段只生成需求准入门禁清单；不生成测试方案、测试用例 XMind、Excel、CSV 或测试代码。
- 阶段一完成即返回调用方，不自动进入阶段二或阶段三；结论为「通过」时只提示 `/qa-design <KEY>`，「暂不通过」或仍有未关闭项时提示产品修订后复跑阶段一。
- 全部不通过项关闭并复跑结论为「通过」才放行；「有条件通过」或仍有未关闭项时，材料不予放行。

## gate.spec.json（本技能唯一输出格式）

阶段一只写这个 JSON，**不直接写 HTML**。`render-gate.mjs` 会按固定模板生成 HTML 与 Jira 评论。

```json
{
  "schemaVersion": 1,
  "jiraKey": "KEY-123",
  "requirementName": "需求名称",
  "prdVersion": "v0.1",
  "deliverableVersion": "1.0",
  "scope": "项目/模块",
  "analysisTime": "2026-10-22 10:00 +08:00",
  "materials": [
    { "id": "1001", "filename": "xxx_PRD_DELIVERY.md", "type": "PRD v0.1", "uploadedAt": "2026-10-20 14:00" }
  ],
  "conclusion": "通过 | 暂不通过",
  "failures": [
    {
      "type": "材料冲突 | 材料未明确",
      "topic": "事项",
      "facts": [ { "source": "PRD 3.2", "quote": "材料原文" } ],
      "problem": "事实认定或当前问题",
      "closingConditions": ["关闭条件1", "关闭条件2"]
    }
  ],
  "nonBlockingFacts": ["不影响放行的文字事实"]
}
```

硬性规则：

- `conclusion=通过` 时 `failures` 必须为空；`暂不通过` 时至少 1 项。
- `failures[].type` 只能是「材料冲突」或「材料未明确」；`productAction` 由渲染器按类型自动填「修订材料 / 补充结论」。
- 每条 failure 至少 1 条 `facts[].quote`，且 quote 必须逐字来自需求材料。
- 编号由渲染器按数组顺序生成 1..N，不要手写编号。
- `materials` 必须与 `materials.json` 的 Jira 附件 ID、文件名、上传时间一致；只列需求侧材料，不列本地路径。
- `analysisTime` 可用 `--now` 固定；缺省由渲染器生成。
