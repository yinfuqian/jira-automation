# 测试产出结构模板

> 本模板只定义三个阶段的交付结构与验收基线。实际执行必须依次使用 `/review-jira-qa`、`/qa-design`、`/qa-cases`，不得跨越人工审核门禁；完整规则以 `prompts/contract.md` 为准。

## 统一交付目录

```text
outputs/<scope>/<JiraKey>/
├── risk-analysis/
├── test-plans/
└── test-cases/
```

- scope 由主需求材料在 `inputs/<输入类别>/` 下的相对父目录确定，辅助材料不参与推导。
- 主需求直接位于输入类别根目录时 scope 为空，需求根目录为 `outputs/<JiraKey>/`。
- Jira Key、需求名称、scope 或需求交付根目录冲突时停止，不跨目录递归选择同名文件。

## 阶段一：需求准入门禁

交付物：需求准入门禁清单。

标准输出：

```text
outputs/<scope>/<JiraKey>/risk-analysis/<JiraKey>-<需求名称>-需求准入门禁清单-v<版本>.html
```

自包含 HTML 必须来自同一份判定结果，固定结构：

1. 结论：`暂不通过：N 项未关闭`
2. 不通过项总表：编号 1..N；列：编号、类型、事项、当前问题、关闭条件、产品需要做什么。
3. A. 材料冲突：事实原文、事实认定、关闭条件。
4. B. 材料未明确：原文、当前问题、关闭条件。
5. 非阻断文字事实。
6. 评审说明。
7. 读取材料清单（Jira 附件）。
8. 分析时间。

> 阶段一结束即返回调用方，不自动进入阶段二；结论为「通过」时仅提示人工触发 `/qa-design`。

## 阶段二：测试方案与测试点

标准输出：

```text
outputs/<scope>/<JiraKey>/test-plans/<JiraKey>-<需求名称>-测试方案-v<版本>.md
outputs/<scope>/<JiraKey>/test-cases/<JiraKey>-<需求名称>-测试用例-v<版本>.xmind
```

### 测试方案结构

- 测试目标
- 测试范围
- 非测试范围
- 回归影响范围
- 测试策略与重点
- 测试环境要求
- 测试数据要求
- 资源与依赖
- 入口标准
- 出口标准
- 风险与应对措施

### XMind 结构

```text
需求或功能名称
└── 业务模块/流程/操作路径
    └── 【模块名称】具体测试场景
```

- 只保留具有业务语义的分组，不创建字面名称为“测试点”的中间 topic。
- 正式测试点是无业务子 topic 的叶子；一个正式叶子对应阶段三的一条用例。
- 合并与拆分必须在形成叶子前完成；阶段三不得跨叶合并或拆分叶子。
- 标题使用 `【模块名称】具体测试场景`，不得使用测试类型或抽象主题代替模块前缀。
- 类型、路径、预期或用例边界不明确时，标题使用 `【待确认】【模块名称】具体测试场景`；确认前不计入正式用例数。
- 不适用的测试类型不创建空分组或占位叶子。

### 正式叶子 notes 模板

```text
用例属性
主要用例类型：功能测试
优先级：P1

前置条件
1. 已准备具备目标功能权限且会话有效的账号。
2. 已准备满足业务规则的目标数据。

测试数据
1. 目标对象：示例对象。
2. 输入组合：有效值、空值、负数、非法特殊字符。

测试步骤
1. 进入【一级菜单 > 二级菜单 > 目标页面】页面。
2. 选择目标对象，执行核心业务操作并保存。
3. 查看目标对象和必要的关联业务结果。

预期结果
1. 页面加载和可操作区域正常展示。
2. 核心操作按业务规则执行并保存成功。
3. 目标对象更新为预期值，必要的关联数据保持不变。

补充说明
普通页面用例以会话已登录为前提；登录、会话失效和鉴权另行设计。
```

notes 规则：

- 固定包含“用例属性、前置条件、测试步骤、预期结果”；测试数据和补充说明按需增加。
- 每个正式叶子只能有一个标准中文主要类型和一个优先级。
- 所有前置条件从 `1.` 连续编号；步骤与预期从 `1.` 连续编号，数量和编号集合完全一致。
- 普通页面用例步骤 1 使用 `进入【完整路径】页面。`，路径包含实际存在的全部导航层级，不重复登录。
- 非页面场景写明真实接口名或 URL、日志入口、表名、消息、任务名或后台作业入口。
- 普通 UI 和正向功能用例不机械附加跨层检查；重要写操作说明目标变化和必要不变量。
- 常规用例使用 2～4 个主要步骤；不可分割的 P0/P1 长链路必须说明保留原因、覆盖链路和失败定位方式。

### 用例类型设计规则

标准中文枚举：功能测试、接口测试、UI测试、数据校验、权限/安全测试、异常测试、边界值测试、兼容性测试、性能测试、回归测试。

- 每条用例只选择一个主要类型，不因类型不同复制同一业务场景。
- 功能流程已覆盖的普通 UI、内部接口和数据结果不再重复成例。
- 接口测试主要面向需求明确的外部、第三方、开放、回调或集成接口。
- 边界值在同一操作、字段或规则下尽量合并；检查项过多或风险独立时再拆分。
- UI 检查按同一操作路径合并入口、展示、字段回显、布局、文案和控件状态，不按字段机械拆分。
- 报表指标可按独立指标成例；不同页面中公式、口径和来源相同的指标合并对账。
- 权限/安全用例必须具备授权、账号、入口、步骤和可验证证据。
- 兼容性仅依据私有化 B 端支持矩阵，可包含桌面浏览器、分辨率、操作系统、数据库、中间件和部署版本；不扩展 APP、手机端或小程序。
- 回归测试必须有历史缺陷、现有用例、需求准入门禁清单或明确影响清单作为依据。

### 优先级规则

- Excel 使用 P0/P1/P2/P3；Xray CSV 映射 Highest/High/Medium/Low。
- 按业务影响、发生概率、可恢复性、补偿能力和回归价值逐条定级。
- 每条主要业务路径默认只选择一个代表性 P0/P1 候选；独立致命风险可例外增加并说明理由。
- UI、异常、权限/安全、兼容和边界用例在没有更高风险证据时可作为 P2 候选，但不强制整类定级。
- P0 建议不超过正式用例总数的 10%，超过时逐条说明独立致命风险并人工复核；比例不作为机械阻断条件，不为调整分布修改优先级。

> 阶段二输出后停止，等待人工复核测试方案、正式叶子、页面路径、主要类型和优先级。

## 阶段三：最终方案与测试用例

输入必须同时包含同一需求交付根目录中的人工复核后测试方案和人工审核后 XMind。先依据最终 XMind 刷新测试方案，再生成：

```text
outputs/<scope>/<JiraKey>/test-cases/<JiraKey>-<需求名称>-测试用例.xlsx
outputs/<scope>/<JiraKey>/test-cases/<JiraKey>-<需求名称>-Jira导入.csv
```

### Excel 测试用例字段

| 用例编号 | 模块/分类 | 用例标题 | 前置条件 | 测试数据 | 测试步骤 | 预期结果 | 优先级 | 用例类型 | 是否适合自动化 | Requirements |
|---|---|---|---|---|---|---|---|---|---|---|
| DEMO-123-TC001 | 对话设计 / 配置管理 / 变量管理 | 【变量管理】修改默认值并验证引用结果 | 1. 已准备具备变量管理权限且会话有效的账号。<br>2. 已创建可编辑的目标场景。 | 目标变量默认值：示例值 | 1. 进入【对话设计 > 配置管理 > 变量管理】页面。<br>2. 选择目标场景，修改变量默认值并保存。<br>3. 查看变量及其引用结果。 | 1. 页面加载和可操作区域正常展示。<br>2. 保存成功。<br>3. 默认值更新，引用结果使用新值。 | P1 | 功能测试 | 是 | DEMO-123 |

- 一叶一用例，按人工审核后的 XMind 顺序转换，不重新排序。
- 用例编号为 `<JiraKey>-TC<三位序号>`，从 TC001 连续且唯一。
- 模块/分类直接作为 Xray `Test Repository Path`，按 `需求名称 / XMind业务层级 / 测试分类` 生成可变层级路径；过滤 `业务管理`、`业务配置`、`业务管理 > 业务配置` 等通用菜单包装层级，统一使用 `/` 分隔且不保留 `>`。
- “用例类型”只能填写一个标准中文枚举。
- Excel 用例统计保留十种类型的数量和占比，未使用类型显示 0。

### Xray CSV

固定字段：

```text
Summary,Description,Test Repository Path,Priority,Labels,Test Steps,Data,Expected Result,External ID,Requirements
```

- 使用 UTF-8 BOM、英文逗号分隔，List Delimiter 使用 `/`。
- 前置条件写入 `Description`，不新增独立 `Precondition` 列。
- XMind notes 中存在可选“测试数据”段时，原样写入 Excel“测试数据”和 CSV `Data`，并将 CSV `Data` 映射为 Xray `Data`；不存在时两处均为空，且不在 `Description` 中重复测试数据。
- `Test Repository Path` 与 Excel“模块/分类”完全一致，以需求名称作为 Jira 用例库根路径，并继承 XMind 业务层级。
- `Priority` 映射：P0→Highest、P1→High、P2→Medium、P3→Low。
- CSV 不承载主要用例类型，不新增 `type-*` 或其他未经确认的类型映射。
- `External ID` 使用 `<JiraKey>-TC<三位序号>`，不能替代 `Requirements`。
- `Requirements` 每行填写目标 Jira Key，导入时映射为 `Link "Tests"`；不得使用 `relates to`。

### 阶段三禁止静默修改

不得静默改变业务语义、页面或技术入口、一叶一用例边界、步骤与预期关系、优先级和主要类型。只允许去除首尾空白、统一换行、CSV 转义、固定优先级映射、连续编号、安全路径拼接，以及明确不改变业务含义的错别字、空格和标点修正。可能改变业务含义的文字问题、标题重复或其他内容问题退回阶段二人工审核。

### 100% 强制校验

- XMind 正式叶子数 = Excel 数据行数 = CSV 数据行数。
- 标题一对一映射且唯一。
- 文件名前缀、Excel 用例编号、CSV External ID 和 Requirements 使用同一 Jira Key。
- ID 从 TC001 连续递增、非空且唯一；Excel 与 CSV ID 集合一致。
- 所有前置条件从 1 连续编号；步骤与预期编号、数量和编号集合一致。
- 人工确认路径在 XMind notes、Excel 和 CSV 中一致。
- XMind 和 Excel 的主要类型一致；CSV 不参与类型一致性校验。
- Excel 类型统计合计等于用例总数，未使用类型显示 0。
- XMind notes、Excel“测试数据”和 CSV `Data` 的内容及空值状态一致。
- CSV 使用 Xray 导入标准版本 3 的固定 10 列表头，Requirements 全部非空且等于目标 Jira Key；Repository Path 以需求名称为根并继承 XMind 业务层级。
- XMind ZIP、`content.xml` 和 sheet/root topic 可解析；XMind 2.0 核心元素使用默认命名空间，不存在 `ns0:` 等重写前缀。

任何机械一致性或导入完整性校验失败均不得正式交付；业务覆盖和合理性以人工审核结论为准。

## 自动化建议

阶段三可按以下条件标记是否适合自动化及建议优先级：

- 高频回归。
- 规则明确。
- 步骤稳定。
- 断言清晰。
- 数据可重复准备。

测试代码必须在最终测试设计完成，且环境地址、鉴权方式、账号、数据准备方式和技术栈信息充分后另行生成。
