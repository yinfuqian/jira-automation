# 一键执行口令：阶段二｜Jira 最新需求 → 测试方案与测试点

调用本模板表示需求已经通过评审。契约（交付物字段、命名、目录、阶段门禁）以 `prompts/contract.md` 为准；方法（分析规则、设计细则、合并与判断策略）以 `prompts/stage2-plan.md`、`prompts/stage2-xmind.md` 为准。

## 标准口令

```text
/qa-design <Jira需求Key或URL>
```

## 输入

- 主需求材料：从 Jira 单当前最新需求附件自动读取/下载（必需）；不使用 `inputs/` 下旧副本。
- 阶段一需求准入门禁清单：按 Jira Key 与 scope 从 `outputs/<scope>/<JiraKey>/risk-analysis/` 读取最新版本（必需）。
- Jira Key 或完整 `/browse/<IssueKey>` URL：必需。
- 接口文档、原型、环境、权限矩阵、客户支持矩阵和历史缺陷：可选。

## 阶段门禁与目录

主需求材料与需求准入门禁清单的 Jira Key、需求名称、scope 与需求交付根目录必须一致，不得跨 scope 或需求目录递归选择同名文件。

标准输出：

```text
outputs/<scope>/<JiraKey>/test-plans/<JiraKey>-<需求名称>-测试方案-v<版本>.md
outputs/<scope>/<JiraKey>/test-cases/<JiraKey>-<需求名称>-测试用例-v<版本>.xmind
```

## 执行步骤

1. 读取 Jira 最新需求附件和最新需求准入门禁清单，展示 resolved scope 与需求交付根目录，不重复生成需求准入门禁清单。
2. 明确测试范围、非测试范围、回归影响、风险响应、资源、环境和数据要求。
3. 生成测试方案。
4. 按业务模块、流程和操作路径设计测试点，不创建字面名称为“测试点”的中间 topic。
5. 正式叶子标题使用 `【模块名称】具体测试场景`，模块前缀必须是实际业务模块或操作环节，不得使用 `【条件组合】`、`【一致性】`、`【UI兼容】`、`【回归】`、`【异常】` 等测试类型或抽象主题前缀；正式叶子不得存在业务子 topic，notes 不计为子 topic。
6. 在形成叶子前完成合并与拆分：同一操作路径中可连续执行的检查尽量合并；不同目标、入口、权限、状态、数据、风险或预期时拆分。
7. 常规用例建议三步法，使用 2～4 个主要步骤；超过 4 步原则上在阶段二拆分。不可分割的 P0/P1 端到端闭环可例外保留，并在 notes 说明保留原因、覆盖链路和失败定位方式；机械校验先检查该说明，不直接判定失败。
8. 页面用例统一以会话已登录为前提，步骤 1 使用 `进入【完整路径】页面。`；完整路径包含实际存在的全部导航层级。弹框场景不强制写触发按钮；非页面场景必须写明真实接口名或 URL、日志入口、表名、消息、任务名或后台作业入口。
9. 每个叶子 notes 固定包含“用例属性、前置条件、测试步骤、预期结果”；测试数据和补充说明按需增加。可选“测试数据”段是阶段三 Excel“测试数据”和 CSV `Data` 的唯一内容来源；出现时必须可稳定解析且在 Markdown 与 XMind 中一致。前置条件、步骤和预期均使用连续数字编号；步骤与预期数量和编号集合完全一致。不在中文行为描述中添加无意义空格，英文短语、命令、路径、协议字段、JSON 等技术内容保留必要空格；各固定段内容结尾保留换行。
10. 每个叶子填写一个中文主要类型和一个优先级；按主要验证目标而非执行入口定型。类型、路径、预期或边界不明确时，标题标记 `【待确认】`，仍填写当前建议类型和优先级、完整步骤和预期，并记录问题、依据和需补充结果。
11. 普通 UI 和正向功能场景默认只验证直接业务结果，不机械附加接口、数据库、日志、缓存、trace 或运行时检查；仅当该层是结论成立的必要证据时增加。重要写操作必须说明目标对象变化及必要的关联数据不变量。
12. 每个测试点叶子必须输出 XMind 任务优先级标记，并与 notes 中的用例优先级一致：P0→`priority-1`、P1→`priority-2`、P2→`priority-3`、P3→`priority-4`。
13. 生成测试用例 XMind，回读自检；先保存到 `outputs/...` 对应目录，再将测试方案与测试用例 XMind 上传 Jira，删除同名旧版本，只保留最新版本；上传不替代本地保存；上传失败停止并报告。

## 用例设计核心规则

1. **目标明确**：一个叶子围绕一个业务目标，不按字段、按钮或测试类型机械拆分。
2. **标题清晰**：使用 `【模块名称】具体测试场景`，直接描述业务验证点，不使用疑问句或“检查/验证是否正确”等空泛表达。
3. **入口真实**：页面写完整路径，非页面使用真实技术入口；无法确认时标记 `【待确认】`。
4. **前置准确**：只写第一步前已成立的账号、权限、状态、配置和预置数据，不把核心验证操作伪装成前置条件。
5. **数据分离**：影响业务分支、边界或预期的数据写入“测试数据”；同一规则的等价数据尽量参数化合并。
6. **步骤可执行**：常规用例 2～4 个主要步骤，每个编号只写一个主要动作，一个序号一行；最后一步仍是操作或观察动作。
7. **逐项对应**：步骤与预期均从 `1.` 连续编号，数量和编号集合完全一致并逐项对应。
8. **结果可判定**：预期必须可观察、查询、测量或比较，禁止“结果正常”“处理正确”“符合预期”等空泛表达；异常写明错误反馈和数据最终状态，写操作写明目标变化及关联数据不变量。
9. **必要且充分**：覆盖需求变更和关键正常、异常、边界、权限、状态、数据及回归风险；同一路径可连续完成的检查合并。
10. **可重复可追踪**：相同条件下结果一致，每个正式叶子可追踪到 Jira 需求、业务模块和主要风险。

## 专项收敛规则

- 一个正式叶子对应阶段三的一条用例；功能流程已覆盖的普通 UI、内部接口和数据结果不重复输出。
- 边界值：同一规则下的负数、空值、特殊字符等尽量合并；风险或处理逻辑独立时拆分。
- UI：同一路径的入口、展示、字段回显、布局、文案和控件状态尽量合并。
- 数据校验：相同公式、口径和来源的指标合并对账，存在差异时拆分。
- 接口测试：默认只面向明确的外部、第三方、开放、回调或集成接口。
- 兼容性：仅基于私有化 B 端支持或部署矩阵，不扩展无关客户端。
- 权限/安全：必须有授权、账号、入口和可验证证据；推测性风险标记待确认。
- 回归：必须有历史缺陷、现有用例、需求准入门禁清单或明确影响清单依据。
- 不适用类型允许为 0 条，XMind 不创建空类型分组。

## 优先级规则

以下各级占比均为**分布复核参考值**，仅用于交付后的分布复核，不作事前分配；定级一律按 P0–P3 等级定义逐条判断。

### P0

- 优先级最高，覆盖系统基本功能和基础核心用例；每个功能建议 1～2 条，建议总占比不超过 10%。超过时必须逐条说明独立致命风险并人工复核，但不作为机械交付阻断条件。
- 划分依据：用例执行失败会导致多处重要功能不可用，或属于发生概率较高、经常使用的核心功能。
- 执行要求：新功能测试必须执行；后续每个迭代版本回归均需执行；自动化优先覆盖。

### P1

- 覆盖系统重要功能，数量建议占比约 60%。
- 划分依据：使用频率较高的正常功能、重要应用场景、功能交互和规则校验。
- 执行要求：新功能测试必须执行；后续每个迭代版本回归均需执行；系统重要功能必须实现并验证。

### P2

- 覆盖系统一般性功能，数量建议占比约 20%。
- 划分依据：应用场景较少、使用频率较低，包括边界值、特殊符号、一般异常和兼容性等场景。
- 执行要求：新功能测试时执行；后续迭代不要求每次回归执行；全量回归时执行验证。

### P3

- 覆盖系统较生僻、低价值或可选功能，建议占比不超过 10%；没有适用场景时允许为 0。
- 划分依据：前置条件或数据设置生僻、使用频率非常低，不验证也不影响主要功能使用，例如低价值新增 UI 菜单等。
- 执行要求：新功能测试后仅在全量回归时评估是否验证。

### 定级原则

- 按业务影响、发生概率、可恢复性、补偿能力、使用频率和回归价值逐条定级。
- 每条主要业务路径默认只选择一个代表性 P0/P1 候选；独立致命风险可例外增加并说明理由。
- 建议占比用于分布复核，不得为了满足比例机械调整不符合等级定义的用例。

## 团队验收清单

- [ ] 需求、需求准入门禁清单、Jira Key、需求名称和 scope 是否一致？
- [ ] XMind 是否无字面“测试点”中间节点和无业务意义占位分组？
- [ ] 正式叶子标题是否使用真实业务模块或操作环节前缀、保持唯一，且无业务子 topic、notes 完整？
- [ ] 是否一叶一用例，且没有按类型复制场景？
- [ ] 常规用例是否使用 2～4 个主要步骤，超过 4 步的 P0/P1 例外是否具备完整说明？
- [ ] 页面路径是否包含实际存在的全部导航层级，步骤 1 是否统一为进入页面？
- [ ] 所有前置条件、步骤和预期是否连续编号，步骤与预期是否逐项对应且无不可判定表达？
- [ ] notes 中各固定段结尾是否保留换行，中文行为描述是否无无意义空格，技术内容是否保留必要空格？
- [ ] 每个测试点叶子的 XMind 任务优先级是否与 notes 中 P0/P1/P2/P3 一致？
- [ ] 每个正式叶子是否有且仅有一个中文主要类型？
- [ ] 不适用类型是否未在 XMind 中创建空分组？
- [ ] 待确认叶子是否保留建议类型、优先级和完整步骤/预期，且未计入正式用例数量？
- [ ] 普通 UI/正向功能是否未机械附加跨层检查，重要写操作是否说明目标变化和必要不变量？
- [ ] 优先级是否符合 P0/P1/P2/P3 等级定义，建议分布是否仅用于复核且未机械调级？

## 强制门禁

- 不重新生成需求准入门禁清单。
- 测试方案、测试点和路径未人工复核前，不生成 Excel 或 Xray CSV。
