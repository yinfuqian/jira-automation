# 缺陷单完整性检查清单

本清单是「缺陷单提交后门禁」的默认判定依据：缺陷单进入研发处理前，先确认提单信息是否足够定位问题。

- **检查入口**：缺陷单提交后（状态通常是「待处理 / 新建」）。
- **检查范围**：现象、复现、环境、时间、证据、影响面；不检查实现细节，也不评价修复方案。
- **判定结果**：`不通过`（打回补充） / `通过`（可流转，或继续走自查与自动分析）。

## 检查项等级

| 等级 | 含义 | 影响 |
|---|---|---|
| `MUST` | 缺任一项即打回 | 打回补充 |
| `SHOULD` | 建议补充，记录但不打回 | 评论区提示 |
| `REDLINE` | 一票打回红线 | 直接打回 |

判定必须能指向具体证据：字段值、描述段落、评论内容、附件文件名或可辨认的图片内容。找不到证据记为「证据不足」，不允许凭印象写“已满足”。

## 0. 效果类缺陷日志/复现豁免

只有同时满足下面两个条件，才允许豁免复现步骤和日志要求：

1. 缺陷性质明确判定为**效果类缺陷**，例如页面展示、交互效果、样式呈现、文案效果等，不属于报错、异常、接口失败、性能、数据或资源故障。
2. 评论区存在一条明确声明，原文包含固定语句：`明确缺陷不需要额外提供日志信息`。

命中后：

- 1.3「复现步骤」按不适用处理，不因缺失打回。
- 1.7 中的**日志**要求按不适用处理；截图、录屏或页面效果对比等效果证据仍按常规要求检查。
- 评论检查项应写 `(/)` 并注明“效果类缺陷，已按固定评论声明豁免日志/复现”，不能写成缺少日志或复现步骤。
- 本条只豁免日志与复现要求，不豁免概要、现象与期望、环境、版本、时间、影响范围等其它 `MUST`，也不豁免任何 `REDLINE`。

无论是否命中，评论都必须把豁免判定说清楚：

- 固定声明原文：`明确缺陷不需要额外提供日志信息`。
- 判定条件：必须同时满足“本单是效果类缺陷”和“评论区存在固定声明”，缺一不可。
- 未命中时：说明具体缺少哪一项，并明确日志与复现步骤仍按普通缺陷检查；若确属效果类，提示补充固定声明原文。
- 命中时：说明已豁免日志与复现步骤，但截图、录屏等效果证据仍要检查，其它 `MUST` 和全部 `REDLINE` 均不豁免。

未同时满足两个条件时不适用本条，仍按普通缺陷检查。

## 0.1 持续存在问题的时间豁免

只有缺陷单明确属于**持续存在、无单次发生时间**的问题时，才允许豁免 1.6 的具体故障时间：

- 描述、评论或可辨认附件文字明确写明“一直存在”“长期存在”“持续存在”“始终存在”“每次必现”“配置后一直如此”等，说明问题是稳定状态而不是一次事件。
- 不能只因为工单没有写时间就推定“持续存在”；必须存在上述明确表述或等价证据。
- 偶现问题不适用；偶现问题仍需提供发生频率和最近一次发生时间。

命中后，1.6 按不适用处理，不因缺少单次故障时间打回。评论检查项写 `(/)` 并注明“问题持续存在，无单次发生时间，按持续存在豁免”，同时引用描述、评论或附件中的原文。该豁免只影响时间信息，不免除日志、复现步骤、环境、版本、影响范围等其它检查。

## 1. MUST：缺任一项即打回

| 编号 | 检查项 | 判定要点 | 证据位置 |
|---|---|---|---|
| 1.1 | 概要一句话说清现象 | 含对象/模块 + 现象，不是「报错」「有问题」「系统异常」这类无信息标题 | 概要字段 |
| 1.2 | 现象与期望结果 | 明确「期望发生什么」与「实际发生什么」，两者能直接对比 | 描述 |
| 1.3 | 复现步骤 | 可执行操作过程与必要数据；偶现问题需给出发生频率与最近一次时间；不要求环境入口或操作版本 | 描述 |
| 1.4 | 发生环境 | 客户/项目、环境（生产/测试/预发）、产品与至少一个可识别模块；Jira 模块/组件字段不是必填来源；允许同时影响多个模块，不要求提单人指定责任主模块；模块名可从描述、评论或可辨认图片识别 | 环境字段 / 描述 / 评论 / 可辨认图片中的模块或组件 |
| 1.5 | 影响的版本 | 至少提供一个可识别的「模块与版本」对应关系；可来自影响的版本字段、概要、描述、评论，或附件中的部署清单、镜像列表、`kubectl get po -o yaml` 等可辨认截图。截图中的 `仓库/模块:Tag` 整体有效，例如 `bot/bot-dialog:v0.5.0-ZYKJ20260089-rc1` 可识别为模块 `bot-dialog`、版本 `v0.5.0-ZYKJ20260089-rc1`。不要求在描述中重复填写；不要求修复版本，也不要求强制填写 Git Tag。多模块版本逐条列出；自动分析阶段仍需按规则映射并校验真实 Tag | 影响版本字段 / 概要 / 描述 / 评论 / 可辨认附件图片 |
| 1.6 | 时间信息 | 故障发生时间或时间段；不要求填写时区，也不要求与日志采集时间严格对齐；符合第 0.1 节的持续存在问题可豁免具体时间 | 描述 / 评论 / 可辨认附件文字 |
| 1.7 | 证据附件 | 至少一份与该现象对应的日志、截图或接口返回；日志只需非空、可打开且内容与故障现象相关，不要求覆盖故障时间点 | 附件 |
| 1.8 | 影响范围 | 至少说明受影响用户/业务范围，或明确的发布/验收阻断结果；写明“不允许上线”“阻断上线”“阻断发布”“阻断验收”“阻塞主流程”等具体后果即可，不强制同时提供用户数量和主流程细节，但不能只写“有影响” | 描述 / 评论 |

## 2. REDLINE：一票打回

- 只有标题、正文为空或只有一句「系统报错」。
- 描述与附件互相矛盾（例如描述的是 A 接口，日志里全是 B 接口）。
- 日志附件为空文件、损坏、加密或明显属于无关系统；日志时间与故障时间不完全重合本身不是红线。
- 截图无法辨认（全黑、模糊、只有无关页面），且没有其它证据。
- 附件损坏、加密、需要密码才能打开。
- 复现步骤缺失且日志无法定位问题（偶现问题除外，但必须提供时间点与频率；效果类缺陷按第 0 节豁免除外）。

## 3. SHOULD：记录但不打回

- 客户名称、提单人、所属项目阶段。
- 关联需求单、发布单、变更单链接。
- 附件命名是否体现环境与时间。
- 期望修复时间、优先级说明。
- 是否已自查（自查结果由 [self-check.md](self-check.md) 单独判定）。

## 4. 与自动分析的联动

第 4 步「自动故障分析」还需要产品、模块、仓库地址与 Git Tag：

- 产品优先取调用方输入或 Jira「问题发现产品」；模块优先取调用方输入、评论固定块，其次取描述、环境、概要里显式写出的全部 `模块:Tag`，最后取唯一的 Jira 组件（与产品同名时只是产品回声，不算模块）；版本优先取调用方输入、评论固定块、该模块自己的 `模块:Tag`、唯一的影响版本字段，或概要、描述、评论中的明确模块版本号。可辨认图片中的模块/组件及模块版本经 Agent 识别后可作为调用方输入；图片同时出现多个模块时，列出全部候选。第一条仅作为兼容分析接口的技术入口（analysis entry），其余作为关联模块；它不代表责任主模块，不能因无法判断责任模块而打回。修复版本不作为分析版本来源。
- 仓库地址由 `config/scope-mapping.json` 根据产品与模块解析，分析入口模块和非公共关联模块的版本由 `versionMap` / `versionRules` 解析成实际 Git Tag，并调用分析服务确认 Tag 真实存在；这些内容均不需要写进评论。Jira「产品归属」只约束分析入口模块，关联模块按模块名反查自己的产品（例如 Aiforce 单里的 bot-portal 归 bot），不继承主产品。公共组件不单独出现在评论固定块里，只由代码分析按需做联动引用记录，也不要求精准 Tag。
- 完整性检查通过后，若多个模块无法形成各自的 `模块:精准Tag`，或指定 Tag 在远端不存在，**不允许猜测**：按 SKILL.md「自动分析条件不足」模板只列实际缺少项、给出可直接修改的固定评论块，门禁字段写 `未检查`。这属于信息完整但无法自动分析，不执行打回流转、不改变工作流状态、不修改经办人。多个受影响模块本身不是缺参。
- 工单已有产品、模块和版本，但 `scope-mapping.json` 缺少产品、模块、仓库地址或版本规则时，**不要求提单人重补模块**：使用分析命令返回的固定评论通知 `mappingOwner` 补齐映射，门禁字段写 `未检查`。该分支只写评论，不执行打回流转、不调用故障分析、不改变工作流状态，也不修改经办人。**同一轮已经写过预检评论时，映射段落必须用 `comment-append` 追加到原评论，禁止新增第二条评论。**
- 分析入口模块或非公共关联模块的精确 Tag 在远端不存在时，只说明“自动分析条件不足”，门禁结果写 `未检查`，不打回、不改变工作流状态、不修改经办人。公共组件没有精准 Tag 同样不打回；代码确实引用公共组件时，在分析结论中说明引用的公共组件功能和关键代码位置。
- 补齐后再次触发本技能即可直接进入分析，不需要人工确认分析参数。

## 5. 项目自定义

若缺陷单所属项目另有成文的《缺陷单规范》或提单模板，以项目规范为准：

- 在评论里注明依据来源（项目规范名称 / 链接）。
- 项目规范与本文冲突时，采用更严格的一方。
