# Jira 缺陷单门禁 + 自动故障分析

用户给一张 Jira 缺陷单，你自己打开它，按下面的固定顺序处理：

1. **完整性检查**：读描述、字段、附件、评论，按 [references/checklist.md](references/checklist.md) 逐项判定缺陷单信息是否完整。
   - 不完整 → **打回**：写评论列出缺什么、要补什么，停止后续步骤。
   - 完整 → 进入下一步。
2. **自查结果检查**：按 [references/self-check.md](references/self-check.md) 判断评论区是否已经有**有效的自查结果**。
   - 有 → **正常流转**：写一条简短评论说明已找到自查结果并放行，停止后续步骤。
   - 没有 → 进入下一步。
3. **自动故障分析**：调用本工具的故障分析接口分析这张缺陷单的问题，把分析结果渲染成 HTML 报告，上传为缺陷单附件，并在评论区用 Jira wiki 标记格式化说明结论。

只有走完第 3 步才算“已分析”。**不能跳过第 3 步只留下“建议去分析”的评论，也不能自己编造分析结论。**

## 交付物

1. **Jira 评论**（唯一对外留痕，必须真实写入）：一行结论 + 逐项打标记的检查项清单（`(/)` 通过、`(x)` 不通过），模板见本文档「输出模板」节。
2. **HTML 分析报告附件**（仅第 3 步产生）：由 `scripts/analysis-cli.mjs analyze` 生成并上传，文件名形如 `故障分析报告-<单号>.html`。
3. **门禁字段**（可选，字段不存在时自动跳过）：`缺陷单预检结论` = `通过` / `不通过`，以及自查与报告字段，供 Jira 工作流条件/校验器读取。
4. **对话里的摘要**：结论（打回 / 放行 / 已自动分析）+ 关键依据 + 写入的评论与附件，供用户即时看到结果。

不要在本地生成 Markdown/Word 报告作为交付物；本地临时目录只允许存放附件与解析中间文件（例如 `<工作目录>/work/defect-gate/<KEY>/`）。

## 判定依据

- 缺陷单完整性检查项、一票打回红线：以 [references/checklist.md](references/checklist.md) 为准。
- 自查结果的判定关键词与边界：以 [references/self-check.md](references/self-check.md) 为准。
- Jira 取数、写评论、传附件、门禁字段与流转细节：见 [references/jira-api.md](references/jira-api.md)。

**先读这三份参考资料再动手**，不要凭印象发明标准。若缺陷单所属项目另有成文的《缺陷单规范》，以项目规范为准，并在评论里注明依据来源。

## 执行步骤

### 0. 运行环境适配（先读这一节）

本技能可能在两种环境运行，**取数通道不同，判定标准完全相同**：

- **服务器容器 / `codex exec`（默认）**：没有 `node_repl`，用 shell 直接执行技能自带命令行入口：

  ```bash
  node <技能目录>/scripts/jira-cli.mjs selftest
  node <技能目录>/scripts/jira-cli.mjs get <KEY|URL>
  node <技能目录>/scripts/analysis-cli.mjs selftest
  ```

- **桌面 Codex（有 `node_repl`）**：在 `node_repl` 里 `await import("file:///<技能目录>/scripts/jira.mjs")`，能力与命令行入口一致；`node_repl` 没有 `process`，令牌只能用 `--token` 传入或放在令牌文件里。

技能脚本全部用 Node 编写，容器内已随镜像安装 Node。**不要用 curl / Invoke-WebRequest 直接访问 Jira 或故障分析服务**，统一走技能脚本，保证认证头、错误提示与超时处理一致。

### 1. 取数

```bash
node <技能目录>/scripts/jira-cli.mjs get <KEY|URL>    # 描述、字段、附件列表、最近评论
node <技能目录>/scripts/jira-cli.mjs json <KEY|URL>   # 需要精确字段时用 JSON
```

必须读完：类型、概要、描述、状态、经办人、模块/组件、影响版本、环境字段、附件列表、问题链接、子任务、**全部评论**。

### 2. 完整性检查 → 不完整就打回

按 `references/checklist.md` 逐项判定，每条判定都要指向具体证据（字段名、描述段落、附件文件名、评论时间点）。找不到证据一律记为“证据不足”，不允许无证据的“已满足”。

完整性检查必须同时检查可辨认图片，不能把看图推迟到自动分析阶段。先下载附件并逐张识别图片中的客户/环境、模块/组件、版本和时间等文字；图片中能明确识别的模块/组件同样属于 1.4 发生环境证据，模块版本同样属于 1.5 影响版本证据。

```bash
node <技能目录>/scripts/jira-cli.mjs attachments <KEY|URL> <工作目录>/<KEY>/attachments
```

效果类缺陷先执行日志/复现豁免检查：

```bash
node <技能目录>/scripts/jira-cli.mjs log-exemption <KEY|URL>
```

`found=true` 表示评论区命中固定语句 `明确缺陷不需要额外提供日志信息`。只有同时确认本单属于效果类缺陷时，才可按 `references/checklist.md` 第 0 节豁免复现步骤和日志要求；普通故障、报错、接口异常、性能、数据或资源问题不适用。豁免不改变其它完整性检查和红线。

- 存在任一 `MUST` 缺失或命中一票打回红线 → **打回**：
  1. 按「输出模板 · 打回」写评论（列出 `(x)` 项与要补的内容）。
  2. `node <技能目录>/scripts/jira-cli.mjs gate-set <KEY> --file gate.json`，`gate.json` 内容 `{"result":"不通过","selfCheck":"无"}`（字段不存在时会返回 `skipped`，不影响评论，继续即可）。
  3. 如果 `jira-config.json` 配置了 `rejectTransitionName`，再执行 `jira-cli.mjs transition <KEY> --name <名称>`；脚本会保留并恢复流转前的原经办人（处理人），不能让门禁账号留在经办人字段。**未配置时不要自行流转状态**，打回结论以评论与门禁字段为准。
  4. 结束本次任务，不做故障分析。

### 3. 自查结果检查

```bash
node <技能目录>/scripts/jira-cli.mjs selfcheck <KEY|URL>
```

返回 `found=true`（且 `matches` 非空）表示评论区已有有效自查结果：

1. 按「输出模板 · 放行」写评论（注明自查评论的作者与时间，便于追溯）。
2. 写门禁字段 `{"result":"通过","selfCheck":"有"}`。
3. 结束本次任务；不要重复分析、不要生成报告。

`found=false` 时进入第 4 步；若自查评论存在但**明显过期**（早于缺陷单最近一次复现时间，或与最新现象矛盾），按 `references/self-check.md` 的规则视为无效，并在评论里说明理由。

### 4. 自动故障分析 + 报告回写

**4.1 复用缺陷单附件**

```bash
node <技能目录>/scripts/jira-cli.mjs attachments <KEY|URL> <工作目录>/<KEY>/attachments
```

如果第 2 步已完成下载则直接复用，不要重复下载。记录每个附件的下载结果；下载失败要如实记入报告说明，不要静默跳过。

逐张查看所有可辨认图片；识别其中的模块/组件名、模块版本号和关联模块。图片中只有一个明确模块时，可把模块名作为 `inputs.module`、版本作为 `inputs.version`；图片中同时出现多个模块时，列出全部图片识别候选并明确主模块，不能把已识别到模块的工单写成“模块/组件为空”。图片文件名本身不等于图片内容，不能仅凭文件名判断模块或版本。

**4.2 确定分析范围（产品 / 模块 / 仓库地址 / 版本）**

按下面的优先级确定，并把最终使用的范围写进评论：

1. 产品：优先取技能调用方 `inputs.product`，否则取 Jira 字段「问题发现产品」；值为空或 `无` 时按缺失处理。
2. 模块：优先取调用方 `inputs.module`（含 Agent 从可辨认图片识别的唯一模块），其次取评论固定块的第一条 `模块:Tag`，再取描述、环境、概要里显式写出的 `模块:Tag`（首条为主模块，其余作为关联模块），最后仅在 Jira 模块/组件只有一个值且与产品名不同时自动采用。自动采用时 Jira 组件与产品同名只是产品回声，不算模块（人工在评论固定块或描述里显式写出的同名模块仍按原样使用，由 `scope-mapping.json` 别名解析）。图片、Jira 或调用方给出多个候选时**不要猜**，必须列出候选并要求明确主模块和关联模块。
3. 影响版本与精准 Tag：门禁只要求工单中存在明确的模块版本号，可来自调用方 `inputs.version`、评论固定块、该模块自己的 `模块:Tag`、Jira 影响版本字段，或概要、描述、评论和可辨认图片中的模块版本号；描述/评论里写成 `模块:Tag` 时，Tag 与该模块成对使用，其它模块的版本不会互相覆盖。修复版本不作为来源。自动分析时，主模块和非公共关联模块仍须把该版本按规则解析为 GitLab 中真实存在的精准 Tag，不能只停留在业务版本号，也不能使用 `master`、`feature/*` 等分支。评论区固定块只写需要独立分析和拉取的模块，不写公共组件；公共组件由代码分析按需联动处理。
4. 仓库地址与 Git Tag：由 `config/scope-mapping.json` 根据产品、模块和版本规则确定；故障分析只关注 Tag，不使用 `master`、`feature/*` 等分支。Jira「产品归属」只约束主模块；关联模块按模块名在 `scope-mapping.json` 中反查自己的产品，不能一律套用主产品。例如产品归属为 `Aiforce` 时，`bot-portal` 仍应从 `bot` 产品解析出 `bot/bot-portal` 仓库。同一模块配置在多个产品下且主产品不持有该模块时，按映射歧义通知维护人，不猜。
5. 调用 `resolve` 后按失败类型分流：
   - 工单缺少产品、模块或版本，或指定 Tag 在远端不存在：按「输出模板 · 缺分析参数」写评论，写门禁字段 `{"result":"未检查","selfCheck":"无"}`，结束任务。
   - 工单已提供产品、模块和版本，但 `resolve` 返回 `"reason":"scope-mapping-missing"`、`"scope-mapping-invalid"` 或 `"scope-mapping-ambiguous"` 且 `"skipped":true`：这是内部映射配置缺口，不是提单人缺信息。该分支会正常退出并输出 JSON，**不能因为 `ok:false` 就停止**。直接使用返回的 `comment` 字段原样写评论（其中会 @ 映射维护人），写门禁字段 `{"result":"未检查","selfCheck":"无"}`，然后执行 `jira-cli.mjs assign <KEY> --user <mappingOwner.name>` 把经办人转派给映射维护人（默认 `yinfuqian1193`，即尹甫乾）。转派只改经办人、不改工作流状态；不要按缺参打回、不要继续分析，结束任务。

参数齐全、映射成功且远端精准 Tag 校验通过时，直接继续执行 4.3，不需要再向提单人或研发确认模块、仓库地址或 Tag。

先用 `scope` 一次性读取 Jira 产品、模块、Tag 和可选仓库来源，再决定是否需要补充固定评论块：

```bash
node <技能目录>/scripts/jira-cli.mjs scope <KEY|URL>
```

只有工单中确实找不到模块或明确模块版本，或图片及其他来源出现多个模块候选时，才要求提单人补一条固定格式评论。产品/模块已在工单或图片中明确、仅因 `scope-mapping.json` 没有该产品、模块、仓库地址或版本规则而无法解析时，必须走映射维护人通知并跳过检查，不能要求提单人重补模块。图片中已能辨认唯一模块及其版本时直接使用识别结果，不需要为重复提供模块或版本再写评论。产品不要写进固定块；仓库地址和版本到 Tag 的转换规则也不要写进评论：

```text
[FAULT_ANALYSIS]
see-task:v1.2.3
see-management:v1.2.3
```

固定块从最新评论向前匹配；第一条是主模块，后面的条目作为关联模块一起分析。需要分析或拉取的非公共模块写 `模块:精准Tag`，模块名和精准 Tag 都不能省略；找不到或无法确认远端存在的 Tag 时按缺参打回。公共组件不单独写进固定块，只由代码分析在确实引用时联动记录。不要写 `master`、`feature/*` 分支。`repo=<仓库地址>` 仅在临时覆盖仓库时使用。不要写自由格式的“模块是 xxx / 版本是 xxx”，解析器只接受上述固定块。

先用 `resolve` 验证参数能对上工具里的产品与模块，并校验主模块和关联模块的精准 Tag 是否真实存在，再提交分析。`scope` 输出里 `relatedModules` 的每一条都要转成 `--related <模块>:<Tag>` 一起传入，不能只传主模块：

```bash
node <技能目录>/scripts/analysis-cli.mjs resolve --product <名称|ID> --module <名称|ID> [--version <Tag>] [--related <模块:Tag> ...] [--config <映射文件>]
```

`resolve` 返回“精准 Git Tag 校验失败”时，按缺参模板打回，并把失败模块和 Tag 原样列出；不要改用默认分支，也不要继续调用 `analyze`。

**4.3 调用故障分析接口并生成 HTML 报告**

```bash
node <技能目录>/scripts/analysis-cli.mjs analyze \
  --dir <工作目录>/<KEY>/attachments \
  --product <名称|ID> --module <名称|ID> [--version <Tag>] [--related <模块:Tag> ...] \
  --key <KEY> --jira-url <缺陷单地址> \
  --out <工作目录>/<KEY>/故障分析报告-<KEY>.html
```

- 脚本会：上传日志与图片 → 提交异步分析 → 轮询进度（每行 `[analysis]` 输出可直接作为任务日志）→ 渲染单文件 HTML 报告。
- 退出码 `2` 表示分析任务部分失败（例如某个任务超时），此时仍会生成报告，按报告里的失败原因如实写入评论。
- 图片识别由模型完成（本地 OCR 默认停用），不要把“截图里没有文字”当作“没有问题”。
- 附件里没有可分析的日志或图片时，改成评论说明“附件不足以自动分析，请补充日志或截图”，并把门禁字段写成 `未检查`。

**4.4 上传报告 + 写评论**

```bash
node <技能目录>/scripts/jira-cli.mjs attach <KEY> --file <报告.html> --filename 故障分析报告-<KEY>.html
node <技能目录>/scripts/jira-cli.mjs comment <KEY> --file <评论正文.txt>
```

- 评论正文按「输出模板 · 已自动分析」写，结论必须来自报告（`analysis-cli.mjs` 输出的 `summary`），**不允许改写或美化模型结论**。
- 附件上传失败时：先重试一次；仍失败则把结论摘要与报告本地路径写进评论，并在对话里明确告知用户需要手动上传。

**4.5 写门禁字段**

`gate.json` 内容示例：`{"result":"通过","selfCheck":"无","report":"故障分析报告-<KEY>.html"}`。

```text
* 本结论由故障分析工具自动生成，请研发结合报告中的代码位置与证据复核后再关闭缺陷单。
```

```text
* 结论：缺陷单信息完整，但缺少自动分析所需的产品/模块/版本信息 | 预检时间：2026-09-20 10:30（AI 预检）

h4. 需要补充

# (x) *精准 Tag*：see-task:v1.2.3 在 GitLab 不存在 → 改填该模块实际发布的 Tag
```

写这条评论时只列实际缺失项，不要把示例中的未通过项原样照抄。缺模块或 Tag 时，在评论里给出下面这段固定块，并把已知模块和已知 Tag 填好；未知值替换成实际值后再触发本技能：

```text
[FAULT_ANALYSIS]
<模块名>:<Tag>
<关联模块名>:<Tag>
```

固定块补齐并重新触发后，技能会解析产品、主模块、关联模块和 Git Tag，先校验所有 Tag 都真实存在，再提交分析，不再要求额外确认。

### 映射缺失（通知维护人并跳过检查）

当 `analysis-cli.mjs resolve` 返回 `reason` 为 `scope-mapping-missing`、`scope-mapping-invalid` 或 `scope-mapping-ambiguous` 时，说明工单已有分析对象，但 `config/scope-mapping.json` 缺少产品、模块、仓库地址或版本转 Tag 规则。此时**不按缺分析参数打回**，也不要求提单人重复补模块；使用 `resolve` 输出里的 `comment` 原样写评论，写门禁字段 `{"result":"未检查","selfCheck":"无"}`，并执行下面的命令把工单转派给映射维护人，结束任务：

```bash
node <技能目录>/scripts/jira-cli.mjs assign <KEY|URL> --user <返回结果中的 mappingOwner.name>
```

`assign` 只改经办人，不改变工作流状态。返回结果里的 `mappingOwner.name` 是登录名，默认 `yinfuqian1193`，展示名尹甫乾；不要传中文展示名。转派失败时不能静默结束，必须追加评论写明失败原因和“请映射维护人手工接手”，并保留门禁结果 `未检查`。评论固定为：

```text
h3. 模块映射丢失，已跳过检查

* 结论：工单中的产品、模块或版本已识别，但 {{config/scope-mapping.json}} 缺少对应映射，本次门禁未检查。
* 待处理：[~yinfuqian1193] 请补齐映射内容：产品、模块、仓库地址，以及版本转 Tag 规则。
* 当前识别：产品={{<实际产品>}}；模块={{<实际模块>}}；版本={{<实际版本>}}。
* 缺口：<返回的实际缺口>
* 处理方式：无需提单人重复补充模块；映射补齐后重新触发本技能即可自动检查，不要求额外确认。本单会转派给上述映射维护人，不改变工作流状态。
```

映射维护人可在 `config/scope-mapping.json` 顶层用 `mappingOwner` 覆盖 `name`、`displayName` 和 `mention`；默认账号为 `yinfuqian1193`，Jira 提及写法为 `[~yinfuqian1193]`。映射缺失分支会自动把经办人设为这里的 `name`，因此修改负责人时不要只改展示名。

公共组件仓库在 `scope-mapping.json` 中以 `common: true` 留存，但不作为独立模块写进评论固定块，也不要求发布或提供精准 Tag。主模块和普通关联模块的代码或日志确认引用公共组件后，后端会自动拉取该公共组件的默认分支参与分析；未命中的公共组件不会拉取，拉取失败只记录跳过证据并继续主分析。代码分析确认引用公共组件时，应在结论中说明“本缺陷引用了 xxx 公共组件功能，关键代码在 xxxxxx”；无法定位关键代码时必须明确说明，不得编造。公共组件没有精准 Tag 不作为打回原因；非公共模块仍严格使用精准 Tag，不回退默认分支。

效果类缺陷命中日志/复现豁免时，评论中的相关检查项写成 `(/)`，并注明固定依据“评论区已声明：明确缺陷不需要额外提供日志信息”，不得再要求补日志或复现步骤；其它检查项照常列出实际结果。未命中固定语句、或本单并不属于效果类缺陷时，不得使用该豁免。

每条打回评论都必须包含完整的「日志/复现豁免判定」，不能只写一句“不满足豁免条件”：

```text
h4. 日志/复现豁免判定

* 固定声明原文：明确缺陷不需要额外提供日志信息
* 判定条件：必须同时满足“本单是效果类缺陷”和“评论区存在上述固定原文”，缺一不可
* 当前结果：未豁免（当前判断不是效果类缺陷 / 评论区未命中固定原文，写实际原因）
* 影响范围：日志与复现步骤仍按普通缺陷检查；其它检查项不受影响
* 补充方式：如本单确属效果类缺陷，请补充上述固定原文；门禁复核后仅豁免日志与复现步骤
```

命中豁免时改为：

```text
h4. 日志/复现豁免判定

* 当前结果：已豁免（本单判定为效果类缺陷，且评论区已命中固定原文）
* 豁免依据：评论区原文“明确缺陷不需要额外提供日志信息”
* 豁免范围：仅日志与复现步骤；截图、录屏等效果证据仍需提供，其它 MUST 和全部 REDLINE 均不豁免
```

## 令牌与配置

- Jira 令牌：`JIRA_TOKEN` 环境变量（部署时由 `.env` 注入）。容器内后端注入 `SKILLRUN_ENV_LOCKED=1` 后只认该环境变量与 `JIRA_BASE_URL`；桌面端未锁定时可回落到 `--token`，或技能目录 / `~/.codex` 下的 `.jira-token`、`jira-token.txt`、`~/.codex/jira/config.json`。
- 故障分析服务：`ANALYSIS_API_BASE_URL`（容器内默认 `http://api:5000`，宿主网络为 `http://127.0.0.1:5000`）与 `ANALYSIS_API_TOKEN`（内部令牌，未配置时脚本会直接报错并说明如何配置）。
- 分析范围映射：`config/scope-mapping.json` 维护产品、模块、仓库地址、版本到 Git Tag 的规则，以及映射缺口通知人 `mappingOwner`。产品值来自 Jira「问题发现产品」；工单缺模块时要求提单人补充，工单已有模块但配置中缺映射时通知维护人并跳过检查，不允许模糊匹配。
- 可选 `jira-config.json`（放在技能目录或 `~/.codex/jira/config.json`）：

```json
{
  "gateResultField": "缺陷单预检结论",
  "gateSelfCheckField": "缺陷单自查结论",
  "gateReportField": "缺陷单分析报告",
  "gateCheckedAtField": "缺陷单预检时间",
  "rejectTransitionName": "打回",
  "selfCheckKeywords": {
    "headline": ["自查", "自检"],
    "conclusion": ["结论", "通过", "已定位"],
    "evidence": ["日志", "截图", "复现"]
  }
}
```

  `rejectTransitionName` 默认不配置：**默认只写评论与门禁字段，不动工作流状态**。配置后执行打回流转时，会自动保留并恢复流转前的原经办人（处理人）；恢复失败必须如实报告，不能把打回说成已完成。

## 硬性约束

- 除门禁字段、打回后的经办人恢复和映射缺失时的经办人转派外不修改缺陷单字段；打回时不得让门禁账号占用经办人字段，必须恢复流转前的原经办人；映射缺失时经办人必须转派给 `mappingOwner.name`。
- 未配置 `rejectTransitionName` 时不流转状态、不关闭缺陷单。
- 不编造分析结论：评论里的结论必须来自 `analysis-cli.mjs` 的输出。
- 不把“检索工作”反问给提单人；不因为某项无法判定而停止其余项检查。
- 不生成报告类文档作为唯一交付物；报告必须作为附件进入缺陷单。
- 不留未完成的草稿评论；评论写入前确认内容完整。
- 不打印、不回显、不写盘任何令牌。

## 故障排查

| 现象 | 处理 |
|---|---|
| `未配置 ANALYSIS_API_TOKEN` | 在 `.env` 设置 `ANALYSIS_API_TOKEN` 并在 api/worker 生效后重试 |
| `缺少代码仓库地址或版本` | 先用 `jira-cli.mjs scope` 查看来源；缺模块/版本时按固定评论块补齐，仓库地址由 `scope-mapping.json` 维护 |
| `reason=scope-mapping-missing/invalid/ambiguous` | 工单已有分析对象，但配置缺映射：原样使用返回的 `comment` 通知 `mappingOwner`，门禁写 `未检查`，跳过检查且不打回；随后用 `jira-cli.mjs assign --user <mappingOwner.name>` 转派经办人 |
| `故障分析工具中没有匹配的产品/模块` | 配置映射存在但分析服务未注册该对象；记录实际错误，不要伪造映射或改用默认分支 |
| 分析任务超时 | 任务仍可能在后台完成：前端「历史记录」可见；可提高 `CODEX_SKILL_TIMEOUT` 与 `--timeout` 后重跑 |
| `鉴权失败` / HTTP 401 | 检查 `JIRA_TOKEN` 是否过期、`ANALYSIS_API_TOKEN` 是否与 api 服务一致 |
| 附件上传 413 | 报告或附件超过单据限制，压缩报告或拆分日志后重试 |
