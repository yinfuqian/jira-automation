# PRD 需求准入 Checklist（Jira 版）

本清单是 Jira 从「需求设计」流转到「开发设计中」的 G1 需求准入判定依据。章号沿用标准版《PRD 需求准入 Checklist》，便于逐条对照。

- **入口状态**：需求设计 ｜ **目标状态**：开发设计中
- **提交角色**：产品经理 ｜ **参与角色**：产品架构师、研发、测试 ｜ **最终确认角色**：产品架构师
- **检查范围**：业务需求是否完整、清晰、可实现、可测试、可验收；不检查 Java 类、接口实现、数据库字段、SQL、组件、线程池、部署参数等纯技术内容。

## 检查项等级

| 等级 | 含义 | 准入影响 |
|---|---|---|
| `MUST` | 所有需求必须满足 | 任一不满足即退回补充 |
| `CONDITIONAL` | 命中触发条件后必须满足 | 触发后等同 `MUST`；不触发需说明依据 |
| `SHOULD` | 有助于降低歧义和返工 | 不单独阻断，但需记录取舍 |
| `OBSERVE` | 进入研发后仍需关注的业务假设或风险 | 不代替缺失的业务事实，也不包装成已确认结论 |

勾选必须能指向 PRD 章节、稳定 ID 或明确证据；禁止只写“已考虑”“后续补充”或无解释的 `N/A`。

## 5. `MUST`：所有需求必查

### 5.1 文档与唯一事实源

- [ ] PRD 文件和版本唯一可定位，正文、文档说明和变更记录一致。
- [ ] 目标、范围、功能、规则、状态、权限、正式文案、异常和 AC 均以该版本 PRD 为准。
- [ ] Review、原型、图示、截图、历史资料或对话中的新增结论已经回填 PRD。
- [ ] 下游产物与 PRD 存在冲突时，已经修正 PRD 或停止消费冲突产物，而不是让研发自行裁决。
- [ ] 需求变化已经更新正文、版本和受影响产物清单。

### 5.2 背景、目标与范围

- [ ] 业务背景说明了目标用户或业务对象、当前问题、影响和当前解决必要性。
- [ ] 每个 `G` 目标使用完整句说明对象、场景和可观察结果，不是“新增页面”“接口改造”等实现动作。
- [ ] 本期包含的能力、对象和适用场景明确。
- [ ] 只有存在真实相邻范围歧义时才列“本期不包含”；不支持、不创建、不覆盖等会影响行为的负面规则已进入 FR/BR/IR。
- [ ] 不存在目标冲突、范围漂移或把未来设想混入本期交付的问题。

#### 5.2.1 需求背景与价值（客户、业务场景）

- [ ] 说明需求来源与提出方：客户 / 售前 / 线上问题 / 内部规划 / 合规要求，且可追溯到具体客户、项目或工单。
- [ ] 说明目标客户与业务场景：谁在什么场景下、为了完成什么业务目标而使用本期能力。
- [ ] 说明当前问题与痛点：现状如何操作、代价或风险是什么，不使用“体验不好”等无法验证的表述。
- [ ] 说明业务价值与影响面：对客户、业务指标或内部效率的可观察影响（覆盖客户数、涉及角色、替代的现有做法）。
- [ ] 说明紧迫性或“不做”的后果：业务损失、客户承诺节点或合规风险。
- [ ] 价值表述与本期范围一致，不包含本期不交付的内容。

### 5.3 用户、角色与核心场景

- [ ] 主要角色、次要角色、协作角色和外部参与方明确。
- [ ] 每类角色的触发场景、目标、权限边界和可观察结果明确。
- [ ] 主流程从入口、前置条件、关键动作到最终结果闭环。
- [ ] 关键反例、禁止路径和边界场景有明确产品行为。

### 5.4 功能与规则

- [ ] 每个正式功能都有唯一 `FR`，优先级符合 P0/P1/P2 定义。
- [ ] 每个 FR 至少说明需求、触发、产品逻辑和业务规则。
- [ ] 复杂判断、优先级、互斥、覆盖、例外或跨 FR 复用规则按需使用 `BR`；简单规则没有被过度编号。
- [ ] 跨页面联动、多状态/权限差异、复杂取消返回、异步或失败恢复按需使用 `IR`。
- [ ] 规则的触发、不触发、判断顺序、优先级、例外、结果和冲突处理能够唯一理解。
- [ ] 新增 FR、BR、IR、字段、状态、异常或产物能够回扣目标、AC、强制约束或现实失败路径，不存在无依据的未来预留。

### 5.5 状态、权限与操作

- [ ] 业务状态、状态含义、进入条件、允许操作、目标状态或状态不变结果明确。
- [ ] 权限不只描述“能/不能”，还明确显示、隐藏、禁用、只读或脱敏。
- [ ] 页面显隐没有被当作后端权限校验的替代。
- [ ] 多角色、多状态、多操作或字段/按钮存在差异时，提供状态—权限—页面元素—操作矩阵。
- [ ] 操作结果说明数据变化、业务副作用、下一状态和用户反馈。
- [ ] 非法状态、越权、重复操作和数据过期时的业务结果明确。

### 5.6 数据、字段与枚举

- [ ] 涉及 UI 或数据读写的 FR 已说明业务字段、来源、默认值、空值、读写和更新规则。
- [ ] 条件必填明确具体条件，不使用“按需必填”。
- [ ] 有业务意义的格式、长度、范围、精度、枚举和空值语义明确。
- [ ] 动态字段说明何时显示、隐藏、只读、可编辑或脱敏，以及隐藏后旧值如何处理。
- [ ] 枚举列明用户可见值和业务含义；接口编码和存储类型留给研发设计。
- [ ] 数据口径、权威来源、同步时点和历史数据行为明确。

### 5.7 异常、恢复与风险

- [ ] 对现实可触发且会改变用户结果或验收结论的失败路径定义产品行为。
- [ ] 参数非法、权限不足、数据不存在、状态冲突、重复操作和依赖失败有明确结果。
- [ ] 超时、重试、回退、取消、晚到结果、部分成功和并发冲突按适用场景闭环。
- [ ] 每类关键失败说明用户反馈、业务状态、数据保留和可执行恢复方式。
- [ ] 安全、合规、权限和不可逆数据损失等高影响路径没有因低概率被忽略。
- [ ] 风险与异常分开；真实风险包含触发条件、影响、应对和兜底。
- [ ] 正式 PRD 中不存在无处置的“待确认”“待评估”或“后续补充”。

### 5.8 验收标准

- [ ] 每个关键功能及 P0/P1 FR 都关联可验证 AC。
- [ ] 所有涉及 Prompt、模型输出、工具调用或模型失败会影响用户结果的 FR 都关联可验证 AC，不因优先级为 P2 而豁免。
- [ ] AC 能回扣 FR，必要时关联 BR/IR，不使用“功能正常”“体验良好”等不可判断表述。
- [ ] AC 覆盖主流程、关键反例、边界、权限、状态、依赖失败、超时和历史兼容。
- [ ] AC 定义产品最低验收集合；完整 TC 和执行等级由测试继续展开。
- [ ] 指标型需求说明指标定义、门槛、样本范围、环境和验收方式，不编造生产 P95。

#### 5.8.1 验收标准明确且可测

- [ ] 关键及 P0/P1 FR 的 AC 使用可判定的判定条件表达，推荐统一写成 **Given-When-Then**（前置条件 / 触发动作 / 可观察结果）。
- [ ] 每条 AC 的 Then 部分是可观察、可度量、可复现的结果（页面状态、数据变化、提示文案、状态流转、接口业务结果），不写“功能正常”“体验良好”“性能流畅”。
- [ ] AC 使用业务语言，研发与测试读到的结论唯一，不出现“视情况”“合理处理”“尽量”等无法判定表述。
- [ ] AC 覆盖主流程与关键分支：异常、边界、权限、状态、依赖失败与历史兼容（与 §5.7 对应场景一致），P0 场景至少各 1 条正向 AC。
- [ ] AC 不依赖未确认的外部条件；引用的数据、账号与环境前提已在本单或 PRD 中写清。
- [ ] 涉及 Prompt、模型输出、工具调用或模型失败的 FR，其 AC 给出可判定的质量门槛或人工评审方式，不因优先级为 P2 而豁免。
- [ ] AC 定义产品最低验收集合；完整 TC 与执行等级由测试继续展开。

## 6. `CONDITIONAL`：命中场景后必查

### 6.1 UI、交互或正式文案变化

触发：新增或修改页面、入口、字段、操作、用户可见状态或正式文案。

- [ ] 全部可编辑字段及影响理解、权限、状态或结果的只读字段有业务契约。
- [ ] 保存、取消、返回、关闭、字段联动、筛选分页、选择批量和失败恢复的业务结果明确。
- [ ] 非标准或高风险确认说明触发条件、作用范围、确认/取消结果、状态变化和失败恢复。
- [ ] 关键及 P0/P1 UI FR 有代表性原型模拟场景，覆盖核心状态、权限和允许/禁止操作。
- [ ] PRD 没有规定组件、校验触发时机、错误位置、加载和标准确认样式等普通前端实现。

### 6.2 多角色、多状态或复杂规则

触发：角色、状态或规则组合会改变动作合法性、结果或验收。

- [ ] 状态—权限—页面元素—操作矩阵可判定。
- [ ] 复杂规则使用一份权威 BR 文字或表格，不维护重复规则事实。
- [ ] 状态迁移、Guard、非法迁移、逆转、回退和副作用明确。
- [ ] 需要图示时，图只解释 PRD 已定义关系，不新增规则。

### 6.3 跨系统、异步任务或外部依赖

触发：依赖外部系统、回调、消息、轮询、异步长任务或批处理。

- [ ] 明确外部参与方、责任边界、触发和最终业务结果。
- [ ] 等待、处理中、完成、失败、超时、取消、重试和晚到结果的用户行为明确。
- [ ] 部分成功、重复结果、顺序冲突和依赖不可用时的产品口径明确。
- [ ] 用户是否可重试、离页、取消或转人工，以及恢复到何种状态明确。

#### 6.3.1 依赖项已识别（关联需求、外部接口需有协议）

触发：存在关联需求、前置需求、外部系统、外部接口或第三方协议时。

- [ ] 逐项列出依赖，至少说明：依赖对象、依赖内容、责任方、期望提供时间、解除条件。
- [ ] 关联需求：前置、阻塞、被阻塞、替代或需共同发布的需求已建立 Jira 问题链接，并说明相互影响。
- [ ] 外部接口：明确责任方与提供方；**接口协议或联调依据（接口清单、字段、请求与响应、错误码、鉴权方式）已有归属人**；协议未定稿时写明定稿时间点与未定稿期间的处理方式。
- [ ] 第三方协议：涉及外部客户系统、第三方平台或标准协议时，说明协议名称与版本、对接方式、联调与验收责任边界。
- [ ] 依赖不可用或延期时的产品兜底行为明确（降级、排队、转人工、暂不开放），并说明用户可见结果。
- [ ] 依赖项已纳入工作量评估与子任务拆解（见 6.7.1），不存在无人负责的准备工作。

### 6.4 数据迁移、历史兼容或既有能力改造

触发：修改历史数据、既有接口、字段、状态、配置或用户行为。

- [ ] 新旧行为、兼容范围、生效时点和历史数据口径明确。
- [ ] 存量用户、旧页面、旧数据、旧调用方和旧版本的可观察结果明确。
- [ ] 迁移失败、回退和不可逆数据影响有产品边界和 AC。
- [ ] 本期是否需要双轨、灰度或旧能力保留有明确业务决策。

### 6.5 LLM、Prompt 或模型输出参与关键路径

触发：Prompt、模型输出、工具调用或模型失败会影响业务动作、状态或用户结果。

- [ ] 明确 `instruction_change_mode=create | tune_existing` 和稳定指令身份。
- [ ] 说明模型解决的业务问题、输入范围和每个输出通道的具体消费者。
- [ ] 说明模型结果映射到何种业务状态、动作或用户反馈。
- [ ] 定义主要质量指标、指标口径、数值门槛和必须单独达标的关键切片。
- [ ] 定义适用的输出长度、Token、时延、成本和失败预算边界。
- [ ] 定义拒答、超时、非法输出、安全拦截、重试、降级和人工兜底的产品行为。
- [ ] 模型输出触发副作用时，PRD 已定义允许动作、业务状态、用户反馈和 AC。
- [ ] 未要求产品经理提供候选模型、Schema 实例、部署环境、模型账号或实验配置。

### 6.6 性能、容量、安全或合规有产品承诺

触发：相关约束会影响用户行为、可用性、合同、合规或验收。

- [ ] 指标和门槛可测，说明口径、时间窗、负载或样本条件。
- [ ] 超出限制时的用户反馈、降级、排队、拒绝或恢复行为明确。
- [ ] 安全、隐私、脱敏、保留、删除和审计的产品边界明确。
- [ ] 未把线程数、数据库类型、代码框架等内部技术参数当作产品输入。

#### 6.6.1 非功能要求已说明（性能 / 安全 / 兼容）

- [ ] **性能**：说明本需求相关的口径与门槛（并发、时延、吞吐、资源占用、数据量级），写明样本条件或测量环境；确无性能承诺时显式写“不涉及”。
- [ ] **安全**：说明鉴权与越权行为、敏感数据范围与脱敏要求、审计与留痕要求、日志中敏感信息的处理；确无安全影响时显式写“不涉及”。
- [ ] **兼容**：说明需兼容的既有版本、协议、浏览器、客户现场环境、旧数据与旧调用方，以及不兼容时的用户可见行为；确无兼容负担时显式写“不涉及”。
- [ ] 三类中判断为“不涉及”的必须有依据，不能留空或默认不写。
- [ ] 非功能要求同样具备可测 AC（见 5.8.1），不只写成口号式描述。
- [ ] 未把线程数、数据库类型、代码框架等内部技术参数当作产品输入。

### 6.7 工作量与任务拆解

触发：需求进入排期、迭代计划或交付承诺评估时。

> **G1 口径**：本节不进入 §10 一票退回红线，未满足不阻断 G1 需求准入；结论中记为“排期前必须补齐项”，由产品架构师在进入迭代计划前确认。若贵司要求 G1 即校验，可将本节提升为 `MUST`。

#### 6.7.1 产品工作量已拆解到子任务（有工时 / 人天）

- [ ] 需求已拆解为可执行的 Jira 子任务，每个子任务可由一名责任人独立推进，不使用“完成后再看”“后续再拆”的笼统拆分。
- [ ] 每个子任务写明：完成定义、预估工时（人时 / 人天）或 Story Points、责任人。
- [ ] 工作量按可交付单元拆分说明（接口对接、配置项、联调、测试支持、现场部署等），并注明**估算人**与**估算日期**。
- [ ] 工作量包含联调、客户现场支持、回归与文档成本，不只包含编码。
- [ ] 整体工作量有汇总值，评估口径与团队一致（如 1 人天等于多少小时），不使用无单位数字或纯相对值。
- [ ] 明确评估的前提假设，以及假设不成立时工作量的变化幅度。
- [ ] 子任务与依赖项（6.3.1）一一对应，不留下无人负责的准备工作。
- [ ] 责任角色：研发负责人 / 产品架构师；产品经理确认业务范围拆解无遗漏。

## 7. `SHOULD` 与 `OBSERVE`

### 7.1 `SHOULD`

- [ ] 目标较多或跨角色复杂时提供轻量 `G → FR → AC` 追溯矩阵。
- [ ] 复杂判断优先用单一决策表表达，避免重复文字。
- [ ] 参考资料标明用途，避免无说明链接池。
- [ ] 核心场景提供代表性反例，避免只描述成功路径。

### 7.2 `OBSERVE`

只记录不会改变当前业务规则和验收结论、但研发或发布阶段需要继续验证的事项，例如实际流量分布、模型候选效果、生产容量和第三方稳定性。

观察项必须说明：

- 当前已确认事实。
- 需要观察的指标或证据。
- 责任角色和检查时点。
- 观察结果可能触发的动作。

如果结果不同会改变当前产品行为或 AC，它就不是观察项，必须先关闭并回填 PRD。

## 10. 一票退回红线

命中任一项，准入结论必须为“退回补充”：

- PRD 文件或版本无法唯一定位。
- 目标、范围、主流程或核心角色存在未确认冲突。
- 仍需研发自行选择业务规则、状态、权限、动作结果或用户反馈。
- 关键及 P0/P1 FR，或涉及 Prompt、模型输出、工具调用或模型失败影响用户结果的 FR 缺少可验证 AC。
- 多角色、多状态、多操作场景缺少可判定关系。
- 关键字段的业务必填、枚举、空值、权限或动作后果不清。
- 现实可触发且会改变用户结果的异常、超时、回退或恢复未定义。
- 下游产物新增了 PRD 未定义的业务事实，且尚未回填。
- 风险会影响核心需求，但没有应对或兜底。
- 存在无处置的产品级“待确认”“待评估”或“后续补充”。

> **与新增验收项的关系**：5.2.1、5.8.1 未满足时适用本红线；6.3.1、6.6.1 仅在触发条件下按 `MUST` 处理；6.7.1（工作量与任务拆解）不进入红线，仅作为排期前补齐项。

## 11. 准入结论

准入结论只有两种：

- **通过**：所有 `MUST` 和已触发 `CONDITIONAL` 均满足，无未关闭产品语义问题；产品架构师在 Jira 留下正式 G1 结论后，可以流转到“开发设计中”。
- **退回补充**：存在红线、未满足的必须项或条件必填项，留在“需求设计”，不得进入技术方案设计。

`SHOULD` 或纯技术输入缺失不能被包装成产品准入红线；它们分别记录为取舍或专业角色补充。
