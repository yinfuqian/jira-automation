# Jira G2 技术方案准出检查（本地预检）

用户给一个 Jira 需求链接，你自己只读打开它，读完描述、附件、关联需求、历史评论，以及技术方案与 PRD，按《技术方案准出 Checklist》逐项判定，给出**通过 / 退回补充**结论；把结论（退回补充时附全部不通过项）只写入本地评论草稿，不提交 Jira。**全程禁止向 Jira 写入任何内容。**

## 交付物

**交付物只有一个本地预检包。**

1. 本地评论草稿：标题带「（本地预检）」。G2 侧只写结论、OpenSpec 权限、技术方案与 PRD 定位；**通过时不列检查项**，**退回补充时只列不通过项**，不输出通过项、`N/A`、机器判定明细与阻断项数量。PDCA 侧写检查结论、不通过项数与包内报告文件名；所有真实 @ 人语法必须替换为「建议处理人：姓名/登录名」纯文本。完整模板见本文档「输出模板（本地评论草稿）」节。
2. 本地 PDCA RD 报告：存在可检查的技术方案时生成 `{{需求名称}}_RD_{{YYYYMMDD}}_{{NN}}_PDCA.md`（见 §5.2），打包进本地预检包；没有技术方案时不生成空报告，草稿写「未生成（未上传交付物）」。
3. 本地门禁预演记录：草稿固定写「门禁字段：通过 / 不通过（预演未写入）」。
4. 对话里的摘要：单据类型 + G2 结论 + PDCA 结论 + 关键阻断项 + 建议流转 + 本地预检包绝对路径，供用户即时看到结果。

**流转只做预演**（见 §9）：

- 结论为**通过**：G2 的 6 项 `MUST` 全部满足、命中的 `CONDITIONAL` 不存在影响核心实现的阻断，且 PDCA RD 检查为「通过」；不流转状态，保持当前状态，允许进入 OpenSpec `propose` 与开发实施。
- 结论为**退回补充**：G2 命中任一明确阻断（见 checklist §3.1），或 PDCA 判「不通过」；只在草稿与摘要中建议流转到「开发设计中」，记录建议处理人文本，不真实 `@`、不调用流转接口。

**只生成 PDCA RD 角色报告这一份文档进本地预检包，其余报告类文档（HTML/Word 等）一律不生成。** 判定结论只写本地评论草稿；本地中间文件放在 `<工作目录>/work/jira-gate-2/<KEY>/`，最终报告和评论必须放进 `<工作目录>/outputs/` 下的 ZIP 预检包。

**这些中间产物在交付完成后要清掉**（见 §11）：附件与解压产物按任务累积，大方案解压后有几十 MB，留在工作区只会占空间。清理只在**全部交付动作成功之后**执行；交付失败的场景保留现场，便于排查。

## 判定依据

本技能执行**两套并列判定**，两套都必须完整执行，互不替代：

1. **G2 技术方案准出**：检查项、等级（`MUST` / `CONDITIONAL` / `SHOULD` / `OBSERVE`）与判定原则以 [references/checklist.md](references/checklist.md)（技术方案准出 Checklist）为准。
2. **PDCA 开发交付物检查（RD）**：以 [references/pdca-standard.md](references/pdca-standard.md)（通用团队交付物 PDCA 规范，`tools_version: V2.3.0`、`template_version: V1.1`、`collab_checks_skill_version: V1.0`、`ui_check_source_version: "1.2"`）为准，本次只执行其中 **§5.1 开发交付物**的 10 项必查项，以及 §2.4 事实源边界、§2.5 复用既有能力判别、§4 结论口径、§5.4 / §5.5 / §5.6 特殊情形、§6 报告格式、§7.2 Jira 评论格式、§10 禁止事项。产品侧 PRD、产品交付物与 G1/G2/G3 协作门禁由 `GENERIC_TEAM_COLLAB_CHECKS_SKILLS.md V1.0` 统一检查，本技能不重复执行该轮全量检查。

**先读完这两份参考再开始判定**，不要凭印象发明标准。PDCA 部分的具体执行口径见 §5.2。

核心口径：

- **类型与产品门禁先于全部判定与本地交付动作**：先做 §1 的 `precheck`，只处理 `issuetype` 为「故事」（英文站点 `Story`）且产品归属属于 Bot/Call/See/Pal/Learn/Aiforce 之一的单子；任一项不符时立即结束，G2 Checklist 与 PDCA 两套判定都不执行。
- **入口状态参考：开发设计中；通过预演为不改变状态，退回补充时建议流转到「开发设计中」。**
- 每次都执行全部 **6 项 `MUST`**（G2-M01 ~ G2-M06）与所有**命中的 `CONDITIONAL`**（G2-C01 ~ G2-C11），不抽样、不使用总分或平均分。
- 单项结果只允许「满足 / 不满足 / N/A」；`N/A` 只用于未命中的场景项，**由 Agent 内部标记，不输出、不作为退回项**。
- 只有 checklist §3.1 列明的**明确阻断情形**才判「退回补充」；非核心章节缺失、备选方案缺失、指标或任务排序不够详细、证据不够充分但不是核心契约的，不作为退回理由。
- 命中 `CONDITIONAL` 时，只有影响核心实现、数据权限结果、测试验收或发布安全的缺失才阻断；其余缺失记为改进建议，不阻断 G2。
- G2 只判断技术方案的核心实现路径、核心契约与验证入口是否足以让开发接管并进入 OpenSpec `propose`；**不读取、不引用、不输出 G1 结论**，**不校验代码基线、实现完成度，也不要求逐行对照代码**，不要求 OpenSpec tasks 或 Jira 执行子任务在准出前已经生成。
- 不因文档完整度或架构细节丰富度退回；背景复述、代码组织、命名、内部实现方式、非关键优化差异都不构成阻断。
- 前端与后端采用同一标准；涉及页面时按原型或用户确认核对页面入口、核心交互、状态来源、失败结果、权限结果与验证入口，缺失导致页面行为或验收入口无法确定时才阻断；纯后端需求应说明前端不适用及依据。

## 执行步骤

### 0. 运行环境适配（先读这一节）

本技能有两种运行环境，**取数通道不同，判定标准完全相同**：

- **桌面 Codex（带 `node_repl` 工具）**：按下面「通道 A」的 `node_repl` 片段执行。
- **服务器容器 / `codex exec`（没有 `node_repl`）**：用 shell 直接执行技能自带命令行入口 `scripts/jira-cli.mjs`（能力与 `node_repl` 通道一致）：

  ```bash
  # 令牌与连通性自检；令牌来自 --token、JIRA_TOKEN 环境变量或技能目录下的 .jira-token
  node <技能目录>/scripts/jira-cli.mjs selftest
  # 强制预检：类型为「故事」且产品归属在 Bot/Call/See/Pal/Learn/Aiforce 内才继续（见 §1）
  node <技能目录>/scripts/jira-cli.mjs precheck <KEY|URL>
  # 读取需求单并输出紧凑 Markdown 摘要（判定依据）
  node <技能目录>/scripts/jira-cli.mjs get <KEY|URL>
  # 下载附件到工作目录
  node <技能目录>/scripts/jira-cli.mjs attachments <KEY|URL> work/jira-gate-2/<KEY>/attachments

  # 流转人只读取用于本地预演；comment / comment-update / gate-set / attach / attach-prune / transition 均被 CLI 禁用。
  node <技能目录>/scripts/jira-cli.mjs flow-owner <KEY|URL>
  ```

  附件解析仍走 Python：`python <技能目录>/scripts/extract.py <附件目录> --out <附件目录>/../attachments.txt`。

  自检中「校验令牌」步骤返回 401 只表示该令牌无权访问 `/myself` 账户接口，**不等于令牌失效**：只要「访问 Jira」步骤成功、且 `get <KEY|URL>` 能取到需求单，就继续按流程完成检查。

  在该环境中不要尝试调用 `node_repl`，也不要因为缺少桌面工具而降低判定标准。

### 1. 单据类型与产品归属预检（强制，先做）

**只处理同时满足以下两个条件的 Jira 单子：**

1. 类型（`issuetype`）为「故事」；
2. 产品归属（`产品归属`，旧单兼容 `问题发现产品` / `发现产品`）属于 `Bot`、`Call`、`See`、`Pal`、`Learn`、`Aiforce` 之一（大小写不敏感，多值字段只要命中一个即可）。

这是本技能的**第一道强制门禁**，口径与 `jira-gate-1` 完全一致：在读取附件、执行 G2 判定、执行 PDCA 判定、生成报告或组织本地草稿之前，先执行：

```bash
node <技能目录>/scripts/jira-cli.mjs precheck <KEY|URL>
```

返回示例：

```json
{
  "ok": true,
  "key": "CALL-1446",
  "issueType": "故事",
  "expected": "故事",
  "typeSupported": true,
  "product": "Call",
  "productField": "产品归属",
  "products": ["Call"],
  "expectedProducts": ["Bot", "Call", "See", "Pal", "Learn", "Aiforce"],
  "productSupported": true,
  "supported": true,
  "status": "开发设计中",
  "summary": "..."
}
```

- `supported: true`（`typeSupported=true` 且 `productSupported=true`）→ 继续 §2。
- `supported: false` 或任一字段为空 → **立即停止**，不做任何后续动作：
  - 不执行 G2 Checklist 判定，也不执行 PDCA RD 检查；
  - 不生成 PDCA 报告，也不生成或打包本地预检包；
  - 不 @ 任何人，也不清理（本次没有产生中间产物）。

  只在对话里说明「该单类型为 X、产品归属为 Y，不在『故事 + Bot/Call/See/Pal/Learn/Aiforce』范围内，按规则跳过，未对 Jira 做任何写操作」，并在 `.skill-result.json` 里把 `conclusion` 写为 `不适用`。
- 不要用概要、标签、模块或描述去猜测类型与产品归属；只认 Jira 的 `issuetype` 与产品归属字段。字段缺失一律视为不满足。
- `productField` 用于说明值取自哪个候选字段（`产品归属` / `问题发现产品` / `发现产品`），便于排查取数异常。

### 2. 解析单号

`parseIssueKey()` 支持 `/browse/KEY`、`?selectedIssue=KEY`、jql 链接、纯 `KEY` 四种输入。

### 3. 取数：通道 A —— Jira REST（首选）

本地预检优先用技能自带 CLI，而不是 `node_repl`。CLI 入口会显式开启本地模式并只允许只读请求。如果必须使用 `node_repl`，只能在动态导入后调用只读函数；不要在 `node_repl` 顶层引用 `process`，也不要调用任何写函数。

```javascript
// <SKILL_DIR> = 本 SKILL.md 所在目录的绝对路径（如 ~/.codex/skills/jira-gate-2-local）
const j = await import("file:///<SKILL_DIR>/scripts/jira.mjs");
const st = await j.selftest();              // 先自检：令牌、连通性、账号
nodeRepl.write(JSON.stringify(st, null, 1));
```

自检通过后取数：

```javascript
const check = await j.precheckIssueType("CALL-1446");   // 类型不是「故事」或产品归属不在清单内时必须立即停止
const issue = await j.getIssue("CALL-1446");            // 也接受完整 URL
nodeRepl.write(j.renderIssueMarkdown(issue));           // 紧凑摘要，不要直接打印原始 JSON
const files = await j.downloadAttachments(issue.key, "<工作目录>\\work\\jira-gate-2\\CALL-1446\\attachments", { issue });
```

- `getIssue()` 返回规范化对象：描述、自定义字段（中文名）、附件、问题链接、子任务、评论、工时。
- `renderIssueMarkdown()` 是控制上下文的关键，用摘要做判定；只有摘要被截断时才回到原始对象取局部字段。
- 附件下载后用内置 Python 解析文本（脚本只支持动态导入，Python 走 PowerShell）：

```powershell
# $py 用 load_workspace_dependencies 返回的 Python 路径；<SKILL_DIR> 同上一层说明
& $py "<SKILL_DIR>\scripts\extract.py" "<附件目录>" --out "<附件目录>\..\attachments.txt"
```

若环境里已有可用的 `python`（需带 pdfplumber / python-docx / openpyxl / python-pptx），直接 `python extract.py ...` 也可以。

支持 `docx / pdf / xlsx / pptx / txt / md / json / xml / csv / html`；**解析失败要如实记为"无法解析"**，不能当成"附件没有内容"。图片附件用图像查看能力看，不做臆测。

附件是压缩包时脚本会先解压再递归解析（`.zip / .rar / .7z / .tar / .tar.gz / .tgz / .gz / .bz2 / .xz`），解压产物放在 `<附件目录>\__unpacked\`，输出里用 `压缩包名/内部路径` 标明每个文件的来源：

- **`.rar` 是重点**：服务端镜像已预装 `bsdtar`（libarchive-tools）与 7-Zip 系命令，脚本按 `bsdtar` → `7z` → `7zz` → `7za` → `unar` → `unrar` → `tar` 顺序降级，**容器内无需也无法通过联网安装来解决解压问题**；Windows 桌面端则由系统自带的 `tar.exe`（同为 bsdtar）兜底。
- **不要安装软件**：解压工具、Python 与 Node 依赖都已在镜像内备好。遇到工具缺失时如实记录并说明，不要执行 `apt-get` / `pip` / `npm` 等安装命令。
- 引用证据要写到压缩包内部，例如 `技术方案附件.rar/xxx_功能描述与技术方案.md §5.2`。
- 解压失败时会输出 `[压缩包解压失败]` 及尝试过的命令与报错，**这种情况必须如实记为"附件无法解析"，不能当成"附件没有内容"，也不要臆测包内内容**。
- 可选 `--unpack-dir <目录>` 指定解压位置；默认的 `__unpacked` 目录在遍历时会跳过，不会重复解析；同名解压结果自动加 `-2` 后缀，不覆盖上一次结果。

### 4. 取数：通道 B —— 应用内浏览器（无令牌时兜底）

没有配置令牌时，用已登录的应用内浏览器打开需求单：

1. `cua.createBrowserTab("iab", issueUrl)` 打开单子。
2. 用 `tab.playwright.evaluate(() => document.body.innerText)` 取正文，可拿到概要与描述、附件列表、问题链接、子任务、评论；**同时确认页面上的「类型」字段是「故事」、「产品归属」属于 Bot/Call/See/Pal/Learn/Aiforce 之一**，任一项不满足就立即停止。
3. 附件：点击附件链接触发下载，再对下载目录跑 `extract.py`（压缩包会自动解压，见上一节）。
4. 结论评论只写本地评论草稿；不要在页面评论区输入或提交任何内容。

注意：Jira 的 `/rest/...` 地址在浏览器里会被拦截（`ERR_BLOCKED_BY_CLIENT`），**不要在浏览器里访问 REST 地址**；浏览器只用于读取页面内容。通道 B 的结论必须注明"基于页面内容检查"。

### 5.1 G2 Checklist 逐项判定

对 `references/checklist.md` 的每条检查项给出：`满足` / `不满足` / `N/A`，并写明**证据位置**（技术方案章节、PRD 章节、原型、配置/数据库/日志/测试位置、附件名，必要时页码或行号）。

**必须覆盖的范围**：

- §5 全部 **6 项 `MUST`**：G2-M01 输入与事实源、G2-M02 核心链路与实现路径、G2-M03 核心接口/数据与状态契约、G2-M04 高风险场景控制、G2-M05 验证入口、G2-M06 开发接管与任务约束。
- §6 全部 **`CONDITIONAL`**（G2-C01 ~ G2-C11）：命中后逐条判定；只有影响核心实现、数据权限结果、测试验收或发布安全的缺失才阻断，其余记为改进建议。未命中的在内部记 `N/A`，**不输出**。
- §7.1 `SHOULD`：只记录取舍，不阻断结论；不在本地草稿中展开。
- §7.2 `OBSERVE`：只记录 G2 后仍需验证、且不会改变接口/数据/核心流程/任务拆分/AC/发布方式的事项。

判定要求：

- 先定位输入：Jira 主单、PRD、技术方案、涉及原型时的原型文件或用户确认记录。技术方案或 PRD 不可定位、不可读取时，G2-M01 不满足并直接退回补充。
- 业务事实以 PRD 为准；方案改写或新增 PRD 未写的目标、范围、角色、规则、状态、权限、文案或验收结果，判不满足。业务冲突退回 PRD 修改并重新走需求准入；技术事实冲突由方案设计者调查并修订技术方案。
- 证据按技术方案的实际内容取证，不要求固定章节标题或完整架构说明；核心结论缺失、核心内容冲突或命中 checklist §3.1 明确阻断情形的，判不满足。
- 非核心证据缺失、章节缺失、备选方案缺失、监控指标或任务排序不够详细，不作为退回理由。
- 纯代码组织、命名、内部实现方式或个人编码习惯差异，不改变外部行为、接口契约、状态、数据含义、权限、失败结果、验收结论或发布方式的，不阻断 G2。
- 不读取、不引用、不输出 G1 结论或评论；不校验代码基线、实现完成度，也不要求逐行对照代码。
- 不把"OpenSpec tasks 尚未创建"当作不满足；tasks 在 G2 通过后生成。
- 不把未决的模型参数、实验配置等可以在实施前继续细化的事项当作阻断，除非会改变失败策略或业务结果。
- 不评价 PRD 自身质量，不产出 PRD 缺口清单；发现产品语义缺口时写明"回到 PRD 修改并重新走需求准入"，不计入技术方案不通过项。

### 5.2 PDCA 开发交付物检查（RD）

在 G2 Checklist 判定的同时，按 [references/pdca-standard.md](references/pdca-standard.md) 执行 PDCA 的 `Check` 阶段，检查研发的技术方案是否偏离 PRD。**PDCA 是 G2 的补充判定维度，不替代 G2 主判定；两套结论都要写进同一条准出评论。**

**前置条件：§1 类型与产品归属预检必须已通过（`supported=true`）**。任一项不满足时，本节整体不执行，也不生成任何报告。

**角色与范围**

- `mode: jira`、`role: RD`，等价于 `trigger_type = RD_TECH_PLAN_READY`；被检查对象就是本单的技术方案。
- **只执行 RD 一类**：不得自动扩查 QA（测试方案/用例）或 UI（精修原型）。PDCA 规范禁止在未触发时检查其他角色，也不允许把不同角色合并成一份报告。
- PDCA 不修改 PRD、不改写技术方案，也不改 Jira 状态、标签或字段；状态流转只按 §9 预演。

**输入定位**

| 输入 | 定位规则 | 缺失时 |
|---|---|---|
| 技术方案 | 本单附件中匹配 `{需求名称}_功能描述与技术方案.md`；多份时取版本最高 / 最新上传 | 判 PDCA「不通过」，草稿写「未生成（未上传交付物）」，不生成报告 |
| PRD | 附件名以 `{需求名称}_PRD_DELIVERY` 开头且扩展名为 `.md`；多份取语义版本最高，同版本取最新上传 | 记「执行异常」，不产生通过/不通过、不生成报告 |
| 产品交付原型 | 附件名以 `{需求名称}_Prototype` 开头且 `.html`，多份取最新 | 不阻断（PDCA RD 必查项不比对视觉基线），在报告中注明缺少基线 |
| 门禁参照 | 本技能的 `references/checklist.md` | 必然存在 |

PRD 无法唯一定位（多份均无版本号、最高版本仍不唯一）时同样记「执行异常」。**技术方案或 PRD 缺失不改变 G2 的业务结论**：G2-M01 仍按 §5.1 判不满足并退回补充，PDCA 侧只如实标注原因。

**事实源边界（硬约束）**

```text
PRD-DELIVERY：唯一业务事实源
技术方案：被检查对象，不得反向定义产品事实
现有门禁 Checklist：门禁参照，不复制、不改写
```

- 技术方案与 PRD 冲突时以 PRD 为准；出现 PRD 未写的业务规则、字段、枚举、正式文案或入口，判不通过。
- **不评价 PRD 自身质量**，不产出 PRD 缺口清单，不因 PRD 写得不扎实而判研发不通过；发现产品语义缺口时，结论写「回到 PRD 修改并重新走需求准入」，不计入研发责任项。
- 按规范 §2.5 判别「复用既有能力」：PRD 提出本次改变的必须承接，不认豁免；PRD 未提出改变的既有能力不进必查项、不进报告。

**必查项（D-01 ~ D-10，逐项判定，不得抽样）**

| 编号 | 必查项 | 通过边界 |
|---|---|---|
| D-01 | 范围承接 | PRD 本期范围内每个 FR／BR／IR 都有对应改动点；未新增 PRD 未写的业务行为 |
| D-02 | 功能承接 | 每个 FR 写明实现路径：模块、改动位置、入口 |
| D-03 | 规则承接 | BR 的判定条件、优先级、互斥、例外可对应到实现描述 |
| D-04 | 交互承接 | IR 的跨页面联动、多状态与权限差异、取消与返回已承接 |
| D-05 | 字段与数据 | 字段、枚举、默认值、业务长度／格式／范围、数据口径与 PRD 一致 |
| D-06 | 状态与权限 | 状态流转、角色权限、只读／历史版本／无权限表现与 PRD 一致 |
| D-07 | 异常与恢复 | 用户可见失败反馈、降级、恢复、失败落点与 PRD 一致 |
| D-08 | 正式用户文案 | PRD 已确认的正式文案与提示未被改写 |
| D-09 | AC 承接 | 关键及 P0／P1 AC 有技术承接与可核对的验证入口 |
| D-10 | 版本对齐 | 写明所依据的 PRD 版本；与当前 PRD 不一致时说明差异，并以当前 PRD 判定 |

**记录项（不判、不计入结论）**：分层与模块划分、缓存、消息、部署、性能实现、组件选型；代码、接口参数、数据库结构等技术内容本身（只核对是否与 PRD 业务语义一致，不评价技术方案优劣）。

**结论口径**

- 结论只有 `通过` / `不通过` 两个取值，**不使用「有条件通过」「基本一致」「需确认」等中间档**。
- 本次只执行 RD 一类，RD 结论仍只有 `通过` / `不通过` 两档；母版为 UI 新增的「待产品确认」不参与 RD 结论。PRD 缺失、不可读或版本无法唯一确定，或附件取证、检查执行中断时，按母版记为「执行异常」并作为**执行状态**记录，不产生 RD 业务结论，也不改变 G2 结论。
- `通过`：10 项必查项全部核对且无问题；`通过` 必须给出**页面 + 控件 + 触发条件**式的证据定位（技术方案章节 + PRD 稳定编号），不得只写「已实现」「有相关逻辑」。
- `不通过`：任一必查项缺失、与 PRD 不一致，或缺少可核验证据；提供不出依据的「已确认」「已定口径」同样判不通过。
- 交付物以「当前系统不具备该能力」「运行时没有该链路」「本期不支持」缩减 PRD 已确认范围时：该论断只算待证事实，判 `不通过`，整改要求固定为「补齐实现，承接 PRD 原范围」。
- 同一规则落在多个落点时逐落点判定，一处通过不代表整条通过。
- PDCA 不设置严重度分档，问题项只有「不通过」一种。

**PDCA 报告**

先落盘到本地，目录固定为 `<工作目录>/work/jira-gate-2/<KEY>/pdca/`：

```bash
# 生成报告（本地预检仍只保留 RD 章节；文件名按 需求名称_RD_YYYYMMDD_NN_PDCA.md）
# 不执行 attach / attach-prune；报告后续由 pack-local-deliverables.mjs 打进本地 ZIP。
```

- 文件名：`{{需求名称}}_RD_{{YYYYMMDD}}_{{NN}}_PDCA.md`，`NN` 从 `01` 起递增；本地预检不读取 Jira 旧附件编号，也没有历史 Jira 副本，同一任务重跑时删除本次工作目录旧草稿后重新从 `01` 开始。
- **禁止清理 Jira 历史附件**：不调用 `attach` / `attach-prune` / `attach-list`；不修改、不删除任何 Jira 附件。
- 报告顶部按规范 §6 写**最小 front-matter**（`artifact_type: pdca`、`mode: jira`、`source_prd`、`source_prd_version`、`checked_deliverable`、`generated_at`、`pdca_template_version: "V1.1"`、`collab_checks_skill_version: "V1.0"`、`ui_check_source_version: "1.2"`、`jira_issue`、`report_name` 等）；字段与母版保持一致，不自行增删。
- 章节按规范 §6.1.2 只保留 **一、PDCA 结论**、**二、开发侧方案检查结果与问题项**、**五、附录**（输入材料、必查项核对表、AC 追溯明细、未检查项、变更记录）；不生成 UI / 测试章节，也不把未触发的角色写成「未检查」。
- 色标统一用 🟢 / 🔴 / ⚪；问题编号用 `D-` 前缀，每项一张卡：影响 → 怎么改 → 完成标准 → PRD 要求 vs 交付物实际。
- **责任方只写交付方（研发）**，不把产品列为交付物问题的责任方。
- 不检查上传权限；评论草稿里的「PDCA 报告」行写包内归一化文件名「`<KEY>-PDCA-RD报告.md`（本地预检包，未上传）」。
- 同一 PRD 版本与同一技术方案内容（哈希一致）重复触发时可直接复用本次工作目录中的报告，不生成重复文件；最终包仍只保留最新一份。
- 报告的完整明细只留在报告里；评论只写结论与不通过项依据，不粘贴核对表正文、整改步骤或执行过程。

### 6. 得出准出结论

- **通过**：6 项 `MUST` 全部满足、命中的 `CONDITIONAL` 不存在影响核心实现/数据权限结果/测试验收/发布安全的阻断，且 PDCA 的 10 项必查项全部通过；开发可以直接进入 OpenSpec `propose`，无需重新决定业务规则或关键技术方案。
- **退回补充**：任一 `MUST` 不满足、命中的 `CONDITIONAL` 存在核心阻断、或 PDCA 必查项不通过；或存在 checklist §3.1 列明的未决技术问题（会改变外部行为、接口契约、状态、数据含义、权限、失败结果、验收结果或发布方式）。
- PDCA 因 PRD 缺失、不可读、版本无法唯一确定，或附件取证、检查执行中断而记「执行异常」时，**不改变 G2 业务结论**：由 §5.1 的 G2-M01 判定退回补充；评论里如实写「执行异常（原因）」，不得包装成通过，也不得凭空列出 PDCA 不通过项。
- PDCA 结论必须能追溯到 PRD 版本；G2 只要求 PRD 可定位，不强制版本号。方案与 PRD 版本不一致时以当前生效 PRD 判定，并在评论与报告中同时写明差异。
- `SHOULD` 缺失只记录取舍，不单独阻断；`OBSERVE` 不得承载会改变实现、测试或发布路径的未决事项。
- G2 结论只允许两个取值：`通过` / `退回补充`。不要用总分、平均分或"基本通过"等模糊结论。

### 7. 组织评论内容

按本文档「输出模板（本地评论草稿）」节的模板组织正文。G2 部分严格遵循 checklist §9.2 的精简口径：**通过时不列检查项，退回补充时只列不通过项**；PDCA 部分按 `references/pdca-standard.md` §7.2 只写结论、依据与包内报告名。

- 通过：只写结论、OpenSpec propose、技术方案定位、PRD 定位；再补 PDCA 三行、门禁预演与流转预演。不输出 MUST/CONDITIONAL/SHOULD 清单、阻断项数量、判定过程或 N/A 说明。
- 退回补充：在通过所需字段基础上，追加 PDCA 三行与「建议处理人」纯文本行，并逐条列出全部不通过项，每项一行；不输出通过项、`N/A` 项、机器判定明细、复审范围或阻断项数量。
- 不通过项统一写成 `G2-{检查项} {问题}；{责任角色}{补充动作}。`，责任角色写「研发」「方案设计者」或「产品经理」；PDCA 不通过项写成 `D-xx {问题}｜PRD依据：…｜交付物依据：…`。
- PDCA 不通过项与 G2 不通过项在同一份本地草稿中分列，不合并、不交叉替代；PDCA 的完整整改卡片只留在包内报告里。
- 不要用表格（列宽大、手机上难读），用有序列表。
- 评论总长建议 ≤ 2500 字符；不通过项较多时可放宽到 4000。

### 8. 写本地评论草稿

- 本地预检始终只生成草稿，不检查评论权限、不调用 `addComment()` / `updateComment()` / `comment` / `comment-update`。
- 复审同一张单子时，可只读 `findPreviousReviews(key)` 了解上一轮结论；本地草稿始终是独立预演稿，不回复、不编辑 Jira 历史评论。
- 通过时只在草稿里写结论、OpenSpec 权限、技术方案与 PRD 定位，不列检查项清单；退回补充时只列不通过项，不列通过项与 `N/A`。
- 结论为**退回补充**时，草稿只写「建议处理人：{{显示名/登录名}}」纯文本；不得写 `[~登录名]`。
- 完整顺序见 §9 第 4 条：**生成 PDCA 报告 → 写本地评论草稿与门禁预演 → 打包本地预检包 → 清理本次中间产物**。

### 9. 交付顺序与「仅退回补充时建议流转」

**第 4 条的交付顺序适用于全部结论；第 1～3 条只读取预演依据。结论为「通过」时不建议流转、不写待处理人；结论为「退回补充」时只做流转预演。**

1. 取建议处理人：`resolveFlowOwner()`，命令行即 `flow-owner <KEY|URL>`。**口径就是经办人**：优先取 `assignee`；经办人为空时才依次回退 `reporter` → `creator`，回退取到时必须在草稿和摘要里写明实际字段来源。`mention` 只用于识别人员，草稿只写「显示名/登录名」纯文本。
2. 流转预演：
   - 结论为**通过**：不执行流转，也不要调用 `transitionToStatus()`；草稿写「建议流转：保持当前状态（预演未执行）」。
   - 结论为**退回补充**：草稿写「建议流转：开发设计中（预演未执行）」，并写「建议处理人：{{显示名/登录名}}」。目标状态名固定使用「开发设计中」，不要按项目改写成别的状态，也不要用「评审中」「待办」等替代。
   - 可只读执行 `transitions` 命令或 `listTransitions()` 判断是否存在「开发设计中」流转；结果只用于预演说明，不调用 POST。
3. 本地预检不检查流转权限，不调用 `mypermissions` 后写回任何状态；权限或状态名称只写入说明文本。
4. **顺序固定为：生成 PDCA 报告 → 写本地评论草稿与门禁预演 → 调用 `pack-local-deliverables.mjs` 打包并读回 `ok=true` → 写任务根目录 `.skill-result.json` → 清理本次工作区中间产物**。打包命令示例：

```bash
node <技能目录>/scripts/pack-local-deliverables.mjs \
  --key <KEY> \
  --comment work/jira-gate-2/<KEY>/comment.txt \
  --pdca work/jira-gate-2/<KEY>/pdca/<需求名称>_RD_<YYYYMMDD>_<NN>_PDCA.md \
  --out outputs
# 没有技术方案、无需生成 PDCA 报告时，把 --pdca ... 换成 --no-pdca。
```

### 10. 门禁字段只做预演

若 Jira 侧已配置 G2 门禁字段，本地预检也不调用 `setGateResult()`；草稿中固定写预演结论：

* 门禁字段：不通过（预演未写入）

- 取值约定：通过写 `通过`，退回补充写 `不通过`；草稿和门禁预演必须一致。

## 预检规范

**取数范围**（以 Jira 需求单为唯一入口）

- 主单字段：类型（**必须是「故事」**）、概要、描述、优先级、客户名称、产品归属、影响的版本、经办人、标签、模块、工时 / Story Points。这些字段是**定位与证据来源**，字段缺失本身不构成不满足。
- 技术方案：`{需求名称}_功能描述与技术方案.md`（含版本）；方案中引用的架构图、时序图、接口定义、表结构变更、配置变更。这是 PDCA RD 的被检查对象。
- PRD：当前需求的 PRD（唯一业务事实源）。PDCA 按 `{需求名称}_PRD_DELIVERY` + `.md` 匹配，多份取最高版本；无法唯一确定时 PDCA 记「执行异常」。
- 原型/交互稿：涉及页面时必须有原型或用户确认记录及版本。
- 项目事实：`Project.md`、现有接口与配置、数据库结构、日志和测试材料，用于解释项目约束；G2 不校验代码基线、实现完成度，也不要求逐行对照代码。
- Jira：需求范围、状态、责任与问题闭环记录。
- 历史评论：判断上次阻断项是否已关闭、技术方案是否已升版。

**证据要求**

- 每条判定必须指向**具体证据位置**：技术方案章节、PRD 章节、代码/配置/数据库/日志/测试路径、附件文件名（必要时页码或行号）、评论时间点。
- 不允许无证据的"已满足"；找不到证据一律记为"不满足"。
- 证据冲突时（技术方案与 PRD/原型/项目事实不一致）不得自行选择：业务冲突退回 PRD 修改并重新走需求准入；技术事实冲突由方案设计者调查并修订技术方案。
- 附件位于压缩包内时，证据写到内部路径，例如 `技术方案附件.rar/xxx_功能描述与技术方案.md §5.2`。

**禁止事项**

- 不把"检索工作"反问给方案设计者；不因为某项无法判定而停止其余项的检查。
- 不编造方案未写明的内容，不把推测写成已确认事实。
- 不把"OpenSpec tasks 尚未创建""Jira 子任务尚未拆分"当作不满足。
- 不把未决的模型参数、实验配置等可以在实施前继续细化的事项当作阻断，除非会改变失败策略、业务结果或发布路径。
- 不修改需求单字段、不指派经办人、不 @ 任何人；退回补充时只写「建议处理人」纯文本。
- 只生成 PDCA RD 角色报告进本地预检包；不生成其他报告类文档，不上传任何附件，不在需求单中留下草稿评论。
- 不把 PDCA 结论替代 G2 结论，也不因为 PDCA 提到 PRD 缺口就把产品列为交付物问题的责任方。

## 令牌配置

凭证与地址解析顺序：容器内由后端注入 `SKILLRUN_ENV_LOCKED=1` 时**只认环境变量**（`JIRA_TOKEN`、`JIRA_BASE_URL`），不接受 `--token` / `--base-url` 与令牌文件，访问其它站点会直接报错；桌面端未注入该标记时按 入参 → 环境变量 → 令牌文件 解析。令牌文件按序查找 skill 目录下的 `.jira-token` / `.jira-token.txt` / `jira-token.txt`、`~/.codex/jira-token.txt`、`~/.codex/jira/config.json`（支持 `{"token":"...","baseUrl":"..."}`）。

`selftest()` 返回的 `baseUrl` 与 `baseUrlSource` 会标明本次实际访问的站点及来源；**若 `baseUrlSource` 是「内置默认值（生产 Jira）」而当前并非生产环境，先停下来修配置，不要继续预检。**

- 令牌来源：Jira → 右上角头像 → 个人访问令牌 → 创建令牌（Jira 10.3 Server 已启用 PAT）。
- 令牌只用于 `Authorization: Bearer`，不要打印、回显或写进报告文件。
- `selftest()` 返回未找到令牌时，直接告诉用户按上面的路径放好令牌文件，并说明放好后可以立刻重试；同时可以先用通道 B 只读取页面兜底完成检查。

## 硬性约束

- **只处理类型为「故事」且产品归属属于 Bot/Call/See/Pal/Learn/Aiforce 之一的单子**（口径与 `jira-gate-1` 一致）；任一项不符时立即停止，不执行 G2 与 PDCA 判定、不生成或打包 PDCA 报告，也不做任何 Jira 写操作。
- 状态流转规则：**通过建议保持当前状态**；**退回补充建议 → 开发设计中**；不得建议流转到「开发中」「评审中」「待办」等其他状态。不指派经办人，不调用流转接口。
- **必须同时执行两套判定**：G2 技术方案准出 Checklist 与 PDCA RD 开发交付物检查；任一不通过即退回补充，不得只跑一套。
- **禁止调用 `gate-set` / `setGateResult()`**；门禁字段只允许 `gate-get` 只读对照，草稿写「预演未写入」。
- **只生成本地 PDCA RD 报告**（`<需求名称>_RD_<YYYYMMDD>_<NN>_PDCA.md`）；打包时包内文件名固定为 `<KEY>-PDCA-RD报告.md`，不上传附件。
- **禁止调用 `comment` / `comment-update` / `attach` / `attach-prune` / `transition`**；包内 `jira.mjs` 传输层也只允许 GET，任何 POST / PUT / DELETE 都会被硬拦截。历史评论只读不改，技术方案、PRD 等产品附件不删除。
- 不编造方案未写明的内容，不把推测写成已确认事实。
- 不把单据字段缺失、OpenSpec tasks 未生成、纯代码风格差异当作不满足理由。
- 不把未完成的草稿当成交付；本地评论草稿必须完整并进入预检包。
- 打包输出固定为 `outputs/<KEY>-G2本地预检包-<时间戳>.zip`，包含本地评论草稿与可选 PDCA 报告；读回 `ok=true`、`zipBytes>0` 和 `entries` 后才算完成。
- 交付全部完成后先写任务根目录 `.skill-result.json`（见「写机器可读结果」），再按 §11 清理本次任务的工作区中间产物（只删 `work/jira-gate-2/<KEY>/`）；打包失败时保留现场，不要删。
