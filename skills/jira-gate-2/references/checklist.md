# 技术方案准出 Checklist

## 1. 定位

本清单是 Jira 从“开发设计中”流转到“开发中”的 G2 技术方案准出正式判定依据，也是技术方案进入 OpenSpec `propose` 和开发实施的唯一准出入口。

- **入口状态**：开发设计中。
- **目标状态**：开发中。
- **提交角色**：方案设计者。产品架构师或研发均可承担，不新增岗位。
- **参与角色**：产品经理、产品架构师、研发、测试。
- **最终确认角色**：产品架构师。
- **正式结论**：通过 / 退回补充。

G2 只判断 `{需求名称}_功能描述与技术方案.md` 是否完整承接已通过 G1 的需求，技术设计是否可落地，开发人员是否可以无歧义接管并进入 OpenSpec `propose`。G2 不检查代码是否已经实现，也不要求 OpenSpec tasks 或 Jira 执行子任务在准出前已经生成。

## 2. 权威来源与准出输入

- 指定版本 PRD 是当前需求唯一业务事实源。
- `{需求名称}_功能描述与技术方案.md` 是当前需求唯一技术设计事实源。
- 原型、图示、截图和交互稿定义页面结构、入口、控件、文案、状态和交互；没有原型时，以用户确认记录为界面事实依据。
- `Project.md`、代码、配置、数据库结构、日志和测试定义当前项目实现事实。发布包中的 `Project.md` 如标注为 Bot 项目样例，实际项目必须使用自己的项目上下文。
- Jira 提供需求范围、G1 结论、状态、责任和问题闭环记录。
- OpenSpec 在 G2 通过后消费技术方案，生成 proposal、spec、design 和 tasks，不重新猜测产品事实或关键技术决策。

正式判定前必须能够唯一定位：

- Jira 主单。
- 有效 G1 结论及对应 PRD 文件和版本。
- 技术方案文件和版本。
- 方案设计者。
- 代码基线，包括仓库、分支、Commit 或等价版本。
- 涉及原型时的原型文件或用户确认记录及版本。

输入冲突时不得由 Agent、研发或 OpenSpec 静默选择。业务冲突退回 PRD 并重新 G1；技术事实冲突由方案设计者调查并修订技术方案。

## 3. 判定原则

### 3.1 开发接管测试

两名合格开发人员仅依据 PRD、原型、Jira 单和本技术方案，如果能够形成不同且都合理的实现路径，并导致不同的外部行为、接口契约、状态、数据含义、权限、失败结果、测试结论或发布方式，则判定方案不可接管，G2 必须退回。

如果差异只存在于不改变上述结果的代码组织或个人编码习惯，不阻断 G2。

### 3.2 足够进入 OpenSpec propose

技术方案必须已经明确任务拆分所需的边界、依赖、顺序、不可省略工作和禁止自行推断项。G2 不要求提前写出全部 OpenSpec tasks，但要求 `propose` 阶段不需要重新决定业务规则或关键技术方案。

### 3.3 前后端同等可落地

前端与后端采用同一标准判断。涉及页面或交互时，技术方案必须基于原型或用户确认，说明页面入口、组件复用、技术选型、状态与数据流、交互闭环、用户可见状态、权限校验、兼容性、性能和验证方式。纯后端需求必须说明前端不适用及依据。

## 4. 检查项等级

| 等级 | 含义 | 准出影响 |
|---|---|---|
| `MUST` | 所有需求必须满足 | 任一不满足即退回补充 |
| `CONDITIONAL` | 命中触发条件后必须满足 | 触发后等同 `MUST`；不触发需说明依据 |
| `SHOULD` | 有助于提高可实施性、可验证性或可维护性 | 不单独阻断，但需记录取舍 |
| `OBSERVE` | G2 后仍需验证的技术假设或线上指标 | 不得承载会改变实现、测试或发布路径的未决事项 |

`N/A` 只适用于未命中的场景项，并必须记录不适用依据。证据不足、章节冲突或无法唯一判断时，按“不满足”处理。

## 5. `MUST`：所有需求必查

- [ ] **G2-M01 输入与事实源**：Jira 主单、有效 G1、PRD 版本、技术方案版本、方案设计者、代码基线可唯一定位；方案没有重新定义目标、范围、角色、规则、状态、权限、文案或 AC；输入冲突已按权威关系处理。
- [ ] **G2-M02 目标、范围与现状**：目标与 `G/FR/BR/IR/AC` 的承接关系明确；本期范围、非目标、影响面、现有实现和改造原因完整；代码现状结论有可定位证据。
- [ ] **G2-M03 系统边界与主链路**：系统、模块、前端、后端、任务和外部依赖的职责边界明确；正常、异常和异步分支能够从入口走到最终结果；上下游权威数据、调用方向和失败影响唯一。
- [ ] **G2-M04 实现路径与选型**：后端模块、前端页面与组件、复用和新增边界清楚；关键技术选型说明采用理由和至少一个未选方案；前端选型符合项目现有技术栈，并以原型或用户确认作为交互依据。
- [ ] **G2-M05 接口、数据与状态**：接口或消息的调用方、方向、请求、响应、枚举、空值、错误码和兼容策略明确；数据来源、权威数据、存储变化和迁移按适用情况闭环；状态进入退出条件、权限和用户可见结果唯一。
- [ ] **G2-M06 一致性、异步与幂等**：事务或提交边界明确；同步、异步、消息和外部副作用的失败顺序、重试、超时、补偿、对账和恢复可执行；重复请求、重复消费、并发和晚到结果有唯一处理结果。
- [ ] **G2-M07 权限与安全**：身份、角色、租户、资源归属和权威状态校验完整；前端显隐不替代后端鉴权；敏感数据、日志脱敏、导出删除授权和不可逆操作的控制与审计明确。
- [ ] **G2-M08 非功能闭环**：性能、容量、超时预算、限流、降级、配置、兼容、日志、指标、告警和排障按适用情况明确；每项给出设计结论、可测约束、失败动作和验证方式，未命中项有不适用依据。
- [ ] **G2-M09 测试、发布与回滚**：关键及 P0/P1 AC 有验证场景和测试入口；测试数据、环境和依赖准备可执行；发布顺序、兼容窗口、灰度、停止指标、代码回滚、数据回滚和外部副作用补偿明确。
- [ ] **G2-M10 开发接管与任务约束**：改动清单覆盖实际问题范围；任务顺序、依赖、并行边界、不可省略工作和禁止自行推断项明确；实现基线足以供 G3 对照；开发可直接进入 OpenSpec `propose`，无需重新决定业务或关键技术逻辑。

## 6. `CONDITIONAL`：命中场景后必查

触发场景只代表需要检查。命中后以下检查项等同 `MUST`；未命中时必须在机器明细中记录判断依据。

### 6.1 `G2-C01` 普通 CRUD

触发：单模块、低风险、无复杂状态、无跨系统副作用和迁移。

- [ ] 权限、资源归属、唯一性、分页、排序、批量和数据合法性边界明确。
- [ ] 接口失败、数据不存在、重复提交和发布回滚有可执行结果。
- [ ] 未触发的复杂状态、分布式一致性和压测项有不适用依据。

### 6.2 `G2-C02` 核心数据写链路

触发：核心数据新增或修改、不可逆动作、多个写步骤或业务副作用。

- [ ] 唯一约束、状态 Guard、事务边界和失败顺序明确。
- [ ] 幂等键、并发控制、补偿、对账和数据修复可执行。
- [ ] 核心 SQL、索引、数据规模和执行计划有事实或明确验证计划。

### 6.3 `G2-C03` 多系统同步协作

触发：多个服务或外部系统共同决定最终结果。

- [ ] 权威数据源、系统责任、协议、时序和失败归属明确。
- [ ] Deadline、重试、熔断、降级、部分成功和晚到结果明确。
- [ ] 不把不可控远程调用无保护地放入本地事务，并明确补偿与对账方式。

### 6.4 `G2-C04` 异步任务、消息、回调或批处理

触发：使用消息、异步任务、回调、定时任务或批处理。

- [ ] 消息或任务契约、Key、版本、顺序和大小边界明确。
- [ ] 生产失败、数据库提交关系、重复消费、乱序、积压和重放结果明确。
- [ ] 幂等、重试、死信、补偿、对账和用户可见状态明确。

### 6.5 `G2-C05` AI、LLM 与外部智能服务

触发：调用 AI、LLM、NLP 或模型推理服务，或模型输出参与业务结果和外部副作用。

- [ ] 调用契约、服务标识、鉴权、租户上下文、Deadline 和错误映射明确。
- [ ] 输出格式或 Schema、语义、安全、权限、权威状态和动作合法性校验明确。
- [ ] 超时、拒答、非法输出、安全拦截、降级、人工兜底、晚到结果和副作用保护明确。
- [ ] 质量门槛、关键切片、Token、时延、成本和 AC 验证口径明确。
- [ ] 模型参数、实验配置和候选模型可以在实施前继续细化，但不得替代失败策略和业务结果。

### 6.6 `G2-C06` 高并发或高可用

触发：存在明确容量、并发、稳定性或故障恢复要求。

- [ ] QPS、P95、并发、数据规模、故障预算和容量上限有事实或明确验证计划。
- [ ] 限流、隔离、线程池、队列、拒绝策略、热点保护和降级明确。
- [ ] 缓存击穿、锁竞争、依赖故障扩散和压测通过标准明确。

### 6.7 `G2-C07` 存量系统改造

触发：修改已有入口、调用方、公共能力、配置或隐藏契约。

- [ ] 现有调用方、数据、配置和隐藏契约已调查并有证据。
- [ ] 新旧行为、兼容期、灰度、回归范围和退出计划明确。
- [ ] 没有把现有实现偶然行为直接当成产品规则。

### 6.8 `G2-C08` 数据迁移

触发：新增、清洗、回填、切换或删除存量数据。

- [ ] 迁移范围、批次、顺序、限速、停机和在线策略明确。
- [ ] 清洗、校验、对账、失败续跑和重复执行结果明确。
- [ ] 双读、双写、切换条件、最终收口和不可逆数据补偿明确。

### 6.9 `G2-C09` 兼容性改造

触发：数据库、接口、消息、配置、依赖或客户端版本发生变化。

- [ ] 目标版本范围和新旧调用方混用行为明确。
- [ ] 字段类型、分页、保留字、索引、协议和配置差异已验证。
- [ ] 契约版本、废弃期、发布顺序和回退策略明确。

### 6.10 `G2-C10` 前端页面与交互改造

触发：新增或修改页面、路由、组件、表单、列表、前端状态或用户交互。

- [ ] 页面结构、入口、控件、文案、状态和交互来自原型或用户确认，没有自行补设计。
- [ ] 页面、路由、组件、状态管理和 API 适配职责明确，复用与新增边界清楚。
- [ ] 加载、空数据、错误、无权限、重复提交、取消、失败恢复和深链状态明确。
- [ ] 请求触发、缓存、竞态、取消、超时、重试和重复提交策略明确。
- [ ] 前端校验与后端最终校验边界明确，权限显隐不替代后端鉴权。
- [ ] 浏览器或客户端兼容、大数据量处理、前端性能和自动化或人工验证方式明确。
- [ ] P0/P1 AC 映射到页面行为、接口调用和测试入口。

### 6.11 `G2-C11` 前后端联动改造

触发：同时修改前端和后端，或前端依赖新增或变更的接口、枚举、错误码、状态或权限。

- [ ] 前后端责任、接口版本和数据权威边界明确。
- [ ] 字段、枚举、空值、错误码、分页和文案映射一致。
- [ ] 新旧前端与新旧后端混用行为、发布顺序和灰度为可执行方案。
- [ ] 联调、契约、权限、异常和回归测试有明确入口。

## 7. `SHOULD` 与 `OBSERVE`

### 7.1 `SHOULD`

- [ ] 方案优先复用现有模块、接口、组件和对象，新增实体有充分理由。
- [ ] 复杂链路使用最少但足够的图，主链路、跨系统链路和持续状态图与正文一致。
- [ ] 关键技术取舍记录备选方案、排除原因和影响。
- [ ] 日志、指标和排障字段支持按租户、业务和 traceId 定位。

### 7.2 `OBSERVE`

观察项必须包含当前依据、指标、责任方、时点、阈值和触发动作。观察结果如果会改变接口、数据、核心流程、任务拆分、AC 或发布方式，必须在 G2 前关闭，不能留作观察项。

## 8. 角色分工

| 角色 | G2 职责 |
|---|---|
| 方案设计者（产品架构师或研发） | 完成需求澄清、代码调查和技术方案编写；对方案可实施性、证据和开发接管负责 |
| 产品经理 | 处理业务语义问题；确认方案没有改变 PRD 事实；需要变更时回填并升版 PRD，重新 G1 |
| 产品架构师 | 确认技术边界、关键选型和准出结论；对 G2 最终放行负责 |
| 研发 | 参与技术检查；确认方案可以被开发接管；不替产品选择业务结果 |
| 测试 | 检查关键及 P0/P1 AC 是否可测试、可观察、可验收 |

架构师或研发负责技术语言转换和边角澄清。能够从现有资料、项目事实或组织规范唯一确定的技术问题直接记录答案和依据，不转给产品经理。任何澄清如果会改变核心业务结果、权限、状态、数据含义、失败行为或 AC，必须回到产品经理并重新 G1。

## 9. Jira Agent 执行与输出

### 9.1 执行规则

- 触发场景为 Jira 从“开发设计中”流转到“开发中”，以及人工请求重新执行 G2。
- Agent 每次执行全部 10 项 `MUST` 和所有命中 `CONDITIONAL`，不抽样、不使用总分或平均分。
- 单项结果只允许“满足 / 不满足 / N/A”。证据不足、语义冲突或无法唯一判断按“不满足”处理。
- 技术方案文件缺失、版本不可定位、G1 无效或方案与 PRD 版本不一致时，直接判定“退回补充”。
- G2 通过前不要求 OpenSpec proposal、tasks 或 Jira 执行子任务已经存在；这些产物在 G2 通过后生成。
- 任一适用 `MUST` 或命中 `CONDITIONAL` 不满足，结论只能为“退回补充”，Jira 禁止流转，OpenSpec `propose` 禁止执行。
- 全部适用项满足时，结论为“通过”，允许进入 OpenSpec `propose`；产品架构师在 Jira 留下正式确认后，才构成有效 G2。
- 人工评论可以补充证据或记录架构师澄清，但不能直接把 Agent 的“不满足”改成“满足”。方案修改后必须重新执行完整 G2。

### 9.2 Jira 评论

评论顶部展示交接摘要：

```markdown
## G2 技术方案准出结论

- 结论：通过 | 退回补充
- OpenSpec propose：允许 | 禁止
- 结论说明：{{一句话}}
- 技术方案：{{精确路径}}，版本：{{版本}}
- 方案设计者：{{角色或人员}}
- PRD：{{精确路径}}，版本：{{版本}}
- G1 结论位置：{{Jira 评论或字段}}
- 代码基线：{{仓库、分支或 Commit}}
- 阻断项数量：{{数量}}
- 产品架构师确认人／时间：
```

结论为“退回补充”时，摘要后只列按责任角色归并的阻断项，不重复展示所有通过项。评论下部保留机器判定明细：

| 检查项 | 等级 | 结果 | 方案证据位置 | 失败原因或判定依据 | 责任角色 | 关联 AC/Jira |
|---|---|---|---|---|---|---|
| G2-M01 输入与事实源 | MUST | 满足 / 不满足 | {{章节或证据}} | {{说明}} | {{角色}} | {{ID}} |

### 9.3 重新判定

收到技术方案新版本、PRD 新版本、原型确认、代码证据或架构师澄清后，Agent 必须重新执行全部 `MUST` 和命中的 `CONDITIONAL`。不得只复查上次失败项，也不得因评论文字变化直接改变历史结论。

## 10. 生效、复审与指标

- G2 通过后，开发人员以 PRD、原型、Jira 单和本技术方案为输入，执行 OpenSpec `propose`、生成 tasks，再进入编码、联调、自测和问题修复。
- 如果 OpenSpec `propose` 发现新的系统边界、接口、字段、状态、数据模型、一致性方案、失败结果、AC 或关键技术选择，必须停止任务生成，修订技术方案并重新 G2。
- 仅进行不改变技术事实的任务拆分、排序或 Jira 子任务创建，不触发重新 G2。
- 已通过 G2 的历史需求不追溯作废；新规则从下一次 G2 判定开始执行。
- 必须统计 G2 执行率、无记录流转次数和核心阻断关闭率，目标分别为 100%、0、100%。
- 首次准出通过率只作为改进观察项，不设置惩罚性阈值，不用分数覆盖阻断项。

## 11. 判定示例

| 场景 | 结论 | 原因 |
