# GENERIC_TEAM_DELIVERABLE_PDCA_SKILLS

## 1. 定位

支持两种触发模式，并按模式生成报告：

```text
manual：{{需求名称}}_PDCA.md
jira：  {{需求名称}}_{{RD|QA|UI}}_{{YYYYMMDD}}_{{NN}}_PDCA.md
```

Jira 模式只有在触发角色确有可检查交付物时才生成报告；没有交付物时只回写不通过评论，不生成空报告。

本母版对应 PDCA 的 `Check` 阶段，用于产品经理检查协作团队交付物是否符合产品定义与期望，并把发现整理为可执行的 `Act` 闭环项。

它负责：

- 以现有 PRD 为唯一业务事实源，以产品交付原型为已确认需求的 UI 基线，按开发、测试、UI 三类必查项检查协作方交付物。
- 一次列出全部可识别问题，给出明确判定、事实依据、责任方和整改要求。
- 保留 PDCA 报告作为本需求的检查与整改记录，供复审和后续角色消费。
- 在 Jira 模式中生成供接入方回写到触发 Issue 的简明评论，以及需要作为附件上传的完整报告。

它不负责：

- 定义或修改 PRD 的业务事实。
- 评价 PRD 或产品交付原型自身的质量，也不产出 PRD 缺口清单。
- 替代产品架构师的 G2 技术方案准出、测试的 G3 提测准入或 UI 的正式设计验收。
- 修改 PRD、下游交付物，或 Jira 状态、标签和字段。
- 实现 Jira 鉴权、Webhook、重试、评论或附件上传接口；这些由 Jira 接入方负责。
- 对纯技术架构、组件选型、性能实现或测试工具选型作产品侧阻断判断。

检查结论是产品侧一致性意见和整改建议，不是正式门禁结论。正式门禁仍由各角色按现有依据判定。

产品是下游交付物的上游：产品先把需求写进 PRD、再把已确认的 UI 表达变成产品交付原型。本检查只判断下游交付物是否偏离 PRD 与已确认的 UI 基线，不反过来用交付物的缺陷给产品记问题，也不因为 PRD 自身没做扎实而给协作方判不通过。

## 2. 触发与输入

### 2.1 触发方式

PDCA 支持两种触发模式：

```text
mode: manual | jira
```

两种模式使用完全相同的必查项和结论口径，只在输入获取、报告命名和输出载体上不同。

#### 2.1.1 手工模式

产品经理明确表达检查意图时触发，例如：

- `check 下这个技术方案`
- `检查测试用例覆盖`
- `看下 UI 精修原型和 PRD 有没有冲突`
- `对开发、测试和 UI 交付物做一次 PDCA 检查`

按交付物增量触发：本轮只检查新提交的交付物，未被要求检查的其他类别在报告中写「未检查」，不自动重跑。手工模式仍生成固定主档 `{{需求名称}}_PDCA.md`，同一需求重复检查时更新该文件。

#### 2.1.2 Jira 模式

Jira 接入方在状态迁移或附件变化后调用本 Skill，并传入以下最小上下文：

```text
event_id          事件唯一标识
trigger_type      三类触发类型之一
issue_key         触发 Issue Key
parent_issue_key  UI 子任务的父需求 Key；其他类型为空
attachment_ids    本次新增或替换的附件 ID 列表
from_status       迁移前状态；附件事件可为空
to_status         迁移后状态；附件事件可为空
```

鉴权、Webhook 传输、附件下载、评论写入和附件上传由 Jira 接入方负责。Skill 只消费上述上下文和已授权的只读材料，不自行假定 Jira 平台版本或调用其写接口。

| `trigger_type` | 事件条件 | 检查对象 |
|---|---|---|
| `RD_TECH_PLAN_READY` | 主 Issue 从「开发设计中」迁移到「排期中」 | 主 Issue 中尚未处理的技术方案附件 |
| `QA_DELIVERABLE_READY` | 主 Issue 从「排期中」迁移到「开发中」或「测试中」，从「开发中」迁移到「测试中」；或在「开发中」「测试中」新增、替换测试附件 | 本轮新增或替换的测试方案、测试用例等附件；多个附件合并为一次 QA 检查 |
| `UI_SUBTASK_ATTACHMENT` | 设计子任务标题去除空格后包含「UI精调」或「UI调优」，且新增或替换附件 | 子任务附件；PRD 与产品交付原型从 `parent_issue_key` 对应主 Issue 获取 |

Jira 模式按事件指定的角色执行，不自动改查其他角色：

- 开发技术方案、测试交付物和 UI 交付物分别对应 `RD`、`QA`、`UI`。
- 同一轮事件包含同一角色的多个附件时合并检查，并生成一份角色报告。
- 触发角色没有对应交付物时，直接判 `不通过`，回写“未上传交付物”，不生成报告，也不产生 `未检查` 结论。
- 已提供附件但内容无法归入触发角色时，判 `不通过`，不得静默改归到其他角色。
- 不存在新附件、事件重复或相同材料已处理时，不重复运行、不重复评论、不重复上传报告。
- 状态迁移事件中的 `attachment_ids` 可以为空。此时接入方应提供该 Issue 当前有效附件列表；Skill 只处理该角色此前未按同一附件哈希检查过的材料。Issue 中根本没有该角色附件时才按“未上传交付物”判 `不通过`。

去重键为：

```text
mode + role + event_id
role + attachment_id + SHA-256 + PRD版本或PRD哈希
```

`event_id` 用于阻断同一事件重放；附件键用于阻断同一材料因状态迁移、重复回调或自动化重试而再次检查。附件内容变化、附件 ID 变化或 PRD 版本／哈希变化时允许重新检查。

Jira 模式按以下顺序确定事实源：

1. RD、QA 从 `issue_key` 对应主 Issue 读取附件；UI 从 `parent_issue_key` 对应主 Issue 读取 PRD 和产品交付原型，从 `issue_key` 对应子任务读取被检查附件。
2. PRD 候选文件名必须以前缀 `{{需求名称}}_PRD_DELIVERY` 开头且扩展名为 `.md`。仅一份时直接使用；多份时按文件名中的语义版本取最高版本，同版本取最新上传。多份均无可解析版本，或最高版本仍无法唯一确定时，回写“检查未完成”，不产生 `通过／不通过` 结论。
3. 产品交付原型按前缀 `{{需求名称}}_Prototype` 且扩展名为 `.html` 匹配，多份时取最新上传；没有匹配时 UI 按一致性模式检查，并写明缺少产品交付原型。
4. PRD 缺失、不可读取或版本无法唯一确定时，回写“检查未完成”，不生成 PDCA 报告。

### 2.2 必需输入

- 手工模式：指定版本 PRD 的精确文件和版本，以及至少一份待检查交付物。
- Jira 模式：2.1.2 规定的触发上下文、指定版本 PRD，以及事件角色对应的待检查附件。角色附件为空也是有效触发，但结论为 `不通过`，不生成报告。

### 2.3 可选输入

- 产品交付原型（UI 类判定基准；缺省时按一致性模式处理）。
- 技术方案设计 Checklist、提测准入 Checklist 等现有门禁依据。
- UI 规范或组件库规范。
- 评审结论、决策记录。
- 其他已授权正式证据。

输入中未提供的材料不得推定存在；缺失会改变判定结论时，说明缺什么，并按本章口径处理，不自行补齐。

### 2.4 事实源边界

```text
PRD-DELIVERY：唯一业务事实源
产品交付原型：已确认需求的 UI 类判定基准，不得单独定义新的业务事实
交付物：被检查对象，不得反向定义产品事实
现有门禁 Checklist：门禁参照，不复制、不改写
```

- 交付物与 PRD 冲突时以 PRD 为准。
- PRD 是唯一业务事实源；产品交付原型只在 PRD 已确认的 UI 表达范围内作为基线。原型出现 PRD 未定义的新业务事实时，不把它当作需求依据；PRD 自身质量由上游 Review 负责，不在本检查项内。
- PRD 未定义的维度不列为本轮必查项，不影响该类结论，也不追加问题条目。

### 2.5 「复用既有能力」的判别

判据是 PRD 有没有对该项能力提出本次要做的改变，不是交付物有没有举证既有系统的实现。

| PRD 的写法 | 判定 |
|---|---|
| 提出本次要做的改变（新增或修改的控件、状态、文案、阻断或禁用行为、字段或规则） | 交付物必须承接，**不认「复用既有能力」作为豁免** |
| 只提到既有能力、未提出本次改变（如「写入操作日志」「沿用既有权限」「不新增独立入口」） | 不列为本轮必查项，**不进报告** |
| 提出改变但由其他产物承接（如改审核页，本轮只交流程构建原型） | 计入附录「未检查项」，注明承接产物 |

- 不要求交付方举证本轮交付物范围外既有系统的内部实现。
- 该项能力是否属于本次范围，以 PRD 正文为准，不由交付物自行声明或缩减。

## 3. 交付物自动分组

收到输入后先识别并分组，每组独立出结论。类别按**交付物内容**判定，文件名与来源标签只作提示：

| 分组 | 内容特征 | 检查重点 |
|---|---|---|
| 开发交付物 | 架构与分层说明、接口与数据设计、字段与表结构、时序与调用链路、改动点清单、异常码与降级方案 | 是否完整承接 PRD 的目标、范围、功能、规则、状态、权限、异常、正式文案与 AC |
| 测试交付物 | 测试方案、测试用例（前置条件、操作步骤、预期结果）、测试矩阵、覆盖统计、回归清单 | AC 覆盖是否完整，正反向、边界、异常、权限、状态与回归是否覆盖 |
| UI 交付物 | 页面结构、组件与交互稿、可运行的界面原型（HTML／设计稿）、界面状态与跳转 | 交互能否闭环、是否达到 PRD 的需求目的、是否丢失基线已有业务能力 |

分组规则：

- 内容特征与文件名提示冲突时，以内容为准，并在报告中说明判定依据。
- 一份交付物同时具备多类特征时，按主要用途归入一类，并在报告中注明。
- 内容特征不足以判定类别时，写「无法判定类别」并列入未检查项，说明缺什么，不强行归类。
- 手工模式按内容自动分组；Jira 模式只检查 `trigger_type` 指定角色。Jira 附件内容无法归入该角色时，判该角色 `不通过`，不自动改查其他角色。

## 4. 结论口径

每组交付物输出一个结论，取值固定为两个：

| 结论 | 判定条件 |
|---|---|
| `通过` | 该类全部必查项均已核对且未发现不通过项；记录项与无关项目不影响结论 |
| `不通过` | 命中任一不通过条件，或必查项缺少可判定证据 |

判定纪律：

- 只有 `通过` / `不通过` 两种结论。不设置「有条件通过」「基本一致」「需确认」等中间档。
- Jira 的 `检查未完成` 是接入或取证失败时的执行状态，不是第三种 PDCA 结论，也不得参与通过率统计。
- 手工模式中未被要求检查的类别在「未检查项」中写明，不产生结论。
- Jira 模式中事件指定角色没有交付物时，直接判 `不通过`；该场景只回写评论，不生成报告。
- 任一必查项缺少可核验证据、存在事实冲突或无法唯一判断时，一律判 `不通过`，整改方为交付方；交付物声称「已确认」但无依据的，同样判 `不通过`。
- 结论必须可追溯到 PRD 稳定 ID 或交付物明确章节，禁止只写「整体合理」。
- **多落点规则逐落点判定**：同一规则落在多个落点时（如页面级保存、抽屉内保存、发布），逐个落点判定，不得以其中一处通过代表整条通过。
- 判 `通过` 必须给出**证据定位**（页面 + 控件 + 触发条件），不得写「已实现」「有相关逻辑」等无法复核的表述。
- 每次执行全部适用必查项，不抽样、不按数量省略，不使用总分或平均分覆盖阻断项。
- 报告与 Jira 评论的第一屏先给结论；通过项不逐条展开，完整依据留在报告。
- 记录项（UI 本职改动、门禁参照差异、外部约束）不计入结论。

## 5. 检查规则

### 5.1 开发交付物

**必查项**

| 序号 | 必查项 | 通过边界 |
|---|---|---|
| 1 | 范围承接 | PRD 本期范围内每个 FR／BR／IR 都有对应改动点；未新增 PRD 未写的业务行为 |
| 2 | 功能承接 | 每个 FR 写明实现路径：模块、改动位置、入口 |
| 3 | 规则承接 | BR 的判定条件、优先级、互斥、例外可对应到实现描述 |
| 4 | 交互承接 | IR 的跨页面联动、多状态与权限差异、取消与返回已承接 |
| 5 | 字段与数据 | 字段、枚举、默认值、业务长度／格式／范围、数据口径与 PRD 一致 |
| 6 | 状态与权限 | 状态流转、角色权限、只读／历史版本／无权限表现与 PRD 一致 |
| 7 | 异常与恢复 | 用户可见失败反馈、降级、恢复、失败落点与 PRD 一致 |
| 8 | 正式用户文案 | PRD 已确认的正式文案与提示未被改写 |
| 9 | AC 承接 | 关键及 P0／P1 AC 有技术承接与可核对的验证入口 |
| 10 | 版本对齐 | 写明所依据的 PRD 版本；与当前 PRD 不一致时说明差异，并以当前 PRD 判定 |

**不通过范围**

- 任一必查项缺失或与 PRD 不一致。
- PRD 已写范围在方案中没有改动点，也未说明承接方式。
- 出现 PRD 未写的业务规则、字段、枚举、正式文案或入口。
- 以「当前系统不具备该能力」「运行时没有该链路」「本期不支持」为由缩减 PRD 已确认范围（按 5.4 处理）。
- 声称「本期按已确认方案执行」「已定口径」「按评审决定」但无法对应 PRD 版本、决策记录或产品书面确认。
- 未写明所依据的 PRD 版本，或与当前 PRD 不一致且未说明差异，导致无法判断以哪个版本为准。

**记录项（不判）**

- 分层、模块划分、缓存、消息、部署、性能实现、组件选型。
- 代码、接口参数、数据库结构等技术内容本身（只核对它们是否与 PRD 的业务语义一致，不评价技术方案优劣）。

### 5.2 测试交付物

**必查项**

| 序号 | 必查项 | 通过边界 |
|---|---|---|
| 1 | 测试方案 | 已提供；范围覆盖本次 PRD 范围与版本变更 |
| 2 | 测试用例 | 已提供；用例与 AC／FR 的对应关系可追溯 |
| 3 | AC 覆盖 | PRD 全量 AC 逐条列出覆盖结果；关键及 P0／P1 AC 必须有对应用例 |
| 4 | 场景维度 | 覆盖正向、反向、边界、异常、权限、状态与重复提交等与 PRD 相关维度 |
| 5 | 回归范围 | 版本变更后的回归清单明确 |
| 6 | 环境与数据 | 测试环境、账号权限、必要数据准备已说明 |
| 7 | 未覆盖项 | 未覆盖的 AC 或场景逐条标记并写明原因 |
| 8 | 版本对齐 | 写明所依据的 PRD 版本；与当前 PRD 不一致时说明差异，并以当前 PRD 判定 |

**AC 覆盖矩阵**

```text
AC 编号 | AC 描述摘要 | 是否有对应用例 | 用例编号/章节 | 覆盖结论 | 缺口说明
```

**不通过范围**

- 缺测试方案或缺测试用例。
- PRD 的 AC 未逐条列出覆盖结果，或归并成一句概述。
- 关键及 P0／P1 AC 无对应用例。
- 未覆盖项未标记或未写明原因。
- 编造覆盖率分母，或用测试执行等级代替 AC 优先级。
- 测试用例把未确认的新业务行为写成第二需求事实源。
- 用例的预期结果与 PRD 冲突。
- 未写明所依据的 PRD 版本，或与当前 PRD 不一致且未说明差异，导致无法判断以哪个版本为准。

**记录项（不判）**

- 测试工具选型、自动化实现方式、用例书写风格。
- 测试环境的具体搭建方式（只核对是否说明、是否可用）。

### 5.3 UI 交付物

按是否提供产品交付原型分两种模式：

- **差异模式**（有产品交付原型）：先输出精修前后改动清单，只列「改了什么」，再按必查项判定。
- **一致性模式**（无产品交付原型）：只做必查项判定，并写明「缺少产品交付原型，未做差异比对」；不因缺基线判不通过。

**必查项**

| 序号 | 必查项 | 通过边界 |
|---|---|---|
| 1 | 需求达成 | PRD 已定义的功能、入口、页面结构在交付物中都有体现 |
| 2 | 交互闭环 | 主流程可走通：进入 → 操作 → 反馈 → 落点；取消／返回／撤销可用；失败有恢复路径 |
| 3 | 规则体现 | PRD 已定义的业务约束在界面上可见：必填、范围、选择范围、字段联动 |
| 4 | 正式文案 | PRD 已确认的正式业务文案一致 |
| 5 | 场景承载 | PRD 声明需原型承载的模拟场景已复现 |
| 6 | 相对基线 | 差异模式下未丢失产品交付原型已实现的业务能力或入口 |
| 7 | 阻断与禁用断言 | PRD 中「不可提交／不可保存／不可发布／禁用／显示但禁用／隐藏／不展示／阻断／必须先处理」类断言，逐条核到**具体控件 + 触发条件 + 实际表现**；多落点逐落点核对；负向条件确实被拦 |
| 8 | 版本对齐 | 写明所依据的 PRD 版本；与当前 PRD 不一致时说明差异，并以当前 PRD 判定 |

**阻断与禁用断言核对要求**

- 从 PRD 正文、权限或状态矩阵、FR／BR／IR／AC 中抽出全部阻断与禁用类断言，逐条列出原型落点。
- 一条规则若落在多个落点（如页面级保存、抽屉内保存、发布按钮），每个落点单独核对，不得合并为一条结论。
- 必须做**负向验证**：构造 PRD 描述的不满足条件，确认实际被拦（控件为禁用态，或点击后不提交）。
- 核对清单是本次检查的工作产物，写入报告的必查项核对表；不写入原型 HTML，也不新增场景 ID。

**不通过范围**

- PRD 已定义的功能、入口、页面结构未体现。
- 主流程走不通、链路断裂，或取消／返回／撤销缺失导致无法完成操作。
- PRD 已定义的业务约束在界面上不可见或表现相反。
- 正式业务文案与 PRD 不一致。
- PRD 声明需原型承载的模拟场景未复现。
- 差异模式下丢失基线已有的业务能力或入口。
- 出现 PRD 未写的业务功能、规则或入口。
- PRD 写明的阻断或禁用断言未落到对应控件、触发条件或实际表现。
- 同一规则涉及多个落点，只覆盖其中一处即记为通过。
- 仅凭存在校验代码或提示文案判定覆盖，未给出控件与触发条件的证据定位。
- 未写明所依据的 PRD 版本，或与当前 PRD 不一致且未说明差异，导致无法判断以哪个版本为准。

**记录项（不判）**

- 视觉样式：配色、间距、字号、图标、组件外观、圆角、分隔线、布局宽度。
- 标准前端表现：校验触发位置、必填星号、计数器、加载态、防重复点击、组件选择、错误提示呈现方式。
- 交互呈现时机与反馈方式：悬停／聚焦才显示的操作入口、控件状态的表达方式。
- UI 补充信息：为弥补产品交付原型缺失而新增的界面信息（如页签计数、状态标记、空态文案）。
- 界面文案的措辞微调（不承载业务语义时）。

**明确不查**

- 状态与权限：角色权限差异、只读与无权限表现在 UI 类不检查，该维度由开发交付物必查项第 6 条承接。
- 产品交付原型自身未表达的界面状态，不作为不通过依据；交付物自行补充的状态只作记录。
- PRD 只提到、未提出本次改变的既有能力，按第 2.5 节处理，不进报告。

### 5.4 交付物缩减 PRD 范围时的处理

交付物以「当前系统不具备该能力」「运行时没有该链路」「本期不支持」等理由缩减 PRD 已确认范围时：

1. 该论断只能标记为**待证事实**，不得作为结论依据。
2. 判 `不通过`，默认口径为 PRD 原文。
3. 整改要求只有一条：补齐实现，承接 PRD 原范围。
4. 不得在 PDCA 报告中直接建议删除或调整 PRD 中的要求。

### 5.5 交付物声称已确认时的处理

交付物出现「本期按已确认方案执行」「已定口径」「按评审决定」等表述时：

- 必须能对应到 PRD 版本或产品书面确认。
- 无可核验依据时判 `不通过`，整改方为交付方。
- 报告需写明缺少哪类依据，以及由谁补充。

### 5.6 范围与覆盖缺口

- PRD 已写的范围，交付物未落到改动点或验证场景，判 `不通过`。
- 交付物改动了 PRD 未写的业务事实，判 `不通过`，整改方向为删除越界内容或由产品另行补充需求。
- 必查项本身无法核对（如交付物格式不可读、附件损坏），判 `不通过` 并在整改要求中写明需要补齐什么。
- 「复用既有能力」不作豁免：PRD 提出本次改变的，交付物必须承接；PRD 未提出改变的，不列必查项、不进报告（见 2.5）。

## 6. 报告格式

报告写入当前需求交付目录，不新增子目录。

- 手工模式固定为 `{{需求名称}}_PDCA.md`。同一需求重复检查时更新同一份报告，历史检查写入报告内部变更记录。
- Jira 模式固定为 `{{需求名称}}_{{RD|QA|UI}}_{{YYYYMMDD}}_{{NN}}_PDCA.md`。`NN` 为该需求、角色和日期下的两位序号，从 `01` 递增；同一轮多附件只生成一份角色报告。
- Jira 模式只有存在可检查附件时才生成报告。没有交付物时只回写不通过评论，不创建空报告。
- Jira 报告是当轮检查快照，不覆盖上一轮；历史由 Jira 附件序列保留。同一 Issue 的同角色检查应串行处理，避免序号冲突。

报告顶部只保留最小 front-matter：

```yaml
---
artifact_type: pdca
mode: "<manual|jira>"
source_prd: "<PRD 文件名>"
checked_deliverable: "<本轮被检查交付物文件名>"
generated_at: <检查日期>
jira_issue: "<Jira Issue Key；手工模式省略>"
jira_parent_issue: "<UI 父需求 Key；其他情况省略>"
jira_event_id: "<Jira 事件 ID；手工模式省略>"
trigger_type: "<Jira 触发类型；手工模式省略>"
source_prd_version: "<PRD 版本>"
report_name: "<报告文件名>"
---
```

### 6.1 报告结构

手工报告保留以下完整结构。Jira 角色报告只保留本轮触发角色对应的检查章节，其他角色章节不生成；附录仍需记录触发事件、输入附件、必查项核对表、AC 追溯和变更记录。这样既保持单份角色报告完整，也不把未触发的其他角色伪装成“未检查”。

```markdown
一、PDCA 结论
    1. 结论总览
    2. 结论摘要
二、开发侧方案检查结果与问题项
    1. 结论
    2. 不通过／问题项
三、UI 侧原型检查结果与问题项
    1. 结论
    2. 不通过／问题项
    3. 精修前后改动清单（只列改了什么）
四、测试侧方案／用例检查结果与问题项
    1. 结论
    2. 不通过／问题项
五、附录
    1. 上下文材料输入
    2. 必查项核对表
    3. AC 追溯明细
    4. 未检查项
    5. 变更记录
```

### 6.2 色标

结论与核对表结果列统一使用以下符号，含义只在本节定义：

| 符号 | 含义 |
|---|---|
| 🟢 | 通过 |
| 🔴 | 不通过 |
| ⚪ | 未检查 |

关键结论与责任方使用**加粗**。

### 6.3 结论总览与结论摘要

结论总览：一行总结论，加一张每类交付物一行的表。

```text
总结论：<类别> 🔴 不通过（其他类别：⚪ 未检查）

| 交付物 | 类别 | 结论 | 不通过项数 |
```

结论摘要：说明为什么，以及本轮影响面（谁要做什么）。

```text
为什么：<一句话说明触发不通过的必查项与事实>
PRD 依据：<FR／BR／IR／AC 稳定编号>
本轮影响面：<责任方> <要做什么>
```

### 6.4 问题项卡片

问题项按设计侧报告的可读顺序输出，每项一张卡：

```text
#### 🔴 <编号> <一句话标题>

**影响**
<现状，以及不修的后果>

**怎么改**
**<责任方>** 整改要求

**完成标准**
<可判定的关闭条件>

**PRD 要求** ｜ **交付物实际**

| PRD 要求 | 交付物实际 |
|---|---|
| <原文摘录> — 出处：<FR／BR／IR／AC 编号或小节> | <实际表现> — 出处：<文件:行号或明确章节> |
```

- 编号按类别加前缀：开发 `D-`、测试 `T-`、UI `U-`。
- `责任方` 只写交付方（研发／测试／UI）；**产品不作为交付物问题的责任方**。
- 不引入严重度分档，问题项只有「不通过」一种。

### 6.5 必查项核对表

每类交付物给出一张必查项核对表，逐项标注结果：

```text
| 编号 | 必查项 | 结果 | 说明 |
```

结果取值：`🟢 通过` / `🔴 不通过` / `记录` / `⚪ 未检查`。

### 6.6 AC 追溯明细

```text
| AC 编号 | AC 描述摘要 | 是否应在本载体承载 | 承载位置 | 证据定位与判定方式 | 覆盖结论 | 缺口说明 |
```

`证据定位与判定方式` 必须写明核对了哪个页面、哪个控件、什么触发条件，或说明该 AC 由哪个产物承接。

### 6.7 报告纪律

- 只引用当前正式 PRD、产品交付原型和已授权交付物。
- 不包含 Review 过程、Agent 推理过程或未经证据支持的事实。
- 不评价 PRD 自身质量，不产出 PRD 缺口清单。
- 手工模式未要求检查的类别在「未检查项」中明确写出，不生成覆盖率或结论；Jira 模式触发角色没有交付物时不生成报告。
- 记录项单独成节，不写入问题清单，不计入结论。
- 报告只写问题与结论，不写检查执行过程。
- 门禁参照只作为辅助说明，不写成正式门禁结论。
- 「怎么改 + 完成标准」即 Act 闭环项，不另设 Act 章节。
- AC 追溯明细、上下文材料输入等长表置于附录。
- Jira 角色报告保留本章结构与完整明细，不因评论精简而删减报告中的问题、核对表和 AC 追溯。
- Jira 报告不承载 Webhook 请求日志、鉴权信息、重试过程或平台执行日志。

## 7. 对话输出格式

### 7.1 手工模式

对话只输出以下内容，控制在可一屏读完：

1. 结论总览（每份交付物一行，含结论与不通过项数）。
2. 不通过项（每项一条，写明事实、PRD 依据与整改要求）。
3. 记录项摘要（一句话概述，不逐条展开）。
4. 未检查项（未提供的交付物）。
5. 报告路径。

输出纪律：

- 使用 `1. / 2. / 3.` 分条，书面化表达，先结论后依据。
- 先给结论与为什么，再列依据与整改要求。
- 不使用口语化叙述、过程描述和重复铺垫。
- 完整明细写入报告，对话不复述报告全文。

### 7.2 Jira 评论

Jira 评论只回写本轮检查所需的最小结论，不复制报告正文。评论固定包含角色、结论、检查附件、PRD 版本、全部不通过项及依据、报告文件名；不写必查项核对表、AC 追溯、整改步骤、检查过程或记录项展开。

有交付物时使用以下格式：

```text
PDCA｜<RD|QA|UI>｜<通过|不通过>
检查附件：<附件名 1、附件名 2>
PRD：<PRD 文件名>（<版本>）
不通过项：
- <D/T/U-编号> <问题标题>｜PRD依据：<稳定 ID 或章节>｜交付物依据：<文件:行号或明确章节>
报告：<角色报告文件名>
```

- 通过时写 `不通过项：无`，不展开已通过的必查项。
- 不通过时逐条列完全部不通过项，每项只占一行；不得截断、只列前 3 项或归并成概述。
- 评论不写“怎么改”“完成标准”、门禁判断或长篇说明，完整内容只留报告。

触发角色没有交付物时使用以下格式，且不生成报告：

```text
PDCA｜<RD|QA|UI>
未上传交付物，检查结论：不通过。应补：<技术方案|测试方案或用例|UI 精修原型>。
影响：本轮无法核对产品定义与交付结果。
后续：补齐附件后重新触发或人工补检；本轮不生成报告。
```

上述评论只描述缺失事实与整改方向，不写具体检查项核对表或模拟问题，也不生成 `未检查` 报告。

PRD 缺失、不可读取或无法唯一确定版本，或检查执行中断时使用以下格式，不产生 `通过／不通过` 结论：

```text
PDCA｜<RD|QA|UI>｜检查未完成
原因：<缺失或失败事实>
后续：<补齐材料或由接入方重试>
```

重复事件或已处理过的相同附件不新增评论。Jira 评论写入失败时，由 Jira 接入方按自身重试策略处理，Skill 不把未成功回写视为已完成。

Jira 模式对接入方的输出契约为：

```text
mode: jira
role: RD | QA | UI
result: pass | fail | not_completed
comment_markdown: 按 7.2 生成的评论正文
report_path: 存在交付物且检查完成时为角色报告路径；否则为空
report_filename: 同上对应的文件名；否则为空
dedupe_key: 本轮事件与附件对应的去重键
```

接入方负责按该契约写评论和上传报告；Skill 不直接调用 Jira 写接口。

## 8. 与其他产物的关系

- PRD-DELIVERY：唯一业务事实源。
- 产品交付原型：UI 类判定基准。
- REVIEW_SKILLS：检查 PRD 与产品侧产物质量；本母版检查协作方交付物与 PRD 的一致性，两者职责不同。
- Overview、DIAGRAM、Prototype、LLM_PROMPTS：产品侧下游产物，不在本母版检查范围内。
- 技术方案设计 Checklist、提测准入 Checklist：现有门禁依据，只引用不改写。
- Jira：承载状态／附件事件触发、简明结论评论和 PDCA 报告附件。接入方负责平台 API、鉴权、重试与幂等；本母版不修改 Jira 状态、标签或字段。

任何一方发现产品语义缺口时，统一回到 PRD 修改、升版并重新 Review，再由本母版重新检查受影响交付物。

## 9. 输出质量检查

### 9.1 Jira 触发验收矩阵

| 场景 | 期望结果 |
|---|---|
| `RD_TECH_PLAN_READY` 且存在未处理技术方案 | 检查 RD 附件，回写简明评论，生成一份 RD 角色报告 |
| 任一角色触发但 Issue 中没有对应交付物 | 回写“未上传交付物，检查结论：不通过”，不生成报告 |
| `QA_DELIVERABLE_READY` 同轮有测试方案和测试用例 | 合并为一次 QA 检查，生成一份 QA 角色报告 |
| 同一 `event_id` 重放 | 不重复检查、不重复评论、不重复上传报告 |
| 同一附件 ID 内容变化，或 PRD 版本／哈希变化 | 允许复检并生成新快照 |
| PRD 缺失、不可读取或最高版本无法唯一确定 | 回写“检查未完成”，不产生通过／不通过结论，不生成报告 |
| UI 子任务标题命中 `UI精调`／`UI调优` 且有附件 | 使用子任务附件，从父 Issue 读取 PRD 与产品原型并检查 |
| UI 子任务标题不命中关键词 | 不触发 UI PDCA |
| 检查存在多项不通过 | Jira 评论逐项列完全部问题及两类依据，不粘贴核对表或整改步骤 |
| 同一角色一天内多次复检 | 报告序号依次递增，不覆盖历史快照 |

- [ ] 是否以指定版本 PRD 为唯一业务事实源，并只在 PRD 已确认范围使用产品交付原型作为 UI 基线。
- [ ] 是否按开发、测试、UI 内容特征自动分组，并对每组独立给出结论。
- [ ] Jira 模式是否只检查触发类型指定的角色，并把同一角色本轮多个附件合并为一份报告。
- [ ] Jira 模式没有对应交付物时，是否判 `不通过`、只输出规定评论且不生成空报告。
- [ ] Jira 模式是否按 `event_id` 与附件哈希去重，并对附件替换或 PRD 变化允许复检。
- [ ] Jira 评论是否只写角色、结论、附件、PRD 版本、全部不通过项及依据和报告文件名。
- [ ] 是否按每类必查项逐项核对，并给出核对表。
- [ ] PDCA 结论是否只用 `通过` / `不通过`；手工模式未要求检查的类别是否写「未检查」，Jira `检查未完成` 是否只作为执行状态。
- [ ] 手工报告是否按第 6.1 节的五章结构输出；Jira 角色报告是否只保留触发角色章节，且结论均放在最前。
- [ ] 色标是否统一使用 🟢 / 🔴 / ⚪，且未另造严重度分档。
- [ ] 问题项是否按 影响 → 怎么改 → 完成标准 → PRD 要求 vs 交付物实际 的顺序成卡。
- [ ] 问题编号是否按 `D-` / `T-` / `U-` 前缀归类，可追溯到具体必查项。
- [ ] 是否抽出了 PRD 全部阻断与禁用类断言，并**逐落点**核对。
- [ ] 是否对阻断与禁用断言做了**负向验证**，而不是只走正向路径。
- [ ] 判 `通过` 的项是否给出页面 + 控件 + 触发条件的证据定位，没有写「已实现」「有相关逻辑」。
- [ ] 是否按第 2.5 节处理既有能力：PRD 未提出改变的是否未进报告。
- [ ] 测试检查是否逐条列出 AC 覆盖结果和未承接项，没有归并成一句概述或编造分母。
- [ ] UI 检查是否先出精修前后改动清单；缺少产品交付原型时是否明确写出限制。
- [ ] 是否把 UI 本职（视觉、标准前端表现、交互呈现时机、UI 补充信息）判成不通过。
- [ ] 是否把「状态与权限」写进 UI 类必查项。
- [ ] 下游以技术限制收缩 PRD 范围时，是否标记为待证事实并判不通过，整改要求为补齐实现。
- [ ] 交付物声称「已确认」但缺少依据时，是否判 `不通过`。
- [ ] 是否评价了 PRD 自身质量，或把 PRD 缺口写成协作方的问题。
- [ ] 不通过项的责任方是否只写交付方，未把产品列为交付物问题的责任方。
- [ ] 手工模式未要求检查的类别是否明确写「未检查」；Jira 模式没有对应交付物时是否判 `不通过`，没有生成空报告或虚假覆盖率。
- [ ] 记录项是否单独成节、未计入结论。
- [ ] 是否写明了交付物所依据的 PRD 版本，并在版本不一致时说明差异。
- [ ] 手工模式是否更新 `{{需求名称}}_PDCA.md` 并写入变更记录。
- [ ] 手工模式是否维护 `{{需求名称}}_PDCA.md`；Jira 模式是否按 `{{需求名称}}_{{RD|QA|UI}}_{{YYYYMMDD}}_{{NN}}_PDCA.md` 生成独立角色报告。
- [ ] Jira 角色报告是否只保留触发角色的完整检查章节，并保留同轮全部输入附件和事实依据。
- [ ] 对话输出是否分条书面化、可一屏读完，完整明细是否留在报告中。
- [ ] 是否没有替代 G2、G3 或 UI 正式验收，也没有修改 PRD、交付物或单据状态。

## 10. 禁止事项

- 不要用交付物替代 PRD 作为业务事实源。
- 不要用下游交付物的技术论断直接改写或建议改写 PRD 范围。
- 不要评价 PRD 或产品交付原型自身质量，不要产出 PRD 缺口清单，不要因 PRD 缺口判协作方不通过。
- 不要把交付物自称的「已确认口径」当作产品确认。
- 不要输出「需确认」「有条件通过」「基本一致」等中间结论。
- 不要把 PRD 未提出改变的既有能力列为必查项或问题项，也不要因此判不通过。
- 不要只在一处落点实现阻断就判整条规则覆盖。
- 不要用点击后提示替代 PRD 明确要求的禁用态。
- 不要在交付物问题上把产品列为责任方。
- 不要因视觉样式、标准前端表现、交互呈现时机或 UI 补充信息判 `不通过`。
- 不要在 UI 类检查角色权限差异、只读与无权限表现。
- 不要对纯技术架构、组件选型、性能实现或测试工具作产品侧阻断判断。
- 不要要求产品经理填写或判定代码、接口参数、数据库结构等技术内容。
- 不要把 AC 追溯缺口归并成一句概述而不逐条列出。
- 不要编造测试覆盖率分母，也不要用缺少测试输入生成通过结论。
- 不要在没有产品交付原型时虚构精修前后差异。
- 不要输出评分、Top N 或「整体合理、建议优化」等无依据结论。
- 不要在对话中复述报告全文或输出长篇过程描述。
- 不要在手工模式创建按版本或日期拆分的多份 PDCA 文件。
- 不要把 PDCA 结论写成 G2、G3 或 UI 正式验收结论，也不要修改单据状态。
- 不要在没有对应交付物时生成空报告、伪造 `未检查` 结论，或把缺失附件写成 `检查未完成`。
- 不要在 Jira 评论中粘贴必查项核对表、AC 追溯明细、完整整改步骤或执行过程。
- 不要把 Jira 状态迁移、标签、字段或工作流作为 PDCA 的正式门禁结论。
- 不要在 Jira 模式下自动检查未触发的其他角色，也不要把不同角色合并成一份报告。
