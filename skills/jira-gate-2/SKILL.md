# Jira G2 技术方案准出检查

用户给一个 Jira 需求链接，你自己打开它，读完描述、附件、关联需求、历史评论，以及技术方案与 PRD，按《技术方案准出 Checklist》逐项判定，给出**通过 / 退回补充**结论；把结论与检查项清单写进这张单子的评论区。

## 交付物

**交付物只有一个落点：Jira 评论。**

1. Jira 评论：结论摘要 + 逐项打标记的检查项清单（`(/)` 满足、`(x)` 不满足）；通过与否用同一套结构（模板见本文档「输出模板」节）。
2. 对话里的摘要：单据类型 + 通过/退回补充 + 关键阻断项 + 状态流转结果，供用户即时看到结果。

**状态流转**（见 §9）：

- 结论为**通过**：不流转状态，保持当前状态，允许进入 OpenSpec `propose` 与开发实施。
- 结论为**退回补充**：把需求单流转到「开发设计中」，并在评论里 `@` 流转人。

**不要生成报告类文档（Markdown/HTML/Word 等）作为交付物，也不上传附件。** 结论只进 Jira 评论区；本地仅允许在临时目录存放附件与解析中间文件（如 `<工作目录>/work/jira-gate-2/<KEY>/attachments/`），这些中间文件不是交付物，也不要放进 outputs 目录。

**这些中间产物在交付完成后要清掉**（见 §11）：附件与解压产物按任务累积，大方案解压后有几十 MB，留在工作区只会占空间。清理只在**全部交付动作成功之后**执行；交付失败的场景保留现场，便于排查。

## 判定依据

检查项、等级（`MUST` / `CONDITIONAL` / `SHOULD` / `OBSERVE`）与判定原则以 [references/checklist.md](references/checklist.md)（技术方案准出 Checklist）为准。**先读它再开始判定**，不要凭印象发明标准。

核心口径：

- **入口状态参考：开发设计中；通过不改变状态，退回补充时流转到「开发设计中」。**
- 每次都执行全部 **10 项 `MUST`**（G2-M01 ~ G2-M10）与所有**命中的 `CONDITIONAL`**（G2-C01 ~ G2-C11），不抽样、不使用总分或平均分。
- 单项结果只允许「满足 / 不满足 / N/A」；证据不足、章节冲突或无法唯一判断按**不满足**处理。
- `N/A` 只适用于未命中的场景项，并必须记录不适用依据。
- 任意适用 `MUST` 或命中 `CONDITIONAL` 不满足，结论只能是**退回补充**，状态流转到「开发设计中」，OpenSpec `propose` 禁止执行。
- G2 只判断技术方案是否完整承接已通过 G1 的需求、技术设计是否可落地；**不检查代码是否已经实现**，也不要求 OpenSpec tasks 或 Jira 执行子任务在准出前已经生成。
- 判定要过「**开发接管测试**」：两名合格开发仅依据 PRD、原型、Jira 单和本技术方案，如果能形成不同且都合理的实现路径，并导致不同的外部行为、接口契约、状态、数据含义、权限、失败结果、测试结论或发布方式，则判定方案不可接管，必须退回。
- 前端与后端采用同一标准；纯后端需求必须说明前端不适用及依据。

## 执行步骤

### 0. 运行环境适配（先读这一节）

本技能有两种运行环境，**取数通道不同，判定标准完全相同**：

- **桌面 Codex（带 `node_repl` 工具）**：按下面「通道 A」的 `node_repl` 片段执行。
- **服务器容器 / `codex exec`（没有 `node_repl`）**：用 shell 直接执行技能自带命令行入口 `scripts/jira-cli.mjs`（能力与 `node_repl` 通道一致）：

  ```bash
  # 令牌与连通性自检；令牌来自 --token、JIRA_TOKEN 环境变量或技能目录下的 .jira-token
  node <技能目录>/scripts/jira-cli.mjs selftest
  # 强制类型预检：只有类型为「故事」才继续（见 §1）
  node <技能目录>/scripts/jira-cli.mjs precheck <KEY|URL>
  # 读取需求单并输出紧凑 Markdown 摘要（判定依据）
  node <技能目录>/scripts/jira-cli.mjs get <KEY|URL>
  # 下载附件到工作目录
  node <技能目录>/scripts/jira-cli.mjs attachments <KEY|URL> work/jira-gate-2/<KEY>/attachments

  # 写入评论：正文先落文件再提交，避免多行标记转义问题
  node <技能目录>/scripts/jira-cli.mjs comment <KEY|URL> --file work/jira-gate-2/<KEY>/comment.txt

  # --- 交付顺序：评论 → 门禁字段 → 流转（仅退回补充，见 §9）---
  node <技能目录>/scripts/jira-cli.mjs flow-owner <KEY|URL>
  node <技能目录>/scripts/jira-cli.mjs transition <KEY|URL> --to 开发设计中
  ```

  附件解析仍走 Python：`python <技能目录>/scripts/extract.py <附件目录> --out <附件目录>/../attachments.txt`。

  自检中「校验令牌」步骤返回 401 只表示该令牌无权访问 `/myself` 账户接口，**不等于令牌失效**：只要「访问 Jira」步骤成功、且 `get <KEY|URL>` 能取到需求单，就继续按流程完成检查。

  在该环境中不要尝试调用 `node_repl`，也不要因为缺少桌面工具而降低判定标准。

### 1. 单据类型预检（强制，先做）

**只处理类型为「故事」的 Jira 单子。** 在读取附件、写评论、回写字段或流转之前，先执行：

```bash
node <技能目录>/scripts/jira-cli.mjs precheck <KEY|URL>
```

返回示例：

```json
{
  "ok": true,
  "key": "CALL-1446",
  "issueType": "故事",
  "expected": "故事",
  "supported": true,
  "status": "开发设计中",
  "summary": "..."
}
```

- `supported: true`（类型为 `故事`；英文站点返回 `Story` 时视为同一种类型）→ 继续 §2。
- `supported: false` 或类型为空 → **立即停止**：不写评论、不回写门禁字段、不流转状态，也不清理（本次没有产生中间产物）。只在对话里说明「该单类型为 X，不是『故事』，按规则跳过，未对 Jira 做任何写操作」。
- 不要用概要、标签、模块或描述去猜测类型；只认 Jira 的 `issuetype` 字段。

### 2. 解析单号

`parseIssueKey()` 支持 `/browse/KEY`、`?selectedIssue=KEY`、jql 链接、纯 `KEY` 四种输入。

### 3. 取数：通道 A —— Jira REST（首选）

在 `node_repl` 工具里执行下面的代码。**注意本机沙箱限制**：PowerShell 无法建立 TLS 连接，`node_repl` 是唯一能访问 Jira 的通道；`node_repl` 内没有 `process`、不支持静态 import，所以脚本必须用 `await import()` 动态加载，且**不要在 node_repl 顶层引用 `process`**。

```javascript
// <SKILL_DIR> = 本 SKILL.md 所在目录的绝对路径（如 ~/.codex/skills/jira-gate-2 或容器内 /data/skills/jira-gate-2）
const j = await import("file:///<SKILL_DIR>/scripts/jira.mjs");
const st = await j.selftest();              // 先自检：令牌、连通性、账号
nodeRepl.write(JSON.stringify(st, null, 1));
```

自检通过后取数：

```javascript
const check = await j.precheckIssueType("CALL-1446");   // 类型不是「故事」时必须立即停止
const issue = await j.getIssue("CALL-1446");            // 也接受完整 URL
nodeRepl.write(j.renderIssueMarkdown(issue));           // 紧凑摘要，不要直接打印原始 JSON
const files = await j.downloadAttachments(issue.key, "<工作目录>\\work\\jira-gate-2\\CALL-1446\\attachments", { issue });
```

- `getIssue()` 返回规范化对象：描述、自定义字段（中文名）、附件、问题链接、子任务、评论、工时。
- `renderIssueMarkdown()` 是控制上下文的关键，用摘要做判定；只有摘要被截断时才回到原始对象取局部字段。
- 附件下载后用内置 Python 解析文本（脚本只支持动态导入，Python 走 PowerShell）：

```powershell
# $py 用 load_workspace_dependencies 返回的 Python 路径；<SKILL_DIR> 同上一层说明
& $py "<SKILL_DIR>\scripts\extract.py" "<附件目录>" --out "<附件目录>\..\attachments.txt"
```

若环境里已有可用的 `python`（需带 pdfplumber / python-docx / openpyxl / python-pptx），直接 `python extract.py ...` 也可以。

支持 `docx / pdf / xlsx / pptx / txt / md / json / xml / csv / html`；**解析失败要如实记为"无法解析"**，不能当成"附件没有内容"。图片附件用图像查看能力看，不做臆测。

附件是压缩包时脚本会先解压再递归解析（`.zip / .rar / .7z / .tar / .tar.gz / .tgz / .gz / .bz2 / .xz`），解压产物放在 `<附件目录>\__unpacked\`，输出里用 `压缩包名/内部路径` 标明每个文件的来源：

- **`.rar` 是重点**：服务端镜像已预装 `bsdtar`（libarchive-tools）与 7-Zip 系命令，脚本按 `bsdtar` → `7z` → `7zz` → `7za` → `unar` → `unrar` → `tar` 顺序降级，**容器内无需也无法通过联网安装来解决解压问题**；Windows 桌面端则由系统自带的 `tar.exe`（同为 bsdtar）兜底。
- **不要安装软件**：解压工具、Python 与 Node 依赖都已在镜像内备好。遇到工具缺失时如实记录并说明，不要执行 `apt-get` / `pip` / `npm` 等安装命令。
- 引用证据要写到压缩包内部，例如 `技术方案附件.rar/xxx_功能描述与技术方案.md §5.2`。
- 解压失败时会输出 `[压缩包解压失败]` 及尝试过的命令与报错，**这种情况必须如实记为"附件无法解析"，不能当成"附件没有内容"，也不要臆测包内内容**。
- 可选 `--unpack-dir <目录>` 指定解压位置；默认的 `__unpacked` 目录在遍历时会跳过，不会重复解析；同名解压结果自动加 `-2` 后缀，不覆盖上一次结果。

### 4. 取数：通道 B —— 应用内浏览器（无令牌时兜底）

没有配置令牌时，用已登录的应用内浏览器打开需求单：

1. `cua.createBrowserTab("iab", issueUrl)` 打开单子。
2. 用 `tab.playwright.evaluate(() => document.body.innerText)` 取正文，可拿到概要与描述、附件列表、问题链接、子任务、评论；**同时确认页面上的「类型」字段是「故事」**，不是就立即停止。
3. 附件：点击附件链接触发下载，再对下载目录跑 `extract.py`（压缩包会自动解压，见上一节）。
4. 结论评论：在页面评论区输入并提交。

注意：Jira 的 `/rest/...` 地址在浏览器里会被拦截（`ERR_BLOCKED_BY_CLIENT`），**不要在浏览器里访问 REST 地址**；浏览器只用于读页面和写评论。通道 B 的结论必须注明"基于页面内容检查"。

### 5. 逐项判定

对 `references/checklist.md` 的每条检查项给出：`满足` / `不满足` / `N/A`，并写明**证据位置**（技术方案章节、PRD 章节、代码/配置/数据库/日志/测试位置、附件名，必要时页码或行号）。

**必须覆盖的范围**：

- §5 全部 **10 项 `MUST`**：G2-M01 输入与事实源、G2-M02 目标/范围与现状、G2-M03 系统边界与主链路、G2-M04 实现路径与选型、G2-M05 接口/数据与状态、G2-M06 一致性/异步与幂等、G2-M07 权限与安全、G2-M08 非功能闭环、G2-M09 测试/发布与回滚、G2-M10 开发接管与任务约束。
- §6 全部 **`CONDITIONAL`**（G2-C01 ~ G2-C11）：命中后逐条判定；未命中的按组记 `N/A` 并给出未触发依据。
- §7.1 `SHOULD`：逐条记录取舍，不阻断结论。
- §7.2 `OBSERVE`：只记录 G2 后仍需验证、且不会改变接口/数据/核心流程/任务拆分/AC/发布方式的事项。

判定要求：

- 先定位输入：Jira 主单、有效 G1 结论、PRD 版本、技术方案版本、方案设计者、代码基线、涉及原型时的原型版本。任何一项不可唯一定位，G2-M01 直接不满足。
- 技术方案文件缺失、版本不可定位、G1 无效或方案与 PRD 版本不一致时，直接判定**退回补充**。
- 结论必须能指向具体证据；找不到证据就是"不满足"，不许写"已满足"。
- 输入冲突不得由 Agent、研发或 OpenSpec 静默选择：业务冲突退回 PRD 并重新 G1；技术事实冲突由方案设计者调查并修订技术方案。
- 纯代码组织或个人编码习惯差异，不改变外部行为、接口契约、状态、数据含义、权限、失败结果、测试结论或发布方式的，不阻断 G2。
- 不把"OpenSpec tasks 尚未创建"当作不满足；tasks 在 G2 通过后生成。
- 不把未决的模型参数、实验配置等可以在实施前继续细化的事项当作阻断，除非会改变失败策略或业务结果。

### 6. 得出准出结论

- **通过**：10 项 `MUST` 与所有命中的 `CONDITIONAL` 均满足；开发可以直接进入 OpenSpec `propose`，无需重新决定业务规则或关键技术方案。
- **退回补充**：任一适用 `MUST` 或命中 `CONDITIONAL` 不满足；或存在会改变外部行为、接口契约、状态、数据含义、权限、失败结果、测试结论或发布方式的未决技术问题。
- `SHOULD` 缺失只记录取舍，不单独阻断；`OBSERVE` 不得承载会改变实现、测试或发布路径的未决事项。
- 结论只允许两个取值：`通过` / `退回补充`。不要用总分、平均分或"基本通过"等模糊结论。

### 7. 组织评论内容

按本文档「输出模板」节的模板组织正文。**通过与退回补充用同一套结构**，差别只在标题措辞、每项标记与阻断项说明。评论正文包含：

- 顶部结论摘要：结论、OpenSpec propose 是否允许、结论说明、技术方案路径与版本、方案设计者、PRD 路径与版本、G1 结论位置、代码基线、阻断项数量、产品架构师确认人/时间、预检时间、状态流转。
- 机器判定明细：按 `MUST` / `CONDITIONAL` / `SHOULD` 分组的逐项清单，每项一行、行首必须带标记。
- 结论为「退回补充」时，摘要后按责任角色归并阻断项，便于分派；下方完整逐项清单仍必须保留，不得省略通过项。

**检查项清单的写法**

- 标记：满足写 `(/)`（绿勾），不满足写 `(x)`（红叉）。两者都必须显式写出，不允许留空或省略。
- 满足项：只写 `(/) *编号 名称*（等级）`；确有必要说明边界时，最多补一句 30 字以内的结论。
- 不满足项：写 `(x) *编号 名称*（等级）：问题 → 要补什么；证据：位置`。
- 未命中的条件组：写 `(/) *G2-Cxx 组名*（CONDITIONAL，N/A）：判断依据`；命中的组要展开到组内每个子项（如 `G2-C02.1`）。
- `SHOULD` 项不阻断：满足用 `(/)`，缺失用 `(x)` 并在括号里注明「SHOULD，不阻断 G2」。
- 排列顺序按 checklist 编号（G2-M01 → G2-M10 → G2-C01 → … → G2-C11 → 7.1.x）。
- 判定过的项都要出现，**不得只列不通过项**；不通过项不做删减，精简的是表述，不是缺口。
- 不要用表格（列宽大、手机上难读），用有序列表。
- 评论总长建议 ≤ 4000 字符；检查项多时可放宽到 6000。

### 8. 写 Jira 评论

- 写入前用 `mypermissions` 做一次只读权限预检（见 `references/jira-api.md` §7）；`ADD_COMMENTS=false` 时不要反复重试，直接告知用户缺权限。
- 用户已明确要求把结论落到评论时，直接写入，并在对话里同步摘要。
- 只有用户要求"先看草稿""不要写"时，才改为只展示内容不写入。
- 复审同一张单子时，先 `findPreviousReviews(key)`；有历史 G2 评论时**只在原评论下回复复审结论**（按最新判定重新打标记：本次已补的项由 `(x)` 变为 `(/)`，仍缺的项保持 `(x)`），不要新增第二条完整准出评论。
- 通过与否都写入同一套检查项清单：通过时标题写「通过（允许进入开发中）」。
- 结论为**退回补充**时，评论还要按 §9 在元信息区带上 `@` 流转人的「待处理人」行。
- 完整顺序见 §9 第 4 条：**写评论（含 @）→ 回写门禁字段 → 流转状态（仅退回补充）**。

### 9. 交付顺序与「仅退回补充时流转并 @ 流转人」

**第 4 条的交付顺序适用于全部结论；第 1～3、5 条的流转与 `@` 动作只在结论为「退回补充」时执行。** 结论为「通过」时：不做 `@`，也不执行任何状态流转，保持当前状态；评论与门禁字段两件事照常做。

1. 取流转人：`resolveFlowOwner()`，命令行即 `flow-owner <KEY|URL>`。**口径就是经办人**：优先取 `assignee`；经办人为空时才依次回退 `reporter` → `creator`，回退取到时必须在对话摘要里写明实际字段来源，不要静默 @ 到别人。返回的 `mention` 形如 `[~liu.huan]`，拼进评论即渲染为 @ 人。
2. 写评论：退回补充模板在元信息区固定多一行「待处理人」（含 `mention`），见「输出模板」节的示例。
3. 执行流转：
   - 结论为**通过**：不执行流转，也不要调用 `transitionToStatus()`；评论里写「未流转（通过，保持当前状态）」。
   - 结论为**退回补充**：`transition <KEY|URL> --to 开发设计中`（`transitionToStatus(key, "开发设计中")`）。
   - 目标状态名固定使用「开发设计中」，不要按项目改写成别的状态，也不要用「评审中」「待办」等替代。
4. **顺序固定为：写评论（含 @）→ 回写门禁字段 → 流转状态（仅退回补充）**。流转放在最后一个动作：评论与门禁字段都是判定留痕，不会因为流转失败而丢结论。
5. 评论里「状态流转：」的取值必须与真实结果一致。由于评论先于流转写出，**流转执行后必须核对返回值**：与评论里写的不一致时，用 `comment-update <KEY> <评论ID> --file <文件>` 把该行改成实际结论（删掉评论里的猜测值，不要留在单子上），并在对话摘要里说明。

| 返回值 | 含义 | 评论里怎么写（流转后核对，不一致就用 `comment-update` 修正） |
|---|---|---|
| `{ok:true, skipped:false}` | 退回补充流转成功 | 已流转至「开发设计中」 |
| `{ok:true, skipped:true, reason:"already-in-target"}` | 本来就在目标状态 | 已在「开发设计中」 |
| `{ok:false, reason:"no-transition"}` | 当前状态没有通向「开发设计中」的流转 | 未流转（该单当前状态无「开发设计中」流转） |
| 报错（403 / 权限不足） | 缺少 `TRANSITION_ISSUES` 权限 | 未流转（缺少流转权限） |

- 结论为**通过**时不调用流转接口，评论固定写「未流转（通过，保持当前状态）」，不要套用上表的流转结果。
- 评论先写、流转后做，所以评论里先按**预期结果**写；流转跑完必须核对，任一非成功分支都要 `comment-update` 改成上表的实际措辞。
- 流转未成功时**不要重试、不要改用其他状态**，也不要删掉 `@`：`@` 的职责是通知流转人来看红叉项，与流转是否成功无关。
- 流转前用 `mypermissions` 看 `TRANSITION_ISSUES`（见 `references/jira-api.md` §7）；为 `false` 时跳过流转动作，直接按上表写「未流转（缺少流转权限）」。
- 复审时结论由「退回补充」变为「通过」：不再 @，也不流转，保持当前状态；只在原评论下回复复审结论。

### 10. 回写门禁字段（用于 Jira 工作流门禁）

若 Jira 侧已配置 G2 门禁字段，写完评论后**必须**把结论回写，供工作流校验器/条件读取：

```javascript
const gate = await j.setGateResult(key, { result: "通过" });  // 退回补充时 result 写 "不通过"
nodeRepl.write(JSON.stringify(gate));
const back = await j.getGateResult(key);        // 写入后读回确认
```

- 字段不存在时返回 `{ skipped: true, reason, hint }`：**不要报错、不要重试、更不要伪造字段名**，照常交付评论，并在对话里说明"该 Jira 尚未配置 G2 门禁字段，本次仅留评论"。
- 字段名默认按 `G2准入结论` / `G2技术方案准出结论` / `技术方案准出结论` 与 `G2预检时间` 依次匹配；实际字段名不同时，修改技能目录下的 `jira-config.json`（`gateResultField` / `gateCheckedAtField`），不要改脚本。
- 取值约定：通过写 `通过`，退回补充写 `不通过`。
- 评论与字段必须一致：先写评论，再写字段；复审后结论有变化时重新回写一次。

### 11. 收尾：清理本次任务的工作区中间产物

全部应执行的交付动作（评论、门禁字段，以及退回补充时的流转）完成之后，把本次任务落在工作区的中间产物删掉，别让附件副本按任务堆积：

```bash
node <技能目录>/scripts/workdir-cleanup.mjs --key <KEY>
```

- 清理范围只有 `<工作目录>/work/jira-gate-2/<KEY>/` 一个目录（附件、`__unpacked/` 解压产物、`attachments.txt`、`comment.txt`、`gate.json`、`issue.md` 等中间文件）。
- 脚本按单号定位目录（单号不区分大小写），解析后的父目录必须正好是 `work/jira-gate-2`，否则拒绝执行——路径写错时不会误删工作区。
- 收尾是幂等的：目录已经不存在时返回 `{ok:true, removed:false, reason:"not-found"}`，不算失败。
- 想先看看会删掉什么，加 `--dry-run`：只统计文件数与字节数，不实际删除。
- **交付失败（异常中断）时不要调用本脚本**，保留现场便于排查。

## 预检规范

**取数范围**（以 Jira 需求单为唯一入口）

- 主单字段：类型（**必须是「故事」**）、概要、描述、优先级、客户名称、产品归属、影响的版本、经办人、标签、模块、工时 / Story Points。这些字段是**定位与证据来源**，字段缺失本身不构成不满足。
- 技术方案：`{需求名称}_功能描述与技术方案.md`（含版本）；方案中引用的架构图、时序图、接口定义、表结构变更、配置变更。
- PRD：已通过 G1 的指定版本 PRD（唯一业务事实源）。
- 原型/交互稿：涉及页面时必须有原型或用户确认记录及版本。
- 项目事实：`Project.md`、代码、配置、数据库结构、日志、测试；代码现状结论必须有可定位证据。
- Jira：需求范围、G1 结论、状态、责任与问题闭环记录。
- 历史评论：判断上次阻断项是否已关闭、技术方案是否已升版。

**证据要求**

- 每条判定必须指向**具体证据位置**：技术方案章节、PRD 章节、代码/配置/数据库/日志/测试路径、附件文件名（必要时页码或行号）、评论时间点。
- 不允许无证据的"已满足"；找不到证据一律记为"不满足"。
- 证据冲突时（技术方案与 PRD/原型/代码现状不一致）不得自行选择：业务冲突退回 PRD 并重新 G1；技术事实冲突由方案设计者调查并修订技术方案。
- 附件位于压缩包内时，证据写到内部路径，例如 `技术方案附件.rar/xxx_功能描述与技术方案.md §5.2`。

**禁止事项**

- 不把"检索工作"反问给方案设计者；不因为某项无法判定而停止其余项的检查。
- 不编造方案未写明的内容，不把推测写成已确认事实。
- 不把"OpenSpec tasks 尚未创建""Jira 子任务尚未拆分"当作不满足。
- 不把未决的模型参数、实验配置等可以在实施前继续细化的事项当作阻断，除非会改变失败策略、业务结果或发布路径。
- 不擅自修改需求单字段、不指派经办人（按 §9 流转状态）。
- 不 @ 无关人员：评论里的 `@` 只给流转人（默认经办人），也不因流转失败而删除 `@`。
- 不生成报告类文档、不上传附件；不在需求单中留下未完成的草稿评论。

## 令牌配置

凭证与地址解析顺序：容器内由后端注入 `SKILLRUN_ENV_LOCKED=1` 时**只认环境变量**（`JIRA_TOKEN`、`JIRA_BASE_URL`），不接受 `--token` / `--base-url` 与令牌文件，访问其它站点会直接报错；桌面端未注入该标记时按 入参 → 环境变量 → 令牌文件 解析。令牌文件按序查找 skill 目录下的 `.jira-token` / `.jira-token.txt` / `jira-token.txt`、`~/.codex/jira-token.txt`、`~/.codex/jira/config.json`（支持 `{"token":"...","baseUrl":"..."}`）。

`selftest()` 返回的 `baseUrl` 与 `baseUrlSource` 会标明本次实际访问的站点及来源；**若 `baseUrlSource` 是「内置默认值（生产 Jira）」而当前并非生产环境，先停下来修配置，不要继续写评论。**

- 令牌来源：Jira → 右上角头像 → 个人访问令牌 → 创建令牌（Jira 10.3 Server 已启用 PAT）。
- 令牌只用于 `Authorization: Bearer`，不要打印、回显或写进报告文件。
- `selftest()` 返回未找到令牌时，直接告诉用户按上面的路径放好令牌文件，并说明放好后可以立刻重试；同时可以先用通道 B 兜底完成检查。

## 硬性约束

- **只处理类型为「故事」的单子**；类型不符时立即停止，不做任何 Jira 写操作。
- 状态流转规则：**通过不流转（保持当前状态）**；**退回补充 → 开发设计中**；不得流转到「开发中」「评审中」「待办」等其他状态。不指派经办人。
- **唯一允许写入的字段是 G2 门禁字段**（`setGateResult()` 写入的准出结论/预检时间），它是评论结论的机器可读副本，不是新的事实来源。
- 不生成报告文档、不上传附件；判定结果只以 Jira 评论留痕。
- 不编造方案未写明的内容，不把推测写成已确认事实。
- 不把单据字段缺失、OpenSpec tasks 未生成、纯代码风格差异当作不满足理由。
- 不留下未完成的草稿评论。
- 交付全部完成后按 §11 清理本次任务的工作区中间产物（只删 `work/jira-gate-2/<KEY>/`）；交付失败时保留现场，不要删。
