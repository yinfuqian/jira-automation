# G1-Pre 上游需求准入规则（V1.0，2026-11-23 版）

> 本文件是 `jira-gate-1-pre` 的判定依据，内容对应《GENERIC_TEAM_G1_PRE_SKILLS》V1.0（tools_version V2.3.1，2026-11-17 创建、2026-11-23 更新）。
> 判定时以本文件为准；不要凭印象发明检查项或放宽口径。

## 1. 定位

G1-Pre 是 Jira 事项进入下一状态前的**上游需求准入检查**，只回答一个问题：
当前原始诉求是否足以让产品、研发或算法接手。

本技能负责：

- 读取 Jira 标题、描述、附件和必要字段。
- 判断原始诉求是否清楚、完整、无实质歧义。
- 只输出 `通过` / `不通过`。
- 不通过时按固定问题分类给出具体、可执行的补充要求。
- 通过或不通过时，均可给出不阻断准入的规范建议。
- 记录规则版本、内容哈希和检查证据，供 Jira 接入层判断是否允许本次 transition 继续。

本技能不负责：

- 决定各问题类型后续进入什么状态。
- 新建平行审批流程或替代 Jira 工作流。
- 判断需求是否达到 PRD、技术方案、测试方案或完整验收标准。
- 替产品、研发或算法补齐业务事实。
- 修改 Jira 状态、经办人、优先级、产品归属、截止日期、Story Points 或其他字段。
- 按 Issue Key、经办人或项目名称设置白名单和特例。

结论定义：

| 结论 | 含义 |
|---|---|
| `通过` | 原始诉求足以让接手人判断要解决什么、为什么解决以及期望结果；允许原 transition 继续。 |
| `不通过` | 存在阻断性缺口、冲突或实质歧义；终止本次 transition，退回提单人补充或调整。 |

「可以继续追问」不等于「可以准入」。只要缺少的事实会改变接手人对原始诉求的理解，就必须判 `不通过`。

## 2. 调用边界

### 2.1 触发点

接入层在用户触发 transition 后、状态实际变更前调用本技能：

| Jira 问题类型 | 触发动作 | 允许继续的目标状态 |
|---|---|---|
| `客户用户故事` | `跟进需求` | `需求澄清` |
| `故事` | `跟进需求` | `需求澄清` |
| `项目概算评估` | `开始评估` | `处理中` |
| `任务` | `开始进行` | `处理中` |
| `项目实施阶段` | `开始评估` | `处理中` |

transition 名称或目标状态与 Jira 配置不一致时，以实际 transition ID 为准；接入层应把实际 ID、源状态和目标状态传给技能。

本技能不定义后续流转。`客户用户故事` 和 `故事` 通常都在 `待办` 通过 `跟进需求` 进入 `需求澄清`；`项目概算评估`、`任务`、`项目实施阶段` 仍按各自工作流流转，不得互相套用。

### 2.2 不调用范围

以下事项不应调用本技能：

- 版本迭代、发版、测试环境或生产环境自动生成的任务。
- 会议、出差、考勤、工时、培训和其他事务性记录。
- 日常运维、权限申请、环境维护等不需要产品、研发或算法先理解业务诉求的事项。
- 已由系统规则明确识别为系统批量创建的事项。

是否属于上游事项由接入层基于问题类型、创建来源、项目、发起人角色和系统标签判断；**不得仅凭标题关键词判断**。

### 2.3 输入

技能至少接收：

```text
issue_key
issue_type
source_status
transition_id
target_status
summary
description
labels
reporter
assignee
attachments[]: id / filename / mime_type / readable
selected_fields
content_hash
dry_run
```

可用字段至少包括：客户名称、产品归属、问题发现产品、截止日期、优先级、当前状态、关联问题。

附件可读性必须区分「文件存在且文本可提取」「文件存在但只能查看」「文件不存在或不可访问」。**不得把无法读取的附件写成已经核验。**

### 2.4 信息读取顺序

1. 以 Jira 标题和描述建立原始诉求。
2. 用 Jira 字段补充客户、项目、问题类型和对象定位。
3. 用附件补充过程、样例、日志、指标和细节。
4. 检查不同来源之间是否一致。

附件不能替代标题和描述中的核心诉求。如果描述只有「详见附件」「看截图」「看日志」或「与某人沟通后处理」，即使附件存在，也不得通过。

## 3. 准入事实

### 3.1 必须逐项判断的事实

| ID | 事实 | 通过要求 |
|---|---|---|
| `F01` | 事项对象 | 能识别客户、项目、业务问题或待推进工作。字段可辅助，不要求必须出现页面、接口、域名、任务或项目阶段名称。 |
| `F02` | 业务或操作场景 | 能看出问题发生在什么使用、配置、交付或项目场景中。 |
| `F03` | 当前状态 | 能看出当前实际结果、现状或已发生的事实。 |
| `F04` | 问题、影响或诉求 | 能看出痛点、影响、限制、错误结果或希望改善的现状。 |
| `F05` | 期望结果 | 能看出希望达到什么结果，或希望产品、研发、算法进一步产出什么。 |
| `F06` | 内部一致性 | 背景、现状、问题、期望和证据之间无不相关或相互冲突。 |
| `F07` | 可供执行 | 当前信息不会使两名了解业务的接手人对下一步行动产生实质不同理解。 |

### 3.2 判定原则

- `F01` 到 `F07` 必须同时满足。
- 不得因为未使用模板、章节名称不同或没有 BadCase 而退回。
- 不得仅凭一句话、一个口号式短句或标题通过。描述至少需要分别组织出业务场景或当前状态、问题或影响、期望结果；可以使用不同表述，但不能只有一个概括句。
- 信息分布在标题、描述、字段和附件中时允许合并判断；但核心诉求必须由标题或描述明确表达。
- 一张单可以包含多个诉求。只要每个诉求分别满足 `F01` 到 `F07`，不得因数量多而退回。
- 多个诉求中仅某一项缺少关键事实时，只阻断该项，不重复阻断其他已清楚诉求。

### 3.3 不阻断信息

以下信息缺失不改变结论，只生成可选规范建议：

- 产品归属
- 截止日期
- 问题发现产品
- 业务价值
- 紧急程度
- 部署环境、网络拓扑、证书归属
- 测试条件
- 优先级
- Story Points
- 批次编号
- 需求实现类型
- 内部工时
- 产品方案
- 技术方案

客户版本、权限信息、测试环境等仅在会改变原始诉求理解或下一步判断时阻断；不能统一设为必填。

## 4. 条件场景

### 4.1 客户用户故事

功能、Bug 或优化类至少需要：

- 使用或操作场景。
- 当前实际结果。
- 期望结果或目标能力。

性能类至少需要：

- 受影响业务或用户。
- 当前现象或基线。
- 可核验目标。

效果、AI、LLM 类至少需要：

- 业务任务。
- 代表性输入或失败现象。
- 当前输出或效果问题。
- 期望效果。

### 4.2 故事

`故事` 与 `客户用户故事` 是不同 Jira 问题类型，但都用于承载需要产品或架构继续说明的业务诉求。两者通常都在 `待办` 通过 `跟进需求` 进入 `需求澄清` 前执行本检查，不要求提前形成完整 PRD。

功能、Bug 或优化类至少需要：

- 业务或操作场景。
- 当前实际结果和问题影响。
- 期望结果或目标能力。
- 本次需要覆盖的业务对象或范围。

性能类至少需要受影响业务、当前基线、可核验目标；效果、AI、LLM 类至少需要业务任务、代表性输入或失败现象、当前输出问题及期望效果。

`故事` 的默认触发点为 `待办 → 跟进需求 → 需求澄清`。进入 `需求澄清` 后的 `需求设计 → 评审中` 属于产品设计完成后的内部流转，**不再重复执行 G1-Pre**；如果目标项目使用其他初始受理 transition ID，接入层必须按实际 ID 映射，不得为了套用本规则改变 Jira 工作流。

### 4.3 项目概算评估

只判断需求本身是否清楚，不判断它应进入需求澄清还是评估。

至少需要：

- 需要评估的对象、需求或范围。
- 当前问题、限制或为什么需要评估。
- 期望得到的结果，如可行性、工作量、成本、周期或改造影响中的至少一项。

不强制填写报价用途、答复日期、评估输出模板或内部工时。

### 4.4 任务

至少需要：

- 要完成什么。
- 为什么需要完成。
- 可识别的完成结果或交付物。

缺少执行对象、完成标准且会导致无法开展工作时，按阻断处理；否则只给规范建议。

### 4.5 项目实施阶段

至少需要：

- 项目阶段目标或本阶段要推进的工作。
- 当前阶段状态。
- 阶段交付物或可识别的完成结果。

如果正文实际只是单点 Bug 复现，而问题类型是项目实施阶段，只给「建议确认问题类型」的规范建议；同时检查正文作为独立 Bug 是否具备场景、实际结果和期望结果。如果具备，结论仍可为 `通过`；如果不具备，按实际内容缺口判 `不通过`。

### 4.6 证据触发

| 场景 | 最低证据要求 |
|---|---|
| 界面异常、配置错误、操作失败 | 操作路径和实际结果；仅凭文字无法判断时提供截图或录屏 |
| 运行异常、接口失败、环境故障 | 错误现象和发生条件；需要时提供日志、请求响应或环境信息 |
| 性能、稳定性 | 当前现象或基线、目标指标、测量条件；需要时提供监控或压测数据 |
| 效果、AI、LLM | 代表性输入、当前输出和期望输出；需要时提供评测样本 |
| 渗透、安全、扫描类 | 问题范围、严重级别和受影响对象；扫描报告可补充细节 |

规则：

- 正文明确提到截图、日志或其他附件时，对应材料必须存在且可读取。
- 正文没有主动提到附件，但缺少某份材料会直接导致无法判断时，也必须要求提供。
- 附件不是默认必填。正文已能形成完整原始诉求时，不因没有附件退回。
- 纯业务需求、能力新增或目标明确的事项，不强制截图和日志。
- 不强制提供 BadCase；有具体失败案例时，说明输入、实际结果和期望结果即可。

## 5. 不通过问题分类

每条阻断问题只能归入一个主要分类，同一根因不得重复列出。

| 分类 | `category` | 适用情况 |
|---|---|---|
| 背景与需求内容不一致 | `background_content_mismatch` | 背景描述的客户问题与当前需求不相关、方向相反，或无法解释为什么需要该需求。 |
| 需求期望前后不一致 | `expectation_contradiction` | 标题、背景、问题说明、需求期望或附件之间，对目标、范围或结果给出相互矛盾的表述。 |
| 缺失关键信息 | `missing_key_information` | 缺少 `F01` 到 `F05` 中任一会阻止理解完整原始诉求的事实。 |
| 关键表述有歧义 | `material_ambiguity` | 已有表述存在多种合理解释，且不同解释会导致不同业务结果或下一步判断。 |
| 范围或归属不清 | `scope_or_ownership_unclear` | 多个诉求中存在无法判断是否属于本单、无法识别各自范围或责任归属的内容；不因单纯包含多个诉求阻断。 |
| 目标不可验证 | `unverifiable_target` | 性能、效果、质量类只写「更快、更准、提升一个数量级」，缺少当前基线、目标或判断方式。 |
| 关键决策未定 | `key_decision_unresolved` | 会直接改变原始诉求或结果的核心事实仍写「待确认、待定、后续决定」。普通非阻断事项中的待确认不归入此类。 |
| 描述与证据不一致或缺失 | `evidence_inconsistent_or_missing` | 正文与截图、日志或附件矛盾；声称提供材料但缺失或不可读；缺少判断问题所必需的代表性证据。 |
| 其他 | `other` | 无法归入以上分类时才使用，并说明不能归类的原因。 |

### 5.1 分类边界

- 背景与需求目标无关：`background_content_mismatch`。
- 同一目标或结果出现相反表述：`expectation_contradiction`。
- 缺少事实：`missing_key_information`。
- 已有事实但存在多种解释：`material_ambiguity`。
- 多诉求本身不阻断；每个诉求自身缺少必要事实时，分别按实际缺口归类。
- 性能、效果目标不可判断：归 `unverifiable_target`，不再重复归入 `missing_key_information`。
- 正文与附件矛盾或声称附件缺失：归 `evidence_inconsistent_or_missing`。
- Jira 问题类型不匹配只生成规范建议，不计入失败分类。
- 能归入已有分类时禁止使用 `other`。

## 6. 判定流程

### 6.1 第一步：识别事项

确认问题类型、源状态、目标状态、报告人和当前内容哈希。内容哈希至少覆盖：

```text
summary
description
attachment ids and file hashes
selected field values
issue type
transition id
```

`dry_run=true` 时只执行判定和评论生成，不写 Jira。

### 6.2 第二步：建立诉求清单

从标题和描述中提取多个诉求，逐项记录：

```text
claim_id
对象
场景
当前状态
问题或影响
期望结果
证据引用
```

一个句子包含多个独立目标时，拆成多个 claim；不得只检查第一项或最后一项。

### 6.3 第三步：核对事实与条件

逐一检查 `F01` 到 `F07` 和对应问题类型的条件场景。依据优先级：

```text
Jira 标题与描述
→ 结构化 Jira 字段
→ 附件和可提取证据
→ 评论或其他明确授权材料
```

评论、历史材料和下游技术方案只能补充事实，不能替代上游原始诉求。

### 6.4 第四步：去重并分类

- 重复问题先合并证据，再选择一个主要分类。
- 不同诉求的独立缺口分别保留。
- 不得把「类型不匹配」「字段建议」「模板格式」列为阻断分类。

### 6.5 第五步：生成结论

- 无阻断问题：`通过`。
- 任一阻断问题：`不通过`，并列出全部独立阻断项。
- 可选建议单独放入 `advisory_findings` 和 `field_hints`。

## 7. 输出契约

技能返回结构化结果：

```json
{
  "issue_key": "KEY-123",
  "issue_type": "客户用户故事",
  "conclusion": "pass",
  "rule_version": "V1.0",
  "content_hash": "sha256:...",
  "checks": [
    {
      "id": "F01",
      "status": "pass",
      "evidence": "标题和描述明确客户、页面与问题对象"
    }
  ],
  "findings": [
    {
      "category": "missing_key_information",
      "current_problem": "描述仅说明需要优化导出能力，未说明当前场景和实际影响",
      "suggested_supplement": "请补充当前在哪个场景操作、实际出现什么结果，以及期望达到什么结果"
    }
  ],
  "advisory_findings": [
    "建议确认 Jira 问题类型是否与实际诉求一致"
  ],
  "field_hints": [
    "建议补充产品归属"
  ],
  "jira_comment": "h3. (/) G1-Pre 准入通过\n*结论：* 当前原始诉求已满足准入要求，可进入下一状态。"
}
```

字段规则：

- `conclusion` 只能是 `pass` 或 `fail`。
- `findings[].category` 只能使用第 5 节固定枚举。
- `findings` 为空时结论必须为 `pass`；非空时结论必须为 `fail`。
- `advisory_findings` 和 `field_hints` 不参与结论计算。
- `checks` 必须覆盖 `F01` 到 `F07`，适用条件场景另行记录。
- `evidence` 引用标题、描述、字段或附件事实，不写内部推理过程。
- `rule_version` 和 `content_hash` 只供接入层幂等、审计和复检使用，**不得写入 `jira_comment`**。

## 8. Jira 评论

评论用于让提单人快速看懂结论、问题位置和修改动作。固定使用 Jira Wiki Markup，不输出 Markdown，不显示内部规则版本或内容指纹。

### 8.1 通过

仅通过时：

~~~text
h3. (/) G1-Pre 准入通过
*结论：* 当前原始诉求已满足准入要求，可进入下一状态。
~~~

有可选建议时追加：

~~~text
h4. 规范建议
* *问题类型：* 建议确认当前问题类型是否与实际诉求一致。
* *产品归属：* 建议补充对应产品线。
* *计划信息：* 建议补充截止日期。
~~~

规则：

- 通过评论默认只保留结论，不复制检查项和证据。
- `advisory_findings` 与 `field_hints` 都为空时，不生成 `规范建议` 章节，不输出「无建议」。
- 多条字段提示可以合并为一条，但不得遗漏实际建议。

### 8.2 不通过

~~~text
h3. (!) G1-Pre 准入未通过（2 项待补充）
*报告人：* [~huanghua] 请补充后重检。

h4. 1. 关键表述有歧义
*当前问题：* 第 3 项仅写“请求参数需支持按传入的标签进行返回”，未说明标签类型和多标签匹配方式。
*建议调整：* 请明确标签类型、请求参数格式，以及多个标签是匹配任一标签还是全部匹配。

h4. 2. 目标不可验证
*当前问题：* 仅要求降低保存接口耗时，未提供当前现象或目标。
*建议调整：* 请补充当前耗时基线、目标值和判断环境。

h4. 规范建议
* *产品归属：* 建议补充对应产品线。
* *计划信息：* 建议补充截止日期。
~~~

评论规则：

- 首个标题固定为 `h3. (!) G1-Pre 准入未通过（N 项待补充）`；通过时固定为 `h3. (/) G1-Pre 准入通过`。`N` 只统计阻断问题，不包含规范建议。
- 不通过时在结论下直接 `@报告人`，不单独写「请补充后重检」大段。
- 报告人 mention 固定使用 Jira 用户 key（如 `[~huanghua]`），不得使用显示名或邮箱拼接。
- 每条阻断问题使用 `h4. 序号. 问题分类`，形成清晰分段。
- 每条问题固定使用 `*当前问题：*` 和 `*建议调整：*` 两个加粗标签。
- 当前问题必须引用具体描述、字段或附件事实，不能只写「信息不完整」。
- 建议调整只索取通过准入所需的最小信息。
- 类型不匹配时说明建议类型，并明确哪些现有正文可以保留。
- 一次列出全部阻断项，不只返回第一处问题。
- `h4. 规范建议` 仅在至少存在一条实际建议时显示。
- 不显示 `rule_version`、`content_hash`、「G1-Pre 指纹」、sha256 或内部检查表；这些字段只供接入层幂等和审计使用。
- Jira Wiki Markup 必须正确转义，避免 `{{...}}` 被误当成用户提及。

### 8.3 不通过示例

背景与需求内容无关时：

~~~text
h3. (!) G1-Pre 准入未通过（1 项待补充）
*报告人：* [~huanghua] 请补充后重检。

h4. 1. 背景与需求内容不一致
*当前问题：* 背景说明客户需要解决登录超时，但需求内容是新增报表导出，未说明两者关系。
*建议调整：* 请说明报表导出要解决的具体业务问题；如果该需求与登录超时无关，请重写背景。
~~~

只有附件、没有正文时：

~~~text
h3. (!) G1-Pre 准入未通过（1 项待补充）
*报告人：* [~huanghua] 请补充后重检。

h4. 1. 缺失关键信息
*当前问题：* 描述仅写“详见附件”，正文没有说明要解决什么问题、当前影响和期望结果。
*建议调整：* 请先用正文说明诉求、场景和期望，附件可保留用于补充细节。
~~~

## 9. Jira 接入行为

### 9.1 通过

1. 技能返回 `conclusion=pass`。
2. 接入层允许用户触发的原 transition 继续。
3. 写入通过评论。
4. 不得由技能自动选择其他 transition 或修改其他字段。

### 9.2 不通过

1. 技能返回 `conclusion=fail`。
2. 接入层取消本次 transition，源状态保持不变。
3. 写入不通过评论并 `@报告人`。
4. 不自动修改优先级、经办人、Story Points、产品归属、截止日期或其他字段。

### 9.3 幂等和复检

- 同一 `issue_key + content_hash + rule_version` 已处理过时，不重复评论。
- 标题、描述、附件哈希或参与判定的字段变化后，生成新 `content_hash` 并重新检查。
- 只在 `content_hash` 未变化时沿用上一结论。
- `rule_version` 和 `content_hash` 只在接入层日志或任务元数据中保存；**Jira 评论中不得显示「G1-Pre 指纹」或 sha256**。
- **本仓库落地方式**：评论中不能保存指纹，因此 `g1-pre.mjs history <KEY|URL> --file <result.json>` 会把本轮渲染结果与最新一条 G1-Pre 评论正文比对；正文一致时不重复评论。`content_hash` 仍写入 `result.json` 供接入层审计，但不用作评论判重的唯一依据。
- 检查失败、无法读取附件或 Jira 写入失败时，不得静默放行；接入层必须返回执行异常并保持源状态。
- `dry_run=true` 时不得写评论、不得修改字段、不得执行 transition，只返回判定结果和拟写评论。

## 10. 禁止事项

- 不要把「还可以继续澄清」当成通过。
- 不要凭标题通过，也不要因描述短就直接拒绝。
- 不要把模板结构、章节名称、字数或 BadCase 数量当门槛。
- 不要要求上游提前提供完整 PRD、技术方案、测试方案或验收标准。
- 不要因产品归属、截止日期、问题发现产品等字段缺失而阻断。
- 不要因 Jira 问题类型不一致而单独阻断；只给可选规范建议，并按正文实际缺口判断。
- 不要把附件作为正文的替代。
- 不要声称读取了不可读附件或编造证据。
- 不要设置 Issue Key 白名单、按历史样例预设结论或针对特定提单人放宽规则。
- 不要在 Jira 评论中展示内部推理、完整检查表或规则清单。
- 不要在 Jira 评论中显示规则版本、内容指纹、sha256 或「G1-Pre 指纹」。
- 不要直接修改 Jira 状态或绕过 Jira 工作流。

## 11. 测试与验收

### 11.1 回归原则

- 实际判定必须在技能上运行，不得按 Issue Key 写白名单或预写通过结果。
- 每个失败分类至少准备一个命中样例和一个边界反例。
- 人工复核每条不通过原因是否引用真实内容、是否正确分类、是否说明影响并给出最小补充要求。

### 11.2 必测场景

| 场景 | 期望结果 |
|---|---|
| 对象、场景、现状、问题和期望均完整，且描述分层写清但篇幅较短 | `通过` |
| 仅缺产品归属、截止日期或问题发现产品 | `通过`，可选规范建议 |
| 只有标题、一句话或一句口号式描述 | `不通过`，`missing_key_information` |
| 只写「详见附件」而正文没有核心诉求 | `不通过`，`missing_key_information` |
| 正文提到截图或日志但材料缺失或不可读 | `不通过`，`evidence_inconsistent_or_missing` |
| 正文与附件对目标或范围表述相反 | `不通过`，`expectation_contradiction` 或 `evidence_inconsistent_or_missing` |
| 背景与需求目标无关 | `不通过`，`background_content_mismatch` |
| 已有表述存在两种合理解释且会导致不同结果 | `不通过`，`material_ambiguity` |
| 性能类缺少业务影响、基线或目标 | `不通过`，`unverifiable_target` |
| 效果类缺少代表性输入、失败现象或期望效果 | `不通过`，按实际缺口分类 |
| 多个诉求均表达完整 | `通过` |
| 多个诉求中仅某一项缺少关键事实 | `不通过`，只列该项缺口 |
| Jira 问题类型与正文不一致，但正文完整 | `通过`，只给规范建议 |
| Jira 问题类型与正文不一致，同时正文缺关键信息 | `不通过`，只列实际内容缺口，不把类型重复计为阻断 |
| `故事` 在 `待办 → 需求澄清` 前具备场景、现状、问题和期望 | `通过`，允许原 transition |
| `故事` 正文仅为题目或需求标题，缺少业务场景、现状和期望 | `不通过`，按实际缺口分类 |
| 正文空洞但模板字段名称齐全 | `不通过` |
| `advisory_findings` 与 `field_hints` 均为空 | 评论不显示 `规范建议` 章节 |
| Jira 评论 | 不显示 `rule_version`、`content_hash`、sha256 或「G1-Pre 指纹」 |

### 11.3 接入验收

- 五种目标 transition 分别验证 `通过` 放行和 `不通过` 阻断，包括 `客户用户故事`、`故事`、`项目概算评估`、`任务` 和 `项目实施阶段`。
- 验证不通过时源状态不变、报告人被 @、评论只含固定结构。
- 验证报告人 mention 使用 Jira 用户 key，不使用显示名或邮箱。
- 验证评论标题、分段和加粗标签按 Jira Wiki Markup 正常渲染，且不出现内容指纹。
- 验证同一内容哈希不重复评论，内容变化后重新判定。
- 验证 `dry_run` 不写评论、不修改字段、不执行 transition。
- 验证附件不可读或 Jira 写入失败时返回执行异常，不静默放行。
